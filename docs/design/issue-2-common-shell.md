### 3.1 参考事実

Issue #55には、ツールバーを通知領域の上へ移動すること、タップできるボタン寸法、送信・選択解除の右端配置、状態ボタンの枠線色と選択時の塗りつぶしが記載されている。Z字の視線・マウス移動は当時のレビュー理由として扱い、今回の画面に対する実証済みの操作性評価とはしない。

既存モックのコードでは、ヘッダーは48px、左ナビレールは72px。ヘッダーには画面名、日時、端末名、通信エラー表示を配置する。概況・設備入力・警報一覧はそれぞれ通知領域を持ち、降水ナウキャストには同じ専用領域がない。

実表示では概況・設備入力・警報一覧のツールバーと1段の通知領域が同じ下部位置に揃い、通知領域には通常時の操作案内と「詳細・はい・いいえ」の無効状態のボタンが表示された。ナビレールは最下部まで続き、通知領域はその右側の幅に収まっている。

降水ナウキャストは下部が再生・時刻操作とスライダーで占められ、他ビューの通知行がない。4ビューの切替でヘッダー内の画面名とナビ選択表示が変わることを確認した。

ナビレールを16:9画面の空間利用のために採用したという経緯は、今回ユーザーから共有された記憶として記録する。過去の意思決定資料による裏付けは未確認。

## 4. Issue #2の境界【既存要件】

- ヘッダー・左ナビレール・最下部通知領域を単一の固定シェルとして共有する。
- 防災気象情報・警報一覧・気象通報取得監視・訓練通知を切り替える。

- 通知の生成・保持を端末モードで分岐させず、表示側で絞り込める構造にする。
- ビュー内部、実際の通知判定・音・確認操作、認証・認可は後続Issueで扱う。

**訓練通知の扱い【方針転換】**: 基本設計§3.4は「ナビレールに、3.3（気象通報取得監視）配下の機能として『訓練通知』を追加する」と明記しており、独立画面（ダイアログではない）としての位置づけである。初稿では「独立した第4のビューの実装はIssue #2の範囲外」としたが、Issue #2はナビ構成そのものを扱う共通シェルの設計であり、基本設計が既に画面として確定させている項目をナビの型・一覧から外したまま進めると、後続Issueでシェル側の型定義・ナビ一覧・レイアウト前提を再度作り直すことになる。そのため、Issue #2では訓練通知のナビ項目・画面枠（プレースホルダー表示）のみを他ビューと同列に用意し、サンプル電文の注入・抹消操作、カタログ化、権限等の実装は引き続き後続Issueで扱う。

## 5. 領域構成【提案】

```text
┌──────────────────────────────────────────────────┐
│ ヘッダー：画面名／共通状態／日時・端末情報         │
├──────┬───────────────────────────────────────────┤
│      │ 主領域：選択中のビュー                     │
│      │ ビュー内で必要なスクロールを受け持つ       │
│ 左   │                                           │
│ ナビ ├───────────────────────────────────────────┤
│      │ 画面固有ツールバー（必要なビューのみ）     │
│      ├───────────────────────────────────────────┤
│      │ 共通通知領域（ナビレールを除く全幅）       │
└──────┴───────────────────────────────────────────┘
```

| 領域 | 共通シェルの責務 | ビュー・後続機能の責務 |
|---|---|---|
| ヘッダー | タイトル・端末情報・状態表示の配置 | 通知状態や接続状態の供給、鳴動・確認処理 |
| ナビレール | 最下部までの縦領域、遷移先、選択表示、モードによる表示制御 | 危険度バッジの値の供給 |
| 主領域 | 残りの幅・高さの提供 | 地図・情報パネル・一覧・監視の表示とスクロール |
| 下部ツールバー | 任意の配置枠（ナビレール右側の幅） | ボタン群、選択状態、送信処理 |
| 共通通知 | ナビレールを除いた全幅の単一の表示枠、ビューによらず維持 | 通知の選択・優先順位・確認・スヌーズ |

地図の時間操作カードは基本設計§4.3に従い地図内部に置く。汎用ツールバーへ移さない。汎用ツールバーが不要なビューでは、その高さを主領域へ戻す案とする。

共通通知領域はレイアウト上の高さを確保し、主領域に重ねない。ナビレールは共通通知領域の高さでも維持し、通知領域の左端はナビレールの右端に揃える。地図の中心計算はシェルが差し引いた後のビュー領域を受け取り、その内部の情報パネル・時間操作カードだけを考慮する。

## 6. 本番PoCへ流用するための構造【提案】

`AppShell` はヘッダー情報、ナビ項目、選択中ビュー、主領域、任意のツールバー、通知表示を外部から受け取る。気象固有のAPI呼び出しや通知判定を内包しない。初期段階では同一アプリ内のコンポーネントとして構成し、独立パッケージ化は利用先が具体化した段階で判断する。

端末設定の読み込みはアプリ起動側がURLの端末IDを基に行い、シェルには解決済みの端末名・`terminalMode` を渡す（§6.2）。モードによる非表示は認可機能ではない。

ナビ項目は安定したID、表示名、アイコン、表示可能なモードを持つ定義に集約する。Hモードで監視ビューを指定された場合の扱いは、防災気象情報へ戻す案とする。URL・履歴との同期方法は未確定。

共通通知の状態はビューより上位で保持し、画面切替により消失・再鳴動しない構造とする。本番統合時は中央アプリの通知機構から同じ表示境界に状態と操作を渡せるようにする。確認状態のサーバー永続化は今回の既存要件に含まれない。

### 6.1 テーマとヘッダー【ユーザー確定方針】

画面はダークテーマ固定とし、OSのテーマ設定に追従しない。Issue #1で用意したsystem/light/dark切替基盤に対し、本シェルではダークを使用し、テーマ切替UIは設けない。既存の保存値やOS設定で配色が変わらないよう、実装時に起動時のテーマ適用も合わせる。

ヘッダーは現状の構成・表示を維持する。現在日時への注釈は追加しない。ヘッダーのみ目立たせるためライトモードの色使いとし、本文のダークテーマと分けてMD3トークンを適用する。警戒レベル色と通知区分色は一般テーマから生成しない。

**ユーザー提案・適用範囲確認済み**: Kモードではヘッダー内の端末名バッジのみをターシャリー系の色で塗り、操作モードを識別しやすくする。ヘッダー全体の背景はH/K共通で現状の青系を維持する。K端末名バッジの具体的な色・文字色は見え方を確認して決める。

**ヘッダー上の操作範囲【ユーザー確定方針】**: ヘッダー上の操作はブザー停止のみとし、他の個別操作は設けない。したがって個別操作とブザー停止操作の同時発火を防ぐ境界の検討は不要とする。

### 6.2 端末IDとURL【ユーザー確定方針】

端末の入口は `server:port/tanmatsuID` とする。ブラウザでは使用するHTTP/HTTPSのスキームを付けてアクセスする。今回用意する端末IDは次の4種とする。

| 端末名 | 端末ID | URLパス | terminalMode |
|---|---|---|---|
| 東地区外務H1 | `hkeagh01` | `/hkeagh01` | `H` |
| 東地区外務K1 | `kkeagh01` | `/kkeagh01` | `K` |
| TRC公共H1 | `htrcph01` | `/htrcph01` | `H` |
| TRC公共K1 | `ktrcph01` | `/ktrcph01` | `K` |

**TRC端末のスコープ【ユーザー確定方針】**: TRC公共H1・K1は本リポジトリ限定の実験用構成であり、本番PoCへの統合対象には含めない。10/4に東京流通センターで外務の主要メンバーが集まるイベントがあり、準備が整えばそこで披露する機会の候補として用意する（§6.3）。本番統合時はTRC分の端末設定・地域対応を持ち込まない前提とする。

**実現方法【提案】**: 4端末の対応表をアプリ設定として持ち、URLパスの端末IDを照合して端末名・モードを解決する。先頭文字だけから任意のIDを有効と判定しない。Hでは取得監視を非表示にし、Kでは表示する既存方針へ接続する。ヘッダーの端末名とバッジ配色も同じ解決済み設定を使い、表示と動作の不一致を避ける。

端末IDは端末構成の選択に使用する。通知用の端末セッション識別子とは区別し、認証・認可や同一IDの複数ブラウザ利用の扱いを本Issueで新たに実装しない。端末別の気象対象は§6.3に定める。

各端末URLへの直接アクセス・再読み込みで同じ端末設定のシェルを表示できるようにする。ルート `/`、末尾スラッシュの扱い、および端末内のビュー切替とURL・戻る操作の関係は未確定。

**不明な端末ID【ユーザー確定方針】**: ユーザーは404または403を許容した。配信側でHTTP 404を返せる構成であればそれを優先する。別端末へフォールバックしない。開発用Viteや配信環境の制約でHTTP 404を返せない場合は、フォールバックとしてシェルを表示せず「許可されていない端末です」等のメッセージのみを表示する案とする。この場合の応答ステータスは問わないが、既存端末のシェルを誤って表示しないことを最優先とする。開発用Viteと本番配信の両方で直接アクセス・再読み込み時の挙動（ステータスまたは表示内容）を確認する。認可判定の実装は本Issueに追加しない。

### 6.3 TRC端末と気象対象【ユーザー指定】

TRC端末は、2026年10月4日に東京流通センターで外務の主要メンバーが集まるイベントにおいて、準備が整えば披露するために用意する。これは利用機会の候補であり、同日までの全機能完成を新たな必須条件とはしない。日付・用途・下表のTRC情報はユーザー提供情報として記録する。

| 設定 | 東地区外務H1・K1 | TRC公共H1・K1 |
|---|---|---|
| 会場 | 東京ビッグサイト | 東京流通センター |
| 地図の基準位置 | 基本設計§4.3に従う | 北緯35.58度・東経139.75度（ユーザー指定） |
| 警報・注意報等の対象市区町村 | 江東区 | 大田区 |
| アメダス | 江戸川臨海 | 羽田空港（ユーザー指定の最寄り地点） |

**構成案**: 端末設定から会場・対象地域の設定を参照する。H/Kは機能の表示モード、会場設定は地図の基準位置・情報対象を決める独立した項目とし、同一会場のH/Kは同じ対象を使う。地図を移動しても情報パネルの対象は変えない既存方針を維持する。

取得側の地域コード・羽田空港の地点コード・取得可能な観測要素は未検証。後続のデータ取得・パネル設計で確認し、欠測や未提供の要素を他地点で無表示のまま代替しない。気象防災速報の対象判定も、大田区を含む情報に対応させる必要がある。Issue #2では設定と受け渡しの境界を扱い、取得・正規化・地図・情報パネルの実装は各後続Issueで行う。

## 7. 画面寸法と操作性

**ユーザー確定方針**: PC前提でタッチ操作も考慮し、特定OSには依存しない。ヘッダーは現状維持（既存CSSは48px）、ナビレールは既存72pxを比較の基準とする。主対象の解像度・拡大率は未確定。1920×1080と1366×768を評価候補とし、ブラウザの実表示領域も考慮する。

**通知領域の高さ【ユーザー確定方針】**: 全体で現状の2倍を目標とし、操作領域を極力圧迫しない。既存CSSの通知領域は48pxなので、設計上の初期目標は約96pxとする。ツールバーの高さを含めて倍にする意味ではない。使いづらければ調整する前提であり、96pxを厳密な上限にはしない。警報・問いかけ・操作の各行への配分はタッチ操作と文字の読みやすさを確認して決め、一律32pxの操作ボタンを前提にしない。

確認する点は、長い画面名と端末名・日時の衝突、ナビラベルの判読、下部操作と通知が占める高さ、通知長文・複数件時の操作位置、キーボードフォーカスの見え方と移動順序とする。主領域に `min-width: 0`・`min-height: 0` 相当の縮小可能な境界を設け、コンテンツの大きさでシェルが画面外へ押し出されない構成を想定する。

通知なし・ありで主領域が上下することを避けるため、通知領域は基本高さを予約する案とする。各行の配分・長文時の扱いは約96pxの初期目標の中で具体化する。

## 8. 通知の滞留と再通知に関する協議

### 8.1 確認された課題【ユーザー説明】

既存モックは、非常通報のブザーを停止しても通知領域にメッセージを残す仕様とした。その結果、後から設備変更申請等の問いかけが到着しても表示されなかった。音を止めたことと業務上の対応完了は別であり、非常通報の存在を残しながら後続通知も表示できる構成を目指す。

操作説明・操作結果は常に表示できることをユーザーが求めている。警報・問いかけ・操作の役割分けはIssueコメントの決定事項に合わせる。試作では3行に分け、各行の寸法を確認する。

### 8.2 ユーザー提示の方向性

- 通知受信時に、操作領域へ未読・未対応通知の件数を表示する。
- 未対応の事象を放置した場合、カウントダウン終了後に警報または問いかけで再通知する。
- ヘッダーの「受信異常」と同様の表示パターンで「非常通報」を表示する。

以下は、この方向性を具体化する提案であり、詳細まで承認済みとは扱わない。

### 8.3 表示と状態の役割分担【提案】

**協議で明確になった方針**: 非常ブザーは問いかけ扱いとし、問いかけ行に表示する。独立した第4行は設けない。通知データ上の「非常ブザー」区分は既存の鳴動・スヌーズ仕様のために維持し、表示行への割り当てと区別する。ユーザーはトーストやバッジを極力増やさず、拡張した通知領域へ表示を集約する意図を示した。件数は通知領域の操作行内に文字と一覧への入口として配置する案とし、ナビや画面各所へバッジを追加しない。具体的な寸法は未確定。

| 表示先 | 役割 | 継続・更新の案 |
|---|---|---|
| 操作領域の件数表示 | 未読・未対応の残件に気付ける入口 | 受信時に更新し、残件がある間は維持。操作説明・結果を上書きしない独立した位置に配置 |
| 警報・問いかけ行 | 新着通知・再通知の内容を読む | 停止済みの非常通報が後続通知を塞がない表示選択。回答操作中の強制切替は避け、待機件数を示す |
| ヘッダーの非常通報表示（採否再検討） | 非常事象が未対応で残っていることを示す | 先の候補案。表示集約の方針を踏まえ常設を前提にせず、問いかけ行・未対応件数だけで十分に認識できるか比較する |
| 操作説明・結果 | 現在の操作と実行結果を確認する | 通知の受信・再通知と独立して表示 |

**操作結果【ユーザー確定方針】**: 表示先は通知領域内の操作領域とする。操作メッセージは後から来たものを優先して置き換え、シェルではログを管理しない。一度消えた操作メッセージを履歴・再表示・キューからシェル側で出し直さない。この規則は操作説明・結果の表示に関するものであり、警報・問いかけの未対応事象の保持や再通知、既存要件の業務履歴保存を廃止するものではない。残件数と操作メッセージは同じ領域内で共存させる案を維持する。

「未読」は通知を読んだか、「未対応」は事象への必要な対応が完了したかを示し、別々に管理する。同じ対象が両方に含まれ得るため、件数を足して総件数とはしない。既読になる操作、未対応件数を通知単位・事象単位のどちらで数えるか、対象端末・担当者の範囲は未確定。

**時刻の意味【ユーザー確認済み】**: クライアント（ブラウザ）がサーバーと最後に通信成功した時刻を示す。サーバー側の気象データ取得成功時刻ではない。

ユーザーが表示中のモックを画面遷移・再読み込みせず確認し、ヘッダー中央に赤い「受信異常｜最終更新: 17:34:28」、右側に現在日時が表示されていることを目視確認した。この確認は表示の観察であり、通信失敗・復旧の判定ロジックの検証ではない。

**受信異常の表示【ユーザー確定方針】**: ヘッダーは現状維持とし、表示ラベルも「最終更新」を維持する。H端末の地区本部ユーザーに対してサーバーより先の通信事情を説明する必要はなく、「最終通信成功」への改称や注釈追加は行わない。内部的な時刻の意味は上記のとおりブラウザとサーバーの最終通信成功である。正常時の常設表示は追加しない。異常発生・復旧を警報行にも通知するかは後続の通知設計で具体化する。

時刻は失敗した通信試行で更新せず、初回通信成功前は「通信成功なし」と表示する案とする。どの通信を成功判定の対象にするか（監視用通信・業務API等）、一部APIのみ失敗した場合の扱い、異常・復旧の判定条件は後続設計で具体化する。サーバー側の情報取得状態とは独立して扱う。

非常通報もヘッダーに置く場合は、受信異常との同時表示方法を検討する。「同じパターン」は表示形式の踏襲を指し、点滅・音まで同一にすることは意味しない。

### 8.4 カウントダウンと再通知【提案・詳細未確定】

再通知は元の事象を参照して発生させ、再通知のたびに未対応の事象件数を増やさない。期限到達時に現在も未対応かを確認し、完了・取消・解除済みの対象は再通知しない。画面切替をタイマーのリセット条件にしない。

開始点（受信・ブザー停止・既読）、待ち時間、事象種別ごとの通知区分、再通知後の反復間隔、対応中の扱い、残り時間の表示場所は今後決める。既存の非常ブザースヌーズと再通知は別の目的を持つため、同時に期限が来た場合の重複鳴動を防ぐ規則も必要。

本番で再読み込み・複数端末をまたいで期限を扱う場合の管理主体と永続化は、本番通知機構の設計で決める。シェルは残件・非常状態・必要な期限情報を受け取り表示する境界を持ち、業務上の未対応判定やタイマーの正本を内包しない。

### 8.5 今回の範囲と確認例

Issue #2の設計では表示枠・状態の受け渡し・後続機能との境界を扱う。設備変更申請・非常通報の業務処理、再通知エンジン、担当者別の既読・対応状況の永続化は本Issueの実装範囲へ追加しない。気象PoCの確認状態は基本設計どおりフロントの一時状態であり、本番の業務対応完了と同一視しない。

後続の通知機能で確認する代表例は「非常通報受信→ブザー停止→設備変更申請受信」。このとき、非常通報の未対応状態と一覧への入口を残しつつ、申請を問いかけ行に表示し、残件表示を更新し、操作説明を維持できることを確認する。加えて、期限前の対応完了で再通知しないこと、再通知で事象件数が増えないことを確認する。ヘッダーへの非常通報表示も採用する場合は、受信異常との同時表示を確認する。

## 11. 試作実装（2026-09-08）

以下は着手指示を受けて具体化した実装案であり、新たなユーザー確定事項とは区別する。§6・§7・§9の未確定事項のうち、試作に必要な動作を以下で定めた。

### 11.1 構成と責務

- `apps/web/src/shell/AppShell.tsx`: 解決済み端末・ヘッダー状態・日時・ナビ定義・ビュー・任意のツールバー・通知表示を受け取る。API呼び出しや通知判定は内包しない。ヘッダーのブザー停止はコールバックの境界のみ用意し、今回のアプリでは接続しない。ナビレールの右端に区切り線を引き、通知領域・主領域との境目を明示する。
- `config.ts`: 登録済み4端末を完全一致で照合する。H/Kと会場設定を分離し、同会場のH/Kは同一の設定を参照する。TRCは実験用フラグと指定座標を保持し、東地区の具体座標は地図実装で確定する。`views`は防災気象情報・警報一覧・気象通報取得監視・訓練通知の4項目で、取得監視・訓練通知はKのみに表示する。各項目は`label`（ナビ表示用・4文字以内）と`title`（ヘッダー表示用・フル名称）を別に持つ。
- `App.tsx`: ビューより上位で通知配列と単一の操作メッセージを保持する。画面切替で消去しない。再読み込み時の永続化はない。ビューごとのプレースホルダー文言（記号・見出し・説明）は`ViewId`をキーにした対応表として保持する。
- `notifications.ts`: 保持した通知を変更せず、表示時にHの装置異常を除外する境界を設ける。未読・未対応の件数は表示対象から別々に集計する。試作では1通知を1事象とし、実運用の事象集約は後続設計で定める。
- `NotificationArea.tsx`: 警報・問いかけ・操作の3行。行の意味は色分けと内容から読み取れるものとし、「警報」「問いかけ」「操作」の文字ラベルは付けない。無通知時も空欄のみで「〜はありません」等の文言は出さない。常時表示のボタンは警報行が[詳細][確認]、問いかけ行が[詳細][送信]。問いかけの選択肢（はい/いいえ等）は通知データが都度提供する想定で、試作では選択肢UIそのものは実装しない。複数件時の「ほかN件」表示は設けない。未読・未対応件数は操作行にリンクなしのプレースホルダーとして表示するのみで、一覧への遷移は行わない（試作では警報一覧プレビューの仮実装ごと削除済み）。

### 11.2 URLと遷移

| 入力・操作 | 試作での動作 |
|---|---|
| `/` | 端末未指定の案内のみ。端末一覧や既定端末への自動移動は設けない |
| 登録端末URL | 対応する名前・モード・会場を表示。ビュー指定なしは `#weather` |
| 登録端末URLの末尾 `/` | 同一端末として受け付け、履歴を増やさず末尾なしへ正規化 |
| ナビ操作 | `#weather`・`#warnings`・`#monitor`・`#training`。戻る・進むでビューを復元 |
| Hで `#monitor`・`#training`、未知のハッシュ | 履歴を増やさず `#weather` へ置換 |
| 未登録端末・余分なパス階層 | Vite開発／ビルドプレビューでHTMLナビゲーションにHTTP 404と案内を返す |
| 配信側がSPAフォールバックする環境 | クライアントでも再検査し、シェルを表示せず案内のみ。HTTP 404は配信設定で実現する |

HTTP 404を標準とし、クライアントの案内は配信環境に備えた防御的な代替とする。Vite previewは本番ビルドの検証用であり、本番配信サーバーそのものではない。実デプロイ先での404は配信基盤の実装時に確認する。

### 11.3 寸法・色・操作

- ヘッダー48px、ナビ72px。ヘッダーはライトのMD3 primary/on-primary、K端末名バッジはtertiary-container/on-tertiary-containerを局所適用する。本文は起動前からダーク固定で、保存済みテーマ・OS設定に依存しない。ナビレール右端に1pxの区切り線を引く。
- 通知領域は§7の約96px目標に合わせ、**32px × 3行 = 96px** を常時予約する。短文中心の実メッセージを踏まえた寸法で、長文は行内部で折り返し・スクロールし、行の高さ・ボタン位置は動かさない。ビューごと・通知有無による高さの変化はない。
- 通知領域はナビの右側全幅。主領域だけをスクロールでき、シェルは画面内に固定する。
- 常時表示のボタンは警報行[詳細][確認]、問いかけ行[詳細][送信]（後続実装のため無効）。選択肢UI・件数表示からの遷移は試作に含めない。
- 警戒レベル色・通知区分色（警報行・問いかけ行の背景色、受信異常バナー）はテーマトークンから生成しない方針（§6.1・§3.4.4）自体は満たすが、試作では値をコンポーネントCSSへHEXで直書きしており、[Issue #1設計](issue-1-project-initialization.md)§3.4.2・§3.4.4が求める「セマンティックトークン化」にはまだ対応していない。[Issue #90](https://github.com/BlueKurage119/wx-viewer-poc/issues/90)（A5. 警戒レベル・通知区分のセマンティックカラートークン定義）で対応する。
- 760px以下ではヘッダー88px・通知180pxへ拡張する補助配置を設ける。主評価対象はPCであり、小画面最適化の完了を意味しない。

### 11.4 表示確認と対象外

開発時のみ、端末URLへ `?shellPreview=1` を付けると表示確認用ツールバーを表示する。通知なし・長文・複数区分・操作結果と通知・受信異常を切り替えられる。全通知は表示サンプルと明記し、実気象情報として扱わない。本番ビルドではこのUIを表示しない。

「最終更新」はブラウザとサーバーの最終通信成功時刻。試作は通信判定を接続せず、異常表示のサンプルでは成功時刻がない場合の「通信成功なし」を表示する。実際の状態判定・復旧・ブザー停止・確認・再通知・気象取得は後続Issueの範囲とする。
