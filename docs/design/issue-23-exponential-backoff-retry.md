# Issue #23「C13. 取得失敗時の指数バックオフ・再試行処理」設計

作成日: 2026-09-12

## 1. 目的と範囲

GitHub Issue #23「C13. 取得失敗時の指数バックオフ・再試行処理」を実装するため、気象庁 XML フィード取得の失敗をフィード単位で管理し、正常な前回値を壊さずに復旧取得を行う設計を定める。

本 Issue では次を対象とする。

- すべての XML フィードおよび個別電文 GET に適用する 10 秒タイムアウトを、HTTP 取得境界で一貫して用いる。
- フィード本文の取得または Atom 構造解析に失敗したフィードだけを、60、120、240、300、300 秒…の指数バックオフで再試行する。成功時には当該フィードの連続失敗数と待機状態をリセットする。
- #22/C12 の初期取得が失敗した場合、失敗したフィードを再試行し、初期取得に必要な4フィードがすべて成功した時点で初期取得状態を完了へ遷移させる。
- 通信失敗、構造不正、未対応コード／形式を同一の「正常な発表なし」に縮退させず、取得試行履歴・電文受信履歴・サービス状態の責務に応じて別々に残す。
- 取得失敗時に既存の正常スナップショットや受信履歴を空配列・空スナップショットで上書きしないことを、既存 processor と repository の境界で回帰テストする。

次は対象外とする。

- §8.1 の遅延・異常の閾値判定、設定ファイル化、装置異常通知の生成（C14、D系、E10/K系）。連続失敗数・最終成功時刻は後続が利用できる状態として残すが、ここで「遅延」「異常」を決定しない。
- JST 時間帯別の通常周期、夜間停止・再開契機（C14）。
- 開始・停止・強制更新の HTTP API、操作者要求の重複防止（E11）。
- XML 以外の雨雲・キキクル・アメダスの再試行方式。
- 既存の電文種別固有 parser が判断する採用可否・未知コードの意味付けの変更。

### 2.2 確定事項と判断

統括ヒアリングで、HTTP タイムアウトは10秒、バックオフ初期待機は60秒、上限は5分と確定している。失敗時には正常な前回値を保持し、空配列で上書きしない。不正構造・未対応コードは通信失敗とは別に記録する。Issue #23 本文に追加の未決事項はない。

取得方法レポートは、フィードに掲載がないことを「発表なし」とせず、通信失敗・不正構造・未対応形式を区別することを求める。基本設計 §8.1 も、取得試行の成否と情報の復元・解析成功を別判定とする。従って、フィード HTTP／Atom の失敗だけをフィード再試行の対象とし、正常に取得・解析できたフィード内の個別電文失敗、対象地域外、未対応電文はフィード失敗へ混ぜない。

製造開始時は #22 のマージ済み設計・実装・テストを再照合し、下記の統合条件を満たすよう調整する。

1. フィード HTTP／Atom 成功と、個別電文の失敗件数を区別できる公開結果があること。
2. 初期取得の失敗フィード集合と、初期取得を完了へ遷移させる正規の状態 API があること。
3. 待機中のフィードを通常周期で開始しないこと、および停止時に再試行タイマーを残さないこと。
4. #22 が `retryBackoff.ts` を先行導入している場合も、C13 の要件を満たすテストと復旧スケジューリングを追加すること。既存実装の存在だけで受け入れ済みとはしない。

## 3. 状態・再試行設計

### 3.1 失敗の分類と記録先

| --- | --- | --- | --- | --- | --- |

`errorKind` の文字列集合や `adoptionResult` の既存値は、#22 統合後の repository 型を正とする。本 Issue は通信失敗を未対応コードへ読み替えず、その逆も行わない。エラー文・URL は既存のサニタイズ規則を通し、認証情報やヘッダを保存・公開しない。

通知レベル案は、D7／§8.4 が将来通知を生成するための入力分類であり、C13 は通知・通知出力履歴を生成しない。§8.4 の確定対応は「遅延＝警報」「異常＝問いかけ」である。本表の単発フィード失敗を警報（案）、連続失敗等が後続で定める §8.1 の異常閾値に達した状態を問いかけ（案）とする。遅延・異常の具体的な閾値、状態変化時の重複抑止、実際の通知文・出力は本 Issue で決定・実装しない。

### 3.2 フィード単位のバックオフ状態

各 `JmaXmlFeedKind` ごとに、プロセス内の次の状態を持つ。再起動をまたぐ永続化は本 Issue の対象外であり、新プロセスでは初期取得から状態を組み立て直す。

```ts
export interface FeedBackoffStatus {
  readonly feedKind: JmaXmlFeedKind;
  readonly consecutiveFailures: number;
  readonly isWaiting: boolean;
  readonly waitingReason: string | null;
  readonly nextAllowedFetchAt: UtcIso8601String | null;
  readonly lastAttemptAt: UtcIso8601String | null;
  readonly lastSuccessAt: UtcIso8601String | null;
  readonly lastFailureAt: UtcIso8601String | null;
}
```

失敗回数を `n`（1以上）とすると、待機秒数は `min(60 * 2^(n - 1), 300)` とする。すなわち 60、120、240、300、300 秒…である。失敗を記録した時刻を基準に `nextAllowedFetchAt` を計算する。成功時は `consecutiveFailures=0`、待機理由と次回許可時刻を `null` に戻し、`lastSuccessAt` を更新する。別フィードの状態には影響しない。

待機判定は `now < nextAllowedFetchAt` とする。等しい時刻は再試行可能である。時計・タイマーは注入可能にし、テストで実時間の60秒待機を行わない。

### 3.3 スケジュールと初期取得復旧

通常周期と再試行を、同じサービス内の単一の次回タイマーで調停する。並列の「通常タイマー」と「再試行タイマー」を無条件に増やさず、in-flight サイクルは既存どおり1本に集約する。

```text
フィード取得失敗
  └─ fetch_attempt に失敗を記録
  └─ 当該フィードの nextAllowedFetchAt を更新
  └─ 既存の情報スナップショット・受信履歴は保持
  └─ サービス稼働中なら、通常周期予定と再試行可能時刻の早い方を次回起動に設定

次回起動
  ├─ 初期取得が failed の間: 失敗フィードだけを recovery として再試行
  │    └─ 初期4フィードがすべて成功済みになれば InitialFetchStatus を completed へ更新
  └─ 初期取得完了後: scheduled 対象のうち待機終了済みの失敗フィードを再試行し、
                       それ以外の通常対象も通常周期どおり取得
```

初期取得失敗後の復旧は、すでに成功した長期フィードまで再取得しない。成功済みフィードを含む無差別な `pollOnce('recovery')` の4フィード実行は、復旧対象を不必要に増やし、失敗フィードだけを再試行する本 Issue の目的に反する。そのため、製造時にはフィード集合を明示できる内部 API（例: `pollFeeds(trigger, feedKinds)`）を導入するか、同等の非公開機構で対象集合を渡す。公開の `pollOnce(trigger)` の既存契約を変える必要がある場合は、E11 と #22 の利用箇所を確認して互換性を保つ。

`initialFetch.phase='failed'` の再試行では、過去に成功したフィードと今回成功したフィードの和が初期4フィードを満たしたときだけ `completed` に遷移する。通常 `scheduled` の高頻度2フィード成功だけで初期取得完了にしない。再試行中は `initialFetch.phase` を「再試行中」と別値に増やさず、既存 #22 の状態型を保ったまま、失敗結果とフィード状態から進捗を参照できるようにする。

停止時は通常・再試行の次回投入を取り消し、実行中サイクルを待つ。`stop()` 後にタイマー callback や finally 節が新しい取得を予約してはならない。再開・手動強制更新時にバックオフを無視するかは E11/C14 の責務として、本 Issue の自動再試行では待機を破らない。

### 3.4 正常な前回値の保持

フィード取得失敗および個別電文取得失敗の経路は、snapshot repository の replace/create API を呼ばない。従って既存の `available` スナップショットの items、metadata の正常時刻、受信履歴を空集合で置換しない。

情報種別固有 processor が正常な本文を採用した場合だけ、既存の版比較・スナップショット更新規則に従う。正常に取得した本文が「対象情報なし」を意味するかは、その種別の確定済み parser/processor の責務であり、通信・構造失敗を空一覧へ変換する根拠にはしない。

`available` / `stale` / `unavailable` の遷移閾値・集約は本 Issue で決定しない。現在の repository が `stale` スナップショットを保存できることと、取得失敗時に既存値を保持することを混同しない。C13 は、後続の遅延判定が使える `lastSuccessAt`・失敗回数・失敗履歴を正しく残す。

### 4.2 API 境界

既存の `performHttpGet(url, { timeoutMs })` をすべての XML GET の単一境界として維持し、既定値10,000msをテストで確認する。呼び出し側ごとに別の timeout 実装を作らない。

`JmaXmlPollingService.getStatus()` は、少なくとも `initialFetch`、フィード別 `FeedBackoffStatus`、直近サイクルを返す。後続の監視機能はこの状態と `fetch_attempt` を投影するが、本 Issue は表示用の状態名や閾値を追加しない。

フィードを限定して再試行する内部 API は、呼び出し側が任意 URL や任意フィードを注入できない型付き境界とする。対象は `JmaXmlFeedKind` の固定集合だけで、`JMA_XML_FEED_DEFINITIONS` の URL 検証・取得規則を迂回しない。`attemptNo` は当該フィードの連続失敗数に基づき、成功後は次の失敗を1回目として記録する。

## 5. テスト計画

テストはローカル HTTP サーバー、一時 SQLite DB、注入可能な `clock` / `fetchFn` / タイマーを用いる。実ネットワーク・実時間60秒待機・既定開発 DB は使わない。新規テストは対象の実装を意図的に壊して red を確認し、意味を変えない対照変更が生存することも確認してから完成とする。

1. `performHttpGet` が10秒の既定 timeout を渡し、timeout、ネットワーク例外、HTTP非成功を `httpStatus=null/null/status` と対応する失敗種別で完全に記録する。
2. 同一フィードの連続失敗で待機が 60、120、240、300、300 秒となり、待機終了時だけ次の試行を許可する。別フィードは待機中でも取得される。
3. 成功後に連続失敗数・待機理由・次回許可時刻がリセットされ、次の失敗が60秒から始まる。
4. 待機中のフィードは通常サイクルで HTTP GET・`fetch_attempt` を新規作成せず、待機理由と次回許可時刻を状態で参照できる。
5. フィード HTTP失敗または Atom構造不正ではフィード試行が失敗として記録され、既存の正常な snapshot の全項目・metadata が完全一致で保持される。空配列の snapshot が追加されない。
6. 個別電文の HTTP失敗では当該 `xml_document` 試行だけが失敗になり、フィード取得は成功、フィードのバックオフは増えない。既存正常値を保持する。
7. 未対応構造・未対応コードを含む本文は通信失敗とは異なる reception の採用結果／理由として保存され、フィードの通信バックオフを増やさない。正常な発表なしの空スナップショットを作らない。
8. #22/C12 の初期4フィードのうち1本が失敗した後、60秒前に再試行されず、待機終了後は失敗したそのフィードだけが `recovery` として再試行される。成功済みの3本を再取得しない。
9. 初期取得失敗後、再試行で不足フィードが成功したときだけ `initialFetch` が `failed` から `completed` へ遷移する。通常高頻度フィードだけの成功では遷移しない。
10. 停止中は再試行が起動せず、再試行待ち・通常周期・初期取得の timer が重複しない。in-flight 中の複数要求も1回の取得に集約される。
11. `npm run build`、`npm run typecheck`、`npm run lint`、`npm run format:check`、`npm run test -w apps/api` が成功する。

## 6. 実行可能な受け入れ条件

検収担当は次を順に確認する。

1. フィード取得失敗時、`fetch_attempt` に失敗種別・サニタイズ済み理由・正しい試行番号が残り、既存の正常 snapshot と受信履歴が空値で上書きされない。
2. フィードごとの連続失敗が60、120、240、300、300秒の待機を正確に生成し、成功時にリセットされる。
3. 一方のフィードが再試行待ちでも、他方のフィードは通常周期で取得できる。待機中フィードには余計な HTTP 要求も履歴行も生じない。
4. timeout・network・HTTP・フィード構造不正の失敗と、個別電文の構造不正／未対応コードが、通信失敗へ一括変換されず別々に参照できる。
5. 個別電文失敗・未対応形式は、フィード本文の取得成功およびフィードのバックオフ状態と独立である。
6. フィード通信失敗・フィード構造不正には警報（案）、個別電文の通信失敗・構造不正／未対応形式・未対応コードには非通知（案）が対応し、連続失敗等が後続の異常閾値へ達した場合だけ問いかけ（案）へ上位化する入力分類が完全一致で確認できる。C13 単体では通知・通知出力履歴が生成されない。
7. #22 統合後、初期取得が失敗した場合は失敗フィードだけを待機後に再試行し、初期4フィードがすべて成功したときだけ初期取得が完了する。通常サイクルの成功だけで完了にならない。
8. `stop()` 後に通常・再試行取得が予約されず、再開・重複 start により timer や HTTP 要求が多重化しない。
9. 遅延／異常の閾値判定、設定ファイル、監視 REST API、Web UI、XML以外の取得元に変更がない。
10. 全横断検査と API workspace テストが成功する。

## 7. 後続 Issue への引き継ぎ

- **C14**: 通常周期をJST時間帯別へ置換する際、C13 の `nextAllowedFetchAt` と通常次回予定を単一スケジューラで調停する。停止・スケジュール停止を失敗に数えず、夜間再開の復旧契機を確定する。
- **E10/K6/K8**: フィード別の最終試行・最終成功・連続失敗・次回再試行予定と、構造不正／未対応形式を別欄で表示する。C13 は遅延／異常ラベルを生成しない。
- **D7／§8.4**: C13 の失敗分類を、単発フィード通信失敗・フィード構造不正は警報（案）、後続で定める異常閾値到達時は問いかけ（案）、個別電文通信失敗・構造不正／未対応形式・未対応コードは非通知（案）として利用する。§8.1 の遅延・異常閾値、状態変化の重複抑止、通知生成・出力は後続が実装し、気象内容の通知と混同しない。
- **E11**: 手動開始・停止・強制更新は、C13 のバックオフ待機を無視するか、同じ回復キューへ合流させるかを明示的に決める。任意フィード／任意URLを指定する API は設けない。
- **情報種別ごとの後続実装**: parser/processor が未知コード・不正構造を検知した場合、既存正常値を消さず adoption の理由を残す規則を維持する。
