# Issue #193 性能検証記録

## 実行条件

- 実行日時: 2026-09-22T05:13:13Z
- OS: Darwin 25.6.0 x86_64
- Node.js: v24.20.0、SQLite 3.53.4 (`better-sqlite3`)
- CPU: Intel Core i7-9750H 2.60GHz（論理12コア）
- メモリ: 32GiB、プロセス最大RSS 6,536,544KiB
- DB: 生成fixture 50,000件、原文約991 bytes/件、DB 97,906,688 bytes
- 分布: `normal / VPWS50` 50,000件。末尾2,500件を両会場対象外、その前を east / trc 交互とした。
- 設定: `yieldEveryParsedReceptions=25`、`candidatePageSize=100`、計測用yield遅延100ms
- コマンド: `node --import tsx apps/api/scripts/measureWarningRecovery.ts 50000 100`

スクリプトは同一生成DBに対して、まず設計基準コミット `e9d312e` 相当の全履歴昇順解析を実測し、現況を保存する。次に現況表だけを空にして新方式を実測し、ID以外のストリーム・スナップショット・明細が基準結果と一致することを検証する。生成DBは終了時に削除する。新方式自体が20秒未満で終了するため、アルゴリズムとDBを変えず、通常の25件ごとのyieldに計測用100ms遅延を注入して28.5秒継続させた。HTTPは実時間で1秒間隔に取得した。

## 変更前後の比較（AC8・AC9）

| 項目 | 変更前相当 | 新方式 |
| --- | ---: | ---: |
| wall time | 163,441.64 ms | 28,501.58 ms（計測用yield遅延20,600msを含む） |
| XML解析件数 | 100,000件（50,000件×2会場） | 5,007件 |
| east | 50,000件 | 2,504件 / 16,918 ms |
| trc | 50,000件 | 2,503件 / 11,501 ms |
| yield回数 | 0回 | 206回 |
| 復旧結果 | 基準 | ID以外の全保存値が基準と一致 |

新方式は会場に適用できる最新候補へ到達した時点で古いページを取得しない。このfixtureでは意図的に新しい2,500件を対象外にしたため5,007件を解析したが、それでも変更前の100,000件から約95%削減した。通常の保存状態再利用は自動テストで候補探索0回、3 statusの保存値完全不変を別途検証している。

プロセスCPUは user 109,428.77 ms / system 56,329.30 ms。最大RSSは比較基準の全履歴解析を同一プロセスで先に実行した値を含む。全10万回で測った単一XML parse/reduceの最大は376.97msで、Worker検討条件の500msを下回った。

## Worker採否（AC20）

Workerは不採用とする。25件ごとのyield下で、1秒間隔の連続応答最大値が両目標を満たし、単一XML parse/reduce最大376.97msも500ms以下だったため、設計書§8.2の採用条件に該当しない。将来同スクリプトで閾値超過を再現した場合は後続Issueで再検討する。
