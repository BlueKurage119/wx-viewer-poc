# Issue #237 端末定義の YAML 外部化

## 1. 根拠と確定事項

- [Issue #237](https://github.com/BlueKurage119/wx-viewer-poc/issues/237) 本文とオーナーコメント: 端末 ID・表示名・モード・所属会場の正本を YAML に集約し、API 再起動のみで反映する。開発用ローカル設定も設ける。
- ヒアリング結果: 同一会場・同一モードの複数端末は許可し、端末表示名の重複は禁止する。開発時のみ Git 管理外の `config/terminals.local.yaml` を端末 ID 単位で共有設定へ上書き・追加する。削除表現は設けず、不正な差分は起動失敗とする。
- 依存 Issue #236 は `main` に反映済み。会場レジストリと `GET /api/config/venues` が存在する。端末設定は会場設定の検証後に扱う。
- 現行の端末正本は `packages/shared/src/terminalConfig.ts`、表示名は `apps/web/src/shell/config.ts` に分散する。Vite の 404 判定も固定配列を参照する。

## 2. YAML スキーマと検証

正本を `config/terminals.yaml` とし、ルートは `terminals` キーのみ、値は 1 件以上の配列とする。配列順は列挙順とし、各項目は `id`、`name`、`mode`、`venueId` をすべて必須とする。未知キー、`null`、暗黙の型変換は拒否する。

```yaml
terminals:
  - id: hkeagh01
    name: 東地区外務H1
    mode: H
    venueId: east
  - id: kkeagh01
    name: 東地区外務K1
    mode: K
    venueId: east
  - id: htrcph01
    name: TRC公共H1
    mode: H
    venueId: trc
  - id: ktrcph01
    name: TRC公共K1
    mode: K
    venueId: trc
```

- `id`: `^[a-z][a-z0-9-]{0,31}$`（ASCII 小文字始まり、全長 1〜32 文字）。前後空白は許さない。`api`、`assets`、`config`、`favicon.ico`、`index.html`、`robots.txt`、`@` で始まる Vite 内部パス、既存の静的ルートと同名の ID は拒否する。ルート `/` は ID として扱わない。予約済みパスとの衝突はルーティング側でも同じ判定関数を用いる。
- `name`: 文字列で、`trim()` 後に 1〜80 文字。元の値がトリム後と異なる場合は拒否し、黙って表示値を変更しない。全端末で名前の重複を拒否する。
- `mode`: 大文字の `H` または `K` のみ。
- `venueId`: 空でない文字列とし、検証済み会場レジストリの `resolveVenueId` で存在を確認する。
- `id` は全端末で一意。同一 `venueId`・`mode` の組は重複してよい。ID・名前の重複検査はローカル差分の合成後にも行う。

開発用 `config/terminals.local.yaml` は `.gitignore` に登録し、`NODE_ENV=production` では存在しても読み込まない。ファイルが無ければ共有設定だけを使用する。ローカル差分のルートは `terminals` のみで、各項目は `id` と変更する項目だけを記載できる。既存 ID は項目単位で上書きし、新 ID は全必須項目を要求する。差分単体でも未知キー、重複 ID、不正な型を拒否する。削除用キーや `null` による削除は認めない。共有正本の欠落・破損をローカル差分で補えない。合成後に全体を再検証し、名前重複や未登録会場も起動失敗とする。

共有ファイルの不存在・読込不能・YAML 構文エラー・スキーマ違反は API 起動失敗とし、ハードコード値や直前設定へフォールバックしない。エラーには相対設定パスと YAML 上の箇所（例: `terminals[2].venueId`）を含め、絶対パスや設定全文は出さない。

## 3. 起動順序とレジストリ

`apps/api/src/config/terminalConfigLoader.ts` にファイル読込、YAML 解析、差分合成、厳密検証を置く。会場設定と同じ実行時ルート相対 URL 解決方式を用い、ビルド後もリポジトリの YAML を読む。ファイル読込と純粋検証は分け、合成前後の検証を単体試験できるようにする。

テスト用の `startServer()` と実プロセスのエントリは、共通の起動初期化処理をそれぞれの起動経路として使用する。どちらの経路でも、1 回の起動につき会場設定の成功後に端末設定を 1 回だけロードする。端末レジストリの確定は DB 初期化、HTTP 待受、上流取得より前に完了する。設定は起動中に再読込しない。設定ファイルのみの変更は再ビルドせず、API プロセスの再起動で反映する。

`packages/shared/src/terminalConfig.ts` には `TerminalDefinition`（`id`、`name`、`mode`、検証済み `VenueId`）と読み取り専用 `TerminalRegistry` の型・生成関数を置き、実端末データは置かない。内部配列と各項目を凍結する。`resolveTerminal(id: unknown): TerminalDefinition | null` と `listTerminals(): readonly TerminalDefinition[]` を提供する。API は単一の起動時レジストリを明示的に依存先へ渡し、固定 `TERMINAL_DEFINITIONS` への参照を除去する。外部入力の端末 ID を未検証のまま既知 ID として扱わない。

## 4. API と Web への供給

会場設定と同じ API 設定供給境界に `GET /api/config/terminals` を追加する。レスポンスは `{ generation: string, venueGeneration: string, terminals: TerminalConfigDto[] }` とし、DTO は `id`、`name`、`mode`、`venueId` を含む。`generation` は検証済み有効端末設定を安定シリアライズした SHA-256、`venueGeneration` は同じ起動時に確定した会場設定 API の `generation` とする。Web で必要な型と DTO 検証を shared で共用する。レスポンスは起動時レジストリから生成し、リクエストごとに YAML を読まない。設定 API は非キャッシュとする。

Web は初回描画前に会場設定と端末設定を取得・検証し、端末応答の `venueGeneration` と会場応答の `generation` の一致、および各端末の `venueId` が取得した会場に存在することを照合する。世代が一致しない場合は API 再起動をまたいだ取得とみなし、両設定を再取得する。再取得しても一致しなければ設定取得エラーを表示し、混在した定義で描画しない。成功後に端末レジストリを Context で配布し、`createTerminals`、ヘッダー表示、画面モード・ナビゲーション判定はこれを使用する。`apps/web/src/shell/config.ts` の `terminalNames` と共有パッケージの固定端末配列を削除する。取得中は既存の起動画面、通信失敗は再試行可能なエラー画面、不正 DTO や会場不整合は設定エラー画面とし、古い内蔵端末定義で表示しない。

Web が既に開いている間に API が再起動して世代が変わった場合、既存の画面内レジストリは自動変更しない。ページ更新時に再取得し、新しい定義へ切り替える。変更直後の古い画面からの API 呼出しは API 側の現行レジストリで検証するため、削除済み ID は従来の未登録端末エラーになる。再取得時に必要ならページ更新を促すが、無停止切替は対象外とする。

## 5. 未登録 URL と API 境界

端末 URL は `/<id>` と末尾 `/` 付きのみを登録済み端末として扱う。Web クライアントは端末設定取得後に URL を解決し、未登録なら既存の未登録端末画面を表示し、別端末へ代入しない。SPA フォールバック環境でもこの判定を行う。

Vite 開発・プレビューの HTML ナビゲーション 404 は、Vite 自身が YAML を別読込して台帳を持つ形にはしない。API の `GET /api/config/terminals` から検証済み ID 集合を各 HTML ナビゲーション時に取得して判定する。取得成功時に限り、未登録の端末 URL へ 404、登録済み URL は通常配信とする。API 未起動・設定取得失敗時は端末の登録状態を判定できないため、端末 URL の HTML ナビゲーションに 503 を返す。取得失敗を未登録 404 と混同しない。API パス、静的アセット、Vite 内部パスは既存どおりガードの対象外とする。

気象情報、警報・予報、アメダス、防災速報、ナウキャスト・キキクル、通知差分、起動時通知、端末セッション、監視状態・操作、タイル配信プロファイルの端末 ID 入力を棚卸しする。各境界は同じレジストリで解決し、未登録時の HTTP ステータス・エラー DTO を維持する。監視の代表端末選択は登録順の最初を使う等、暗黙の旧 4 件前提を除く。会場の所属はレジストリの `venueId` から解決し、ID 接頭辞による推測は行わない。

## 6. 移行・削除時の扱い

現行 4 端末の ID、表示名、モード、会場を上記 YAML に同値で移す。既存 URL、H/K の画面差、通知・セッションで用いる端末 ID、API の会場解決、未登録拒否は保持する。端末設定から ID を削除した場合、その端末は再起動後の URL と API で未登録扱いとする。既存のセッションや DB 履歴は自動削除せず、現行端末への付け替えも行わない。

README には共有 YAML のスキーマ、変更と API 再起動手順、ローカル差分の例と本番無効、不正設定での起動失敗を記載する。

- [ ] `config/terminals.yaml` に旧 4 件の ID・表示名・モード・会場が同値で移され、固定台帳と表示名台帳がコードから除去される。
- [ ] 実ビルド成果物で会場設定後、DB 初期化・待受・取得前に端末設定を 1 回読む。再ビルドなしの API 再起動で変更が反映され、稼働中のファイル変更だけでは反映されない。
- [ ] 共有設定の欠落・読込不能・構文誤り、ルート違反、0 件、必須キー欠落、未知キー、型誤り、空文字、ID 形式・長さ・予約語違反、ID 重複、名前重複、モード違反、未登録会場のそれぞれで起動が失敗し、エラーが相対パスと項目を示す。
- [ ] 同一会場・同一モードの複数端末が登録できる。異なる会場間も含め表示名重複は拒否される。
- [ ] ローカル差分の既存 ID 上書きと新 ID 追加、未存在時の共有値利用、本番無効、削除表現拒否、不正差分での起動失敗を確認する。
- [ ] `GET /api/config/terminals` の値とレジストリが一致し、Web は描画前に会場・端末の両設定と世代一致を検証する。取得中・通信失敗・不正応答・会場不整合の画面状態を確認する。API 再起動を挟んで世代が異なる応答を受けたときは両方再取得し、混在した定義を表示しない。
- [ ] 合成端末を設定へ追加し、再起動後の URL、ヘッダー名、H/K 画面差、所属会場、API 応答が新設定どおりになる。名称・モード・所属会場の変更も再ビルドなしで反映する。
- [ ] 未登録端末 ID を全対象 API へ渡した際に既存のステータスとエラー形式を保つ。未登録 URL は SPA・Vite 開発・プレビューで既存端末画面を表示せず、設定取得に成功した Vite は 404 を返す。API が利用できないとき Vite は 503 を返す。
- [ ] API 再起動で端末が追加・削除された後の Vite 404 判定が最新設定に従う。開いたままの Web は更新時に再取得し、古い ID の API 呼出しは未登録として拒否される。
- [ ] 端末削除後も既存 DB 履歴を自動削除せず、削除済み端末 ID を別端末へ付け替えない。
- [ ] 既存 4 端末の API 応答・画面・ナビゲーションと未登録拒否の回帰試験が通る。
- [ ] README にスキーマ、変更・再起動、ローカル差分、不正設定時の動作が記載される。
- [ ] `npm run lint`、`npm run typecheck`、`npm run format:check`、`npm run test --workspaces --if-present`、`npm run build` が成功する。

## 8. 対象外

管理画面、DB への設定保存、ファイル監視、無停止再読込、稼働中のモード・会場切替、正常設定への自動フォールバック、端末認証、秘密鍵配布、オンライン管理、セッション仕様変更、通知確認状態の端末間共有、端末削除時の履歴自動削除、設定監査履歴、Git 外の設定配布基盤は対象外とする。
