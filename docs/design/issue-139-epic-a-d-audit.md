# Issue #139「D9. 基本設計・Issueドラフト・実装の棚卸しと未決事項の整理」設計

作成日: 2026-09-13

## 1. 目的と承認済みの前提

Epic A〜D 完了時点の実装・設計・レビュー記録を照合し、後続 Epic E〜L が使う仕様と申し送りを整理する。成果は棚卸しレポート、基本設計の改定、Issue ドラフトの再編と起票内容であり、製品コードは変更しない。

統括から受領したユーザーの確定判断は以下のとおり。

- A〜D の実装と基本設計・Issue ドラフトの差分、全設計書と対応 PR の本文・コメント・レビューからの申し送り、未決事項、残留リスクを集約する。
- 根拠がある確定仕様を基本設計へ反映し、E〜L の再編・起票案を作成する。
- 未決事項はまず一覧化し、その一覧を見て、今回決めるものと後続へ送るものをユーザーと相談する。未決の仕様を製造担当が補完しない。
- 特に「未決事項と未対応の申し送りなど」は、PR 本文へ表として転載できる形にする。
- 既存の識別番号は不変。途中への追加は枝番、末尾への追加は続番、削除は欠番とする。

本書は棚卸しの実施方法を定める設計であり、全件抽出結果ではない。本書を提示したターンを終了し、ユーザーの設計承認後に製造へ進む。

## 4. 母集団の確定と取得

### 4.1 調査基準

製造開始時に調査日時、対象リポジトリ、基準 main SHA をレポートへ記録する。ローカルの実装調査はその SHA を基準にする。今回の D9 設計書は「調査手順自身」として対象外行を付け、それ以外の `docs/design/issue-*.md` をすべて母集団に登録する。同一 Issue に複数設計書がある場合もファイル単位で別行にする。

`git ls-tree -r --name-only <基準SHA> docs/design` の結果を正とし、`rg --files docs/design` と突き合わせる。基準後に追加された設計書は差分として明記する。調査期間中の main 更新を黙って混在させない。

### 4.2 Issue・PR の関連付け

全状態の Issue と PR をページネーションして取得する。REST の `repos/BlueKurage119/wx-viewer-poc/issues?state=all&per_page=100` は PR も含むため `pull_request` の有無を区別し、PR 一覧も `pulls?state=all&per_page=100` から取得する。

次の関連を併用して、設計書・Issue・PR の多対多対応を作る。

1. 設計書名の Issue 番号、本文中の Issue/PR 参照。
2. PR 本文の `Closes` / `Fixes` / `Refs` 等と GitHub の関連 Issue 情報。
3. PR の変更ファイル。設計書が含まれる PR、A〜D 実装に対する後続修正 PR を補完する。
4. 関連 PR から参照される追補 PR・Issue。未マージのものは解消根拠にせず進行中と記録する。

タイトル一致・マイルストーン・最大件数付きの検索だけで母集団を決めない。関係が判定できない PR は黙って除外せず、保留理由を記録する。A〜D の実装を変更した PR は設計書がなくても対象にする。対象外 PR は番号と対象外理由をまとめ、全 PR の集合との照合を可能にする。

### 4.3 取得する記録

各対象 PR は本文だけでなく次を取得する。`gh pr view` を使う場合も同じ範囲を満たすこと。

- `pulls/<番号>`: 本文、状態、base/head、マージ日時・SHA。
- `issues/<番号>/comments`: 会話コメント全件。
- `pulls/<番号>/reviews`: レビュー本文全件。
- `pulls/<番号>/comments`: inline review comments と返信全件。
- `pulls/<番号>/files`: 変更ファイル全件。
- 関連 Issue の本文・コメント。後続で判断が変更された場合の根拠に用いる。

各配列は `gh api --paginate` 等で末尾まで取得する。API の取得上限・切り詰めがある場合は、ローカルの merge diff 等で補完し方法を明記する。取得日時、件数、取得成否を台帳へ残す。正常応答の空配列だけを「0件」とし、接続失敗・権限不足・削除等は「取得不能」とする。未取得が残る状態で網羅性 AC を合格にしない。

母集団台帳の列は `資料ID / 種別 / パスまたはURL / 関連Issue・PR / 基準SHAまたは更新日時 / 本文確認 / 会話件数 / レビュー件数 / inline件数 / 抽出ID / 取得状態・対象外理由`。設計書では不適用列に「対象外」を記入する。抽出がない資料も「該当なし」を記録し、読了と未読を区別する。

## 5. 抽出・分類・根拠追跡

キーワード検索は入口として用いるが、対象資料の本文全体を読み、見出しがない申し送りも抽出する。テスト・実装も関連モジュールを追い、A（共通型・シェル・テーマ）、B（DB・履歴）、C（取得・復旧・スケジュール）、D（通知・端末・監視）の単位で現状を確認する。E〜L は既存コードとの責務重複を確認する。

### 5.1 差分台帳

列は `差分ID（AD-D001〜） / 論点 / 旧記述の箇所・内容 / 現行実装・確定判断 / 根拠 / 文書への処置 / 関連引き継ぎID` とする。根拠にはコードのパスとシンボル、設計書の節、PR またはコメントの URL を付ける。行番号だけに依存しない。

最低限、会場・予報点・会場別採用履歴、通知レジストリ、通知生成と起動応答の違い、`origin` と `detectionContext`、`isTraining`、`fetch_attempt` と健全性判定、`availability`、セマンティックカラー、実装済み API、E〜L の重複・不足、ドラフト集計を確認する。この列挙を対象の上限にしない。

### 5.2 引き継ぎ台帳

列は `管理ID（AD-H001〜） / 論点 / 種別 / 原記録と要旨 / 現在の状態 / 解消・判定根拠 / 影響・到達条件 / 対応案 / 引き継ぎ先 / 判断記録`。

- 種別: 未決仕様、未対応申し送り、未確認・実機待ち、残留リスク、実装差分。複数指定可。
- 現在の状態: 未決、未対応、確認待ち、対応中、解消済み、対象外。先送りが承認されても未対応であることは維持し、対応方針に「後続へ」を付ける。
- 影響・到達条件: 通常運用、将来の誤用、到達不能、未確認。レビューの優先度をそのまま採用せず統括がトリアージする。
- 引き継ぎ先: 既存識別番号と GitHub 番号、追加案の識別番号、または「要相談」。空欄にしない。
- 判断記録: ユーザー承認の出典と内容。未承認は「案・未承認」と明記する。

同一論点を統合するときはすべての出典を保持する。原記録の項目単位から管理 ID へ追跡できるよう、原記録の節またはコメント URL と項目要旨を残す。一つの原記録に複数論点があれば分割する。解消済みでも削除しない。後続 PR のマージと実装・検証結果を照合できた範囲だけ解消済みにし、「PR が閉じた」「レビューが resolved」だけで解消しない。

統括の追加調査では、PR #142 の本文が旧来の 2 件構成のままでも、inline の指摘・返信とコミット `2dc9d41` で 3 件目が追加され、現行設計も更新されている。PR 本文だけで現状を判定せず、返信・後続コミット・現物を照合する。また、#31 から D8 宛の表示除外の申し送りは #32 では K9 に送られているため、引き継ぎ先の古さも追跡する。旧宛先と新宛先、移管根拠を記録し、移管を実装完了と混同しない。

### 5.3 PR 転載表

レポートに「PR 本文転載用: 未決事項・未対応の申し送り等」の節を設け、次の列で Markdown 表を完成させる。

| 管理ID | 種別・状態 | 論点と影響 | 今回の扱い・次の対応 | 引き継ぎ先 | 根拠 |
| --- | --- | --- | --- | --- | --- |

引き継ぎ台帳から「解消済み」「対象外」以外を全件転記する。確認待ち・受容した残留リスクも除外しない。解消済み・対象外の件数と詳細へのリンクを表の直後に付ける。件数が多くても「主なもの」へ絞らず、種別ごとに分割して同じ列を使う。

台帳と転載表の管理 ID 集合が一致することを検証する。PR はこの表を省略せず本文に載せる。GitHub の本文制限に収まらない場合は文言を短くし、詳細をレポートへリンクする。それでも収まらなければ投稿前に統括へ返し、承認なく外部コメントへ分散しない。PR 上でリポジトリ相対リンクが壊れないよう、レポート内参照は PR の head を指す GitHub URL に変換する。

## 6. 文書反映と E〜L 再編

実装済みという事実と、ユーザーが承認した仕様を区別する。基本設計の【確定】への変更は承認された設計・判断と実装を照合した記述だけに限定する。未承認の実装差分は差分台帳へ残し、確定に昇格させない。気象庁提供仕様の変更は実データ・公式資料・取得方法レポートとの照合を必要とし、未採取は未採取のまま記す。

節内に未確定記述が残るときは節全体を【確定】にしない。旧記述を訂正する際は差分 ID と対応する根拠を文書反映対応表に残す。各対応は `差分/管理ID / 反映先の節 / 変更要旨 / 確度 / 根拠` で追跡する。

E〜L は既存全タスクについて `識別番号 / GitHub番号 / 現状 / 維持・変更・分割・欠番 / 新スコープ / 依存 / 引き継ぎID` を作る。実装済み部分を切り分け、後続 API と画面の責務、会場解決、通知定義、監視状態を明示する。未決があるタスクは着手前の質問と阻害範囲を記載する。新機能の具体仕様を棚卸し担当が決定しない。

起票計画には、操作（新規・本文改定等）、対象番号・タイトル、背景、やること・やらないこと、受け入れ条件、依存、根拠 ID、承認状態を含める。外部投稿にそのまま使える本文をレポートに保持する。識別番号は既存タイトルの先頭から抽出して前後比較し、番号の再利用・改番を禁止する。集計は本文中の現存タスクから数え直し、欠番と追加を別記する。

## 7. 製造・外部更新の手順

1. 設計承認後、統括が `feature/issue-139-epic-a-d-audit` と設計コミットを準備する。設計担当は作成しない。
2. 製造担当が母集団取得、全件抽出、実装照合、台帳作成を行う。
3. 未決・未対応一覧と今回の処置案を統括へ提示する。ユーザーが指定した相談の段階であり、仕様判断が必要な行の確定・その判断に依存する改定は回答まで保留する。独立した調査・文書整備は進められる。
4. 承認済みの処置を反映し、3 文書、転載表、投稿用 Issue 本文を完成させる。検証し、コミットする。push は担当への指示に従い、製造担当は PR を作成しない。
5. 検収担当が本書の AC を実行する。未達は原因・再現手順を統括へ返し、コード・文書を自分で修正しない。
6. 新規・改定 Issue は、完成した本文と変更一覧を統括が確認し、ユーザー承認済みの操作だけ実施する。既存セッションで得た承認を尊重し、承認済みの具体的操作に一律の再承認を求めない。未承認の新規スコープ・クローズ・ラベル変更は実施しない。明示承認がない間は「起票案完成・投稿待ち」とし、Issue #139 全体を完了扱いにしない。
7. 投稿直前に対象 Issue を再取得して競合変更を確認し、二重起票を避ける。投稿後に本文・識別番号・URL を読み戻し、レポートの起票実績へ記録する。途中失敗は成功済みと未実施を分け、成功済み操作を繰り返さない。
8. PR 作成前の AC1〜AC12 が通過したら検収担当が push し、base `main` の通常 PR を作成する。概要・変更内容・検証・転載表・`Closes #139`・アプリケーションとモデル名を記載する。作成後に AC13 を実行して事後確認する。マージはしない。

GitHub 投稿には構造化引数または `gh --body-file` を使い、本文をシェルへ直接展開しない。一時取得データ・本文ファイルは作業後に削除する。

## 8. 受け入れ条件と検証

新しい製品テストは追加しない。文書変更のためミューテーション対象の実装追加はない。棚卸しのために製品の全 AC を再演する必要はないが、文書で新たに実挙動を断定する場合は対応するテスト・実行結果を確認し、未実行のものは既存記録に基づく旨を明記する。

| AC | 実行手順 | 合格条件 |
| --- | --- | --- |
| AC1 母集団 | 基準 SHA の設計書一覧と母集団台帳をパス集合で照合。全 PR 一覧と対象・対象外台帳も照合する | 未登録・重複がなく、同一 Issue の複数設計書が別行。対象外理由がある |
| AC2 取得完了 | 全対象 PR の本文・会話・レビュー・inline の取得件数と台帳を照合し、ページ末尾まで取得した記録を確認する | 取得不能・未読が 0。空件と取得失敗を区別している |
| AC3 抽出の追跡 | 全対象資料を再読し、各申し送り・未決・残留リスクの原項目から管理 ID を追う | 未登録項目がなく、該当なし資料も確認記録がある。統合行でも全出典を辿れる |
| AC4 解消判定 | 解消済み全行の後続設計・PR・現行実装・検証根拠を開く | 単なる終了・resolved を根拠にせず、残る範囲は未対応等として分離されている |
| AC5 実装差分 | A〜D 各領域のコード・設計と基本設計・ドラフトを節単位で比較し、§5.1 の最低確認項目も照合する | 各領域に確認箇所と結論があり、乖離が差分台帳へ記載されている |
| AC6 確度と改定 | 基本文書の diff と文書反映対応表を全行照合する | 全仕様変更に根拠。未承認事項の確定化なし。気象提供仕様の根拠と実電文未確認の限界が保持される |
