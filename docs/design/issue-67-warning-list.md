## 2. 保持範囲

### 確定した範囲

メモリ内の今回起動の通知のみを扱う。localStorage・IndexedDB・履歴APIによる過去通知復元は追加しない。起動応答の `startup:<outputId>` と検知差分の `delta:<notificationId>` は対応付けず別行とする。同じfeedKeyの再受信は同じ行を更新し、重複行にしない。

### 保持時間・件数の具体化

受信時刻基準、起動現況の期間対象外、合計500件は追加ヒアリングで確定した。500件の残し方も発生日時順の案が承認済みである。

| 判断点 | 提案 | 対案と影響 |
| --- | --- | --- |
| 24時間の基準 | 【確定】差分の初回受信時刻を基準に保持する。発生日時は表示・並べ替えに使う | 発生日時基準は採用しない |
| 起動現況の期間制限 | 【確定】起動現況は24時間の期間対象外。500件上限には含める | 起動現況の別枠保持は採用しない |
| 500件の残し方 | 【確定】表示順の先頭500件を残す。起動現況のための優先枠は設けない | 受信順や起動優先: 発生日時の新しい順と保持の優先が異なる |

差分の受信時刻が `now - 24時間` と等しい行は保持し、それより古い行は除外する。再受信は初回受信時刻を延長しない。時刻経過だけでも期限処理を行う。既存 `TerminalApp` の1秒時計を利用し、専用のポーリングは増やさない。

### ヘッダーへの影響防止

既存 `NotificationUiState.items` に一覧の500件・24時間制限を直接適用しない。これを削ると未確認通知、件数、次の鳴動候補が消えるためである。一覧専用履歴を受信遷移時に生成し、その履歴だけを制限する。確認操作で一覧の行を消さない。一覧表示・画面切替・期限処理は確認状態、未読状態、選択中問いかけ、cursor、鳴動要求を変更しない。共通storeの上限なしという既存課題の改修は本Issueに含めない。


### ブザー停止と通知確認の分離（ユーザー訂正）

ブザー停止は音声とヘッダーの鳴動表示だけを停止する。`confirmedFeedKeys`・`unreadFeedKeys`・選択中問いかけ・一覧履歴・下部通知行・未読/未対応件数・cursorを変更せず、次の未確認通知への鳴動要求も発行しない。通知確認は下部の既存明示操作（警報の「確認」、問いかけの確認選択と「送信」）による別の遷移である。

ソース読解では `App.tsx` の `stopBuzzer` は既に `buzzer.stop()` だけを呼び、`confirmNotification` とは別である。`AppShell.tsx` のヘッダークリックも停止経路へ接続済み。一方、F8のキー処理は `apps/web/src` に存在せず、これまでの「既存F8」という記述は訂正する。今回、F8を同じ停止経路へ接続する。キー処理は `AppShell` に配置し、停止可能時に既定動作を抑止して停止する。リスナーはunmount時に解除する。停止ハンドラーに確認処理が混在する経路を製造時に見つけた場合も、今回のユーザー訂正の範囲として分離する。下部の明示的な確認操作の仕様は変更しない。

## 4. 表示

ネイティブの `table`・`thead`・`tbody` を使い、列見出しをstickyにする。表を持つ領域が縦横にスクロールできる。画面全体に大きなカードを並べず、多数の行を同時に読める密度にする。狭い幅では表の横スクロールを許容し、内容を隠さない。具体的な行高は製造時の実画面で確認し、未計測の固定値を受け入れ条件にしない。

| 列 | 値 |
| --- | --- |
| 発生日時 | `occurredAt` を日本時間で年月日・時分秒まで表示。受信時刻・検知時刻に置換しない |
| 通知区分 | warning=警報、question=問いかけ、emergency=非常 |
| 対象サービス | 全行「防災気象情報」。`targets` の名称はこの列には表示しないが、元データを変更・削除しない |
| 情報種別 | warning_current=気象警報・注意報、bosai_bulletin=防災気象情報、fetch_health=取得状態、fetch_control=取得操作、database_recovery=データベース復旧。未知値は元のsourceTypeを表示し、捨てない |
| 内容 | `summary` の改行（CRLF・CR・LF・行区切り・段落区切り）を全角スペースへ置換して1行表示。元データを変更せず、文字列を解析して別項目を捏造しない |

起動時は `source === 'startup'` の行に「起動時」、訓練は `isTraining` の行に「訓練」を文字で併記する。`origin` と `source` と `detectionContext` を同義に扱わない。startupのnullなdetectionContext/changeType/detectedAtを補完しない。

内容は折り返さず、省略せずに1行表示し、横スクロールで全文を読める。summaryが同じでもIDが異なれば別行を維持する。固定の区分1件表示やヘッダーの最大表示数を一覧に流用しない。警報区分だけに絞らず、端末で表示可能な3区分を対象にする。

空の場合は「通知はありません」。開始中は「通知を読み込んでいます」。再試行中は既存一覧を保持し、既存ヘッダーの通信案内を利用する。画面を開く操作で通知を既読・確認済みにしない。MD3色トークンと既存ラッパーを使用し、画像の青/赤等をHEXで再現しない。操作ボタン・確認状態列は追加しない。

## 5. サーバー履歴の実態と本番PoCへの引き継ぎ

サーバーには `notification_output_history` と記録・検索関数が存在する。`GET /api/monitoring/notification-outputs` も存在し、監視履歴として取得できる。したがって、警報履歴を全く管理していない状態ではない。ただし記録の意味はサーバーの検知・出力スナップショットであり、各端末が受信・表示・鳴動・確認した証明ではない。

起動問い合わせは `startup_notification_inquiry` にterminalId/sessionIdと応答JSONを保存する。これも端末の確認履歴ではない。確認状態はフロントの `confirmedFeedKeys` のメモリ内状態で、確認用のサーバー保存APIを今回追加しない。

将来の全端末モードで、サーバー検知履歴を一覧化するなら既存履歴を活用できる。各端末の受領・確認時刻・端末名称を含む画面を作るなら、通知IDと起動outputIdの関係、端末/セッション単位の受領・確認記録、アクセス権、対象会場、保持期間と検索ページングを別途設計する必要がある。今回のコンポーネントは渡された行を表示するが、これを本番の全端末履歴APIが完成済みである根拠にしない。

[差分API設計](issue-41-notification-delta-api.md) §10の「一覧・検索は履歴APIを使う」という後続申し送りと、今回合意した端末内の直近一覧は用途が異なる。#67では今回の合意を優先し、監視履歴APIを追加利用しない。サーバー履歴閲覧は別の画面・後続設計である。
