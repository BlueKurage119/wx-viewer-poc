# Issue #64「H2. 下部通知領域の表示・確認操作」設計

対象Issue: [H2 #64](https://github.com/BlueKurage119/wx-viewer-poc/issues/64)
前提Issue: A2 #2、D1 #25、D8 #31、E9 #41（いずれも実装済み）

---

## 1. 目的と範囲

E9 #41 が提供する起動時現況と通常差分を、web の共通通知 store へ合流させる。固定シェル最下部の通知領域では、警報と問いかけ／非常を別の行に表示し、通知ごとの確認操作、未読・未対応件数、通信状態を表示する。通知到着時は表示中の通知を割り込み表示に切り替える。

### 1.1 対象

1. `POST /api/notifications/startup` の ready 応答と `GET /api/notifications/delta` を受信し、共有型 `NotificationFeedItem` に変換して同一 store へ投入する。
2. 起動完了後、15 秒間隔で差分を取得する。起動時の `202 initializing`、通信失敗、HTTP／応答形式エラーは操作ガイド行に表示し、指数バックオフで再試行する。既存の通知は消去しない。
3. 通知を `warning` 行と `question`／`emergency` 行に分け、各行では新しい順に表示する。非常は問いかけ行に表示するが、チャイム選択の優先度は `emergency > question > warning` とする。
4. 通知ごとの「確認」操作、未読・未対応件数、および新着割り込み時の問いかけ選択状態の解除を実装する。通知がない場合、各通知行にはネイティブの`disabled`属性を持つ文字のない常時操作ボタン2枠だけを表示する。warning行では常時操作ボタンを「詳細」または「関連」と「確認」とする。question／emergency行の表示中だけ、選択肢群と常時操作ボタン「詳細」または「関連」「送信」を表示する。選択肢群と常時操作ボタンの間は全角1文字相当の間隔を空ける。選択肢がない問いかけでは「確認」を選択肢ボタンとして表示し、確認後に送信する。詳細と関連は排他的である。現行契約ではすべて非活性で、Tabフォーカス対象外とする。
5. 将来追加される問いかけ選択肢・詳細操作を安全に接続するため、通知UI側の差し込み境界を定める。
6. H端末では `origin === 'system'` を表示・鳴動・件数から除外する。ただし store への投入、cursor 更新、次回差分取得は継続する。
7. ユーザーが提供する編曲済みチャイムを組み込み可能な資産受入・ライセンス表記の置場を用意する。音源ファイル自体は本Issueでは追加しない。

### 1.2 対象外

- ヘッダー点滅、実際のチャイム再生／停止、非常ブザーのスヌーズ・再通知は H1 #63／H3 #65 の責務とする。H2 は「新着のうち最高区分」をチャイム要求として公開するだけとする。
- 確認済み状態のreload後の扱い、端末内永続化は H4 #66 で定める。本IssueではReactのメモリ内にだけ保持する。
- サーバーへの確認送信、受領監視、担当者・端末をまたぐ確認共有は実装しない。
- 問いかけの選択肢、送信先API、詳細データ、関連遷移先は現行の `NotificationFeedItem`／API契約に存在しないため、実際の選択・送信・詳細表示・遷移は実装しない。H2では、通知到着時の選択肢ボタンおよび操作ボタンのラベルと並びを、非活性の表示境界として扱う。
- 通報の承認・否認など、設備状態を変更する操作API、その認可・監査・冪等性・結果照会は本Issueの対象外とする。本番要件にある承認／否認ワークフローを、気象通知UIのために新設・代替してはならない。
- 通知の詳細内容を表示するダイアログ、または関連ページへ遷移する実処理は、現行通知データに必要な参照情報がないため実装しない。
- ブラウザ⇔APIの疎通異常を通知事実（`origin: system`）として生成・保存しない。操作ガイド行の通信状態表示だけを行う。

## 2. 前提となる実装契約

- E9 #41 はmainに実装済みである。起動時は `StartupNotificationReadyResponse.cursor`、通常取得は `NotificationDeltaReadyResponse.cursor` を返す。`cursor_out_of_range` は409で最新cursorを返す。
- `toNotificationFeedItemFromStartup` と `toNotificationFeedItemFromDelta` は、`feedKey` をそれぞれ `startup:<outputId>`、`delta:<notificationId>` に名前空間分離する。storeはこのキーで重複を排除する。
- 通常差分は件数上限なしで返される。クライアント側の「表示保持上限」はサーバー履歴の削除やcursor進行に影響してはならない。
- 起動・差分の表示文言は、いずれも `summary` を1本の文字列のまま使う。`display.title` 等への再分解・再構成は行わない。
- `ackRequired` はサーバーが通知に要求する性質であり、フロントの確認済み状態ではない。この両者を同一フラグにしない。

### 2.1 将来の問いかけ・詳細操作の接続境界

サーバーAPIからJavaScriptのコールバック関数を受け取って実行してはならない。将来、通知に選択肢を持たせる場合は、shared/API契約で、対象通知、選択肢ID・表示名、許可済み操作を表す操作ディスクリプタ、要求IDを構造化して渡す。web側は操作ディスクリプタの許可リストにある操作だけを対応するAPIクライアントへ渡し、任意URL・任意関数・任意HTTP要求を実行しない。

- 現行契約では選択肢・詳細・関連・送信先が未接続である。通知なしでは各通知行にネイティブの`disabled`属性を持つ文字のない常時操作ボタン2枠だけを表示する。warning行では「詳細」または「関連」と「確認」を表示する。question／emergency行の表示中だけ、選択肢群と「詳細」または「関連」「送信」を表示する。選択肢群と常時操作ボタンの間には全角1文字相当の間隔を設ける。選択肢がない場合も「確認」を選択肢ボタンとして表示する。詳細と関連は排他的である。現行契約には詳細／関連データも選択肢データもないため、実装時のラベル・表示分岐は将来接続境界にとどめる。これらはTabフォーカス対象外とし、ボタン以外のキャプションや説明は表示しない。
- 選択肢なしの将来UIでは、「確認」は何もしない選択肢である。ユーザーは「確認」を選択してから「送信」し、送信時に外部APIは呼ばず、端末内で回答済み・アーカイブ扱いにする。
- 選択肢ありの将来UIでは、ユーザーが選択肢を選んでから「送信」を有効化する。送信時は選択肢に対応する許可済み操作APIを実行し、成功した場合にだけ端末内で回答済み・アーカイブ扱いにする。失敗時は選択と通知を保持し、成功扱いにしない。
- `detail` があれば「詳細」で詳細ダイアログを開き、`related` があれば「関連」で許可済みの関連ページへ遷移する。詳細と関連は排他的である。
- 選択肢送信APIや操作ディスクリプタを導入する変更は、認可・監査・冪等性・失敗時の再送と結果照会を含む後続の別Issueで扱う。H2では型・API・コールバックの追加を行わない。

## 3. 通知storeと取得状態

### 3.1 状態モデル

`apps/web/src/notifications/` に、APIクライアント、ポーリング制御、React hook／storeの純粋な状態遷移を置く。シェルの表示コンポーネントは取得APIを直接呼ばない。

```ts
interface NotificationUiState {
  readonly items: readonly NotificationFeedItem[];
  readonly cursor: NotificationDeltaCursor | null;
  readonly phase: 'starting' | 'ready' | 'retrying';
  readonly operationMessage: string;
  readonly confirmedFeedKeys: ReadonlySet<string>;
  readonly selectedQuestionFeedKey: string | null;
  readonly selectedQuestionChoice: string | null;
}
```

- `items` は `feedKey` で一意とし、受信順ではなく `occurredAt` の降順（同時刻は sequence 降順、最後に `feedKey` 降順）で安定整列する。
- H2では原則として全件をメモリに保持する。ブラウザ資源を守る必要が生じたときだけ、表示対象／非表示対象をそれぞれ最大50件に丸める。その場合も古い順に捨て、cursorは保持し、操作ガイドへ「通知表示は最新50件です」と明示する。初期実装では上限を設けない。
- `confirmedFeedKeys` は通知1件単位で更新する。`ackRequired` がfalseの通知も「内容を確認した」というUI操作は可能だが、未対応件数は `ackRequired && !confirmed` の件数とする。未読は新規投入時に未読、対象行を現在表示した時点で既読とする。既読集合の永続化もH4まで行わない。
- `selectedQuestionFeedKey` と `selectedQuestionChoice` は回答UIの一時状態である。新着が問いかけ行へ割り込む場合、または表示中の問いかけが回答済みになった場合は両方を必ず `null` にする。現行契約に選択肢がないため、H2では選択・送信の状態遷移を行わず、問いかけ到着時の選択肢ボタンの表示境界だけを置く。将来は送信成功時だけ回答済みアーカイブへ遷移し、失敗時に確認済みへ遷移させない。

### 3.2 起動・ポーリング・再試行

1. 端末URLを解決後、既存の端末session IDを使いstartupを要求する。
2. readyなら通知を投入し、応答cursorを保存して直ちに最初のdeltaを1回取得する。その後は成功完了から15秒後に次のdeltaを要求する。同一端末で同時に複数要求を出さない。
3. startupの202、network／serverエラー、deltaのnetwork／serverエラーでは、操作ガイド行の通知受信状態として「通知を受信できません。再試行します。」を表示する。監視APIの障害表示とは状態・文言を分離し、同時に発生した場合も通知受信の再試行中であることを隠さない。失敗回数に応じて 1、2、4、8、16、30 秒（上限30秒）で再試行し、成功時に15秒周期へ戻す。
4. deltaの409 `cursor_out_of_range` は、応答cursorを採用し、操作ガイド行に「通知の受信位置を同期しました。」を一度表示して次周期へ進む。過去履歴を再取得しない。
5. stale responseやアンマウント後の応答は反映しない。端末ID変更時は前端末のタイマー・AbortControllerを解除し、新端末の空storeから開始する。
6. 通信失敗は、既存の監視画面のAPI失敗状態とは混同しない。H2は通知通信の状態だけを操作ガイド行に出し、ヘッダーの受信異常表示の統合は別Issueで扱う。

## 4. 表示と操作

### 4.1 行の割当と割り込み

通知領域は既存どおり、ラベルを増やさない3行（警報／問いかけ・非常／操作ガイド）とする。

| 行 | 対象 | 表示順 | 表示中の新着 |
| --- | --- | --- | --- |
| 警報 | `category === 'warning'` | 新しい順 | 同行の先頭へ即時切替 |
| 問いかけ・非常 | `category === 'question' \| 'emergency'` | 新しい順 | 同行の先頭へ即時切替。切替前の選択肢状態を解除 |
| 操作ガイド | 監視API状態、通知受信状態、画面操作結果 | 状態種別ごとに最新メッセージ | 通知とは独立して更新。監視API障害と通知受信の再試行中は区別して併記し、後者を隠さない |

- 通知行は各行の先頭1件だけを常時表示する。後続はstoreに保持し、先頭通知を確認すると次の未確認通知を新しい順で表示する。既確認通知も保持し、全件確認後は最新通知を表示する。
- 新規の同区分通知も割り込み対象である。非常は問いかけ行内で新しい順を崩さない。非常を常に問いかけより先にする規則は設けない。
- 新着の通知を投入した時点で、対象行の表示通知を既読にする。確認後に次の未確認通知を表示する場合も、その表示時点で既読にする。操作フォーカスを勝手に移さず、スクリーンリーダーには行の内容変更を`aria-live="polite"`で知らせる。非常の緊急通知だけはH1のヘッダー表現で補う。
- 現行契約では、通知なしの各通知行は文字のない常時操作ボタン2枠だけを表示する。warning行は「詳細」または「関連」と「確認」を表示する。question／emergency行の表示中だけ、選択肢ボタンと「詳細」または「関連」「送信」を表示し、選択肢群と常時操作ボタンの間を全角1文字相当空ける。選択肢がない場合も「確認」を選択肢ボタンとして表示し、ユーザーは「確認」を選択してから「送信」する。詳細と関連は排他的である。現行契約に選択肢・詳細・関連・送信先がないH2では、これらはネイティブの`disabled`属性を持ち、Tabフォーカス対象外であり、状態遷移を起こさない。後続契約で有効化された操作は対象の`feedKey`を明示して状態遷移し、別通知を確認済みにしない。送信成功後は現在行を再選択し、選択肢状態も解除する。
- 未読・未対応件数はH/K表示フィルタ後の通知から別々に数える。件数を合算して単一の総件数として扱わない。

### 4.2 H/Kフィルタリング

`visibleNotices` を `NotificationFeedItem` ベースの表示selectorへ置換する。H端末は `origin === 'system'` の通知を表示、未読・未対応件数、チャイム候補から除外する。除外前の全通知はstoreに残し、delta応答のcursorを必ず採用する。`detectionContext`、`venueScope`、`isTraining`をHフィルタの条件にしてはならない。

### 4.3 チャイムへの受け渡し

storeは新規投入された表示対象通知の最高区分を、`emergency > question > warning` の優先度でH1へ通知する。同一取得応答に複数件あれば1回だけ最高区分を通知する。既存通知の再描画、確認、通信再試行、Hフィルタで除外したsystem通知では鳴動要求を出さない。

ブラウザの自動再生制限により、ユーザー操作前の再生は拒否され得る。H1は拒否を未処理例外にせず、次の明示的なユーザー操作で音声利用を有効化できるようにする。H2は音声再生の成否を通知確認やcursorに影響させない。

## 5. 編曲済みチャイム資産の受入条件

H2の製造時点では音源をコミットしない。ユーザーから次の情報とファイルを受領した後、H1または音源追加専用の変更で追加する。

1. 配布可能な音声ファイル（推奨: 短い `wav` と圧縮版 `ogg` または `mp3`）と、利用を許可するリポジトリ内配置先。
2. 元のOSSの正式名称、著作権者、取得元URL、適用MITライセンス全文、編曲済みである旨、編曲者表記の可否。
3. 音源ごとの用途（warning／question／emergencyで同一か別か）、音量・ループの可否。

追加時は、音源を `apps/web/public/audio/` に置き、同じディレクトリまたは `docs/licenses/` にMITライセンス全文と必要な著作権・改変表記を置く。アプリ内に冗長な説明を常設せず、配布物で追跡できるライセンス文書を正とする。出所・ライセンスが確認できない音源は組み込まない。

## 7. 受入条件

1. startup readyとdeltaを同じstoreへ投入し、`startup:`と`delta:`の同名IDが衝突せず、重複応答でも同一`feedKey`が二重表示されない。
2. 起動通知・通常差分ともにsummaryを1本のまま表示し、警報行と問いかけ／非常行で新しい順に保持・表示する。初期実装は表示保持を削らない。
3. 新着が各行の先頭へ即時割り込み、問いかけ行の新着では選択中の問いかけと選択値が解除される。新着および確認後に次に表示される未確認通知は、表示時点で既読になる。将来接続される通知ごとの確認が別通知へ波及しない。
4. 同時に複数の新着が来た場合、チャイム要求は`emergency > question > warning`で1回だけ出る。H端末で除外したsystem通知は鳴動・表示・件数に含まれず、cursorは進む。
5. `ackRequired` とフロントの確認済みは別状態である。現行のネイティブ`disabled`ボタンはTabフォーカス対象外であり、サーバーへ送信・状態遷移を行わない。後続契約で有効化する端末内確認済み状態はreload後に残らない。
6. startupの202、通知APIの通信失敗、異常応答で既存通知を消さず、操作ガイド行に通知受信状態として表示して1/2/4/8/16/30秒で再試行する。監視APIの障害とは区別し、両方が発生しても通知受信の再試行状態を隠さない。成功後は15秒周期へ復帰する。
7. delta 409では返却cursorを採用して次周期へ復帰し、無限再試行や通知の全消去を起こさない。
8. 実装は既存のMD3セマンティックトークンを用い、色のHEX直書きをしない。キーボードで通知本文・操作ガイドなどの有効要素に到達でき、通知本文の更新が支援技術へ伝わる。ネイティブの`disabled`属性を持つボタンはTabフォーカス対象外とする。
9. 通知がない場合は各通知行にネイティブの`disabled`属性を持つ文字のない常時操作ボタン2枠を表示する。warning行は「詳細」または（関連先がある場合の）「関連」と「確認」を表示する。question／emergency行の表示中だけ選択肢ボタンを表示し、選択肢群の右に全角1文字相当の間隔を置いて「詳細」または（関連先がある場合の）「関連」「送信」を表示する。選択肢なしの場合も「確認」を選択肢ボタンとして表示し、将来の有効なUIでは「確認」を選択してから「送信」する。詳細と関連は排他的である。これらはTabフォーカス対象外であり、現行契約では外部API呼出し・状態遷移を行わない。ボタン以外のキャプションや説明は表示しない。選択肢・詳細／関連データは現行契約にないため、fixture／表示分岐は将来接続境界にとどめる。将来の選択肢・詳細・関連操作は、任意関数・任意URLを実行せず、許可リスト型の構造化ディスクリプタを経由してのみ接続できる設計境界を持つ。
