# Issue #63「H1. ヘッダー点滅ブザーの実装」設計

対象Issue: [H1 #63](https://github.com/BlueKurage119/wx-viewer-poc/issues/63)

前提Issue: A2 #2、D1 #25、A5 #90、H2 #64（いずれも現行実装を確認したもの）。

---

## 1. 目的と範囲

通知到着時、wx-viewer-poc の共通ヘッダーに通知区分ごとの一時的な点滅・ブザー表現を出す。これは単一画面内に閉じた練習実装であり、端末間の受領監視、サーバーへの確認状態送信、中央アプリとの統合、通知による画面遷移は実装しない。

### 1.1 対象

1. H2 が通知取得単位ごとに出す最高区分のチャイム要求（`emergency > question > warning`）を受け、ヘッダーの表現状態へ変換する。
2. `warning`、`question`、`emergency` の各区分で、区別できる点滅状態を表示する。
3. `warning`／`question` の実行中は通常青と濃い青を、`emergency` の実行中は赤と濃い赤を交互に表示する。
4. 画面上の「ブザー停止」操作で、現在の一時表現と音声を停止する。通知そのもの、cursor、未読、確認済み状態は変更しない。
5. ブラウザの自動再生制限により音声開始が拒否されても、ヘッダー表現と通知取得を止めない。後続のユーザー操作で音声利用を再試行できる状態を保つ。

### 1.2 対象外

- H2 #64 が担当する通知取得、行ごとの表示、確認、件数、端末モードによる表示除外。
- H3 #65 が担当する非常ブザーのスヌーズ、再鳴動の周期、再通知。
- `1.wav`（お知らせ）と `3.wav`（高レベル警報向け予備音源）の接続。今回の通知区分には割り当てない。
- 通知区分、`ackRequired`、通知文言、通知の優先順位の再定義。

## 2. 現状と責務境界

- `useNotificationFeed` は新着を受けた取得単位で `onChimeRequest` を呼べる境界を持つ。最高区分は `emergency > question > warning` として `notificationStore` が決定済みである。
- `AppShell` は停止用の全面透明ボタンを受け取れるが、呼び出し元は未接続である。現在のヘッダーは MD3 primary 面、中央には受信異常表示を置く。
- 通知行は既存の `--wx-notice-warning-*`、`--wx-notice-question-*`、`--wx-notice-emergency-*` を使う。非常の outline は境界専用であり、面には使わない。
- 通知の確認済み状態は H2 のメモリ内 state である。ヘッダー停止を確認操作として扱ってはならない。

したがって H1 は通知 store を複製せず、`onChimeRequest` と停止操作の間にだけ、ヘッダー／音声の寿命を管理する UI 専用 hook を置く。

## 3. 表現・状態遷移

### 3.1 区分別の表現

| 要求区分 | ヘッダー面 | 点滅 | 音声要求 | 停止 |
| --- | --- | --- | --- | --- |
| `warning` | 通常青と濃い青 | 青系の明滅 | `2.wav`（警報チャイム）を確認扱いまでループ | 停止操作 |
| `question` | 通常青と濃い青 | 青系の明滅 | `4.wav`（問いかけチャイム）を確認扱いまでループ | 停止操作 |
| `emergency` | 赤と濃い赤 | 赤系の明滅 | `5.wav`（非常チャイム）を確認扱いまでループ | 停止操作。スヌーズは H3 |

ユーザー提供の再打ち込み済み音源を使用し、`HTMLAudioElement.loop = true` とする。`warning` を含む全区分は、対象通知が端末内で確認扱いになるまで継続鳴動する。ヘッダーの停止操作は単なる消音ではなく、表示中通知の端末内確認操作を要求する。H1 はその対象の `feedKey` を H2 の `confirm` へ渡し、確認成功時だけ音声・点滅を停止する。確認後に同じ行の次の未確認通知が表示される場合は、H2 がその通知の区分と `feedKey` を H1 へ渡して鳴動を継続する。現行の H2 の非活性ボタンを確認済みと読み替えず、この接続は実操作を有効化する変更と一緒に実装する。

同一取得で複数区分が来たときは store が返す最高区分だけを開始する。実行中により高い区分の要求が来たら直ちに置換し、同じか低い区分の要求は実行中の状態を弱めない。停止後は過去通知から自動で再開しない。H3 のスヌーズだけが非常の再開を扱う。

### 3.2 実装構成

`apps/web/src/notifications/useHeaderBuzzer.ts` を追加し、次を公開する。

```ts
type HeaderBuzzerCategory = 'warning' | 'question' | 'emergency';

interface HeaderBuzzerState {
  readonly category: HeaderBuzzerCategory | null;
  readonly feedKey: string | null;
  readonly isActive: boolean;
}
```

- hook は `request({ category, feedKey })` と `stop()`、表示用 `HeaderBuzzerState` を返す。`stop()` は `feedKey` を呼び出し元へ返し、H2 の端末内確認が完了したときにだけ音声を停止する。タイマーと `HTMLAudioElement` は hook 内で生成・破棄し、アンマウント時に必ず停止する。
- 音源未設定または `play()` の拒否は、画面操作状態へ例外を伝播させない。必要なら開発時だけ console へ記録するが、通知取得・cursor・確認済み状態を変更しない。
- `App.tsx` は `useNotificationFeed` のチャイム要求を、区分だけでなく表示対象の `feedKey` とともに hook の `request` へ渡す。`AppShell` には状態と確認を要求する `stop` を渡す。プレビュー fixture でも同じ経路を使う。
- `AppShell` は状態から `data-buzzer-category` をヘッダーへ付与し、停止操作を有効な `<button type="button">` として表示する。全面透明ボタンのままキーボード操作やヘッダー内の時刻・端末名を覆う構造にはしない。
- CSS の animation は `prefers-reduced-motion: reduce` で点滅を止め、非常時の赤面・区分名を含む支援技術向け状態文は残す。自動フォーカスはしない。

### 3.3 色の使い分け

- warning／question のヘッダー面は通常の MD3 primary と、その dark 側の濃い青トークンを使う。通知区分ごとの警告色をヘッダー面に流用しない。
- emergency のヘッダー面は MD3 error 系トークンの赤と濃い赤を使う。基本設計 §7.2 の「ヘッダーを赤表示」を満たす。
- 下部通知行は、`question` を薄赤背景＋赤文字、`emergency` を赤背景＋白文字とする。既存の `--wx-notice-question-*`／`--wx-notice-emergency-*` の役割と生成値がこの方針を満たすかを確認し、満たさない場合は A5 #90 の変更として別途設計する。本 Issue でトークンを再定義しない。
- 非常用の赤面に `--wx-notice-emergency-outline` を使わない。outline は通知行の境界専用である。
- HEX／RGB の直書き、通知区分トークンの再定義、A5 #90 の変更は行わない。

## 4. 未決事項と製造保留境界

### H1: 非常赤面と既存の受信異常表示の同時視認性

非常中、中央の「受信異常」バナーも赤系であり、ヘッダー面と区別が弱くなる。AD-H020 が要求する実 UI 目視確認の対象でもある。

| 選択肢 | 内容 | 利点 | 注意点 |
| --- | --- | --- | --- |
| A（推奨） | 非常時はヘッダー全体を error 面にし、受信異常バナーは通常時と同じ文言・アイコンを残し、枠線または中立面で分離する | 非常をヘッダー全体で即座に示しつつ、受信異常を隠さない | 小画面を含む実 UI で文字・境界の視認確認が必要 |
| B | 非常中は受信異常バナーを非表示にする | 赤同士の干渉をなくせる | 異なる重要情報を隠すため採用しない |
| C | 非常時のヘッダーを赤い帯だけにし、受信異常バナーは通常の位置・面を維持する | バナーの既存視認性を維持しやすい | 「ヘッダーを赤表示」の範囲が弱く、非常の即時性が下がる |

ユーザー判断により A を採用する。赤面・受信異常バナー・非常通知行を同時に出した実 UI で、通常幅と狭幅における文字、1px 以上の境界、色の組合せを確認する。これは色方針の再承認待ちではなく、AD-H020 の受入検証である。

## 6. 受入条件

1. `warning`、`question`、`emergency` の新着要求で、それぞれ対応するヘッダー状態と音源が開始する。複数新着では `emergency > question > warning` の最高区分だけを開始する。
2. warning／question は通常青↔濃い青、emergency は赤↔濃い赤で表示され、下部通知行は問いかけの薄赤背景＋赤文字と非常の赤背景＋白文字を満たす。
3. 実行中の低い区分へ高い区分が届くと高い区分へ置換し、低い区分の到着で非常・問いかけを弱めない。停止後に既存通知だけから再開しない。
4. 各区分の音源は `loop` を有効にして確認扱いまで継続し、停止操作はキーボードで到達・実行できる。停止操作は表示中の通知だけを端末内で確認扱いにしてから音声・点滅を止め、別通知、cursor、未読、未対応を変更しない。
5. 音声再生が利用不能・拒否されても、例外で画面を壊さず、通知取得と視覚状態が継続する。
6. reduced motion では点滅を止めても、非常の赤面と状態通知を残す。自動フォーカスはしない。
7. 非常、受信異常、非常通知行を同時に表示し、通常幅・狭幅で文字、1px 以上の境界、色の組合せが判別できることを目視確認する。この確認が AD-H020 の結論であり、CAM16 距離だけを弁別保証に使わない。
8. `2.wav`／`4.wav`／`5.wav` の出典、MIT ライセンス全文、著作権者、再打ち込みである旨を配布物で追跡できる。`1.wav`／`3.wav` は今回の配布・再生対象に含めない。
9. `npm run lint`、`npm run typecheck`、`npm run format:check`、`npm run test -w apps/web` が成功する。

## 7. AD-H020 の記録

AD-H020 は**未確認・実機待ちのまま維持**する。A5 #90 によるトークン実装と色見本の確認は済んでいるが、小バッジ・同時通知・非常赤面と受信異常の実 UI 視認性は未検証である。本 Issue では上記受入条件 7 の目視確認を行って初めて解消可否を判断する。採否待ちの保守事項を自動的に修正必須へ昇格させない。

## 8. 製造順序

1. hook の純粋な状態遷移、区分別ループ、単体テストを追加する。
2. `App.tsx` と `useNotificationFeed` の既存 callback 境界を接続し、fixture で区分別に起動できるようにする。
3. `AppShell` と CSS に状態属性、停止操作、reduced motion を追加する。
4. `../chime/2.wav`、`4.wav`、`5.wav` を公開資産へ複製し、MIT ライセンスと出典・再打ち込み情報を同時に追加する。
5. AD-H020 の同時表示を実 UI で確認する。
