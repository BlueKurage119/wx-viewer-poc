# Issue #69: 訓練電文の項目選択・自動生成・プレビュー

## 状態と目的

**設計承認済み・製造許可済み。** 2026年10月11日のヒアリングと追加判断を反映する。下記を既存対応形式に合わせた製造契約とする。速報5種類の地域・雨量・現象の想定もオーナー承認済み。電文テンプレート完成後にオーナー自身による監修を予定しており、完成テンプレートの監修済みを意味しない。

原 Issue J1 の「来歴付きサンプル電文カタログ（一覧・選択）」を、選択項目からその場で合成電文を生成する機能へ変更する。既存サンプルを選んでそのまま投入する機能ではない。来歴の区別は引き継ぎ、生成結果は常に訓練用の合成電文と表示する。Issue 本文の変更は本設計作業では行っていない。

## ヒアリング済み事項

- 【確定】今回の対象は J1 のみ。発表の生成だけを扱い、取消は次回 PR で対応する。取消と解除を混同しない。
- 【確定】地域条件に合わない項目は選択不可とする。→ 2026年10月12日のUI監修で、選択不可表示ではなく項目ごと削除に変更（項目表参照）。
- 【確定】同一現象内は単一段階、異なる現象間は複数選択とする。
- 【既存確定】利用は K 端末のみ。[基本設計](../basic-design.md) §3.4 と [画面設定](../../apps/web/src/shell/config.ts) の既存挙動を維持し、新しい認証は追加しない。
- 【確定】警戒レベルを冠する情報だけでなく、雷・強風等を含む警報・注意報全般を対象とする。
- 【確定】気象防災速報は線状降水帯発生、線状降水帯直前予測、記録的短時間大雨、竜巻注意、竜巻目撃の5種類を含め、地域・雨量・現象の想定は承認済み。完成した電文テンプレートはオーナーが監修する。
- 【確定】ユーザーが操作するのは項目の選択。複数選択を可能とする。
- 【確定】日時は生成時点、地域は東京ビッグサイト付近かつ実際にあり得る区域構成に自動設定する。日時・地域の入力欄は設けない。
- 【確定】今回の到達点は項目選択、合成 XML の生成、内容プレビュー。通常パイプラインへの注入は J2、通知・履歴・表示全体への伝播は J4 に残す。

### 追加ヒアリングで確定した方針

1. **地域適合。** 江東区を含む適切な区域で成立する項目のみ生成可能とし、地域条件に合わない項目は項目表から削除する（当初は選択不可表示としたが、2026年10月12日に削除へ変更）。種類を増やすために対象を近隣へ広げたり、不自然な地域に置き換えたりしない。採用する項目は次の項目表に固定する。
2. **生成状態。** 今回は新規の発表を生成する。継続・強化・解除の遷移セットは含めない。取消は次回 PR で扱い、解除の生成で代替しない。ユーザーの明示は「取り消し（→解除でない）」である。
3. **同一現象の複数段階。** 現象内は単一段階、異なる現象間は複数選択とする。同じ現象の競合する段階を同時生成せず、UI と API の双方で制御する。

これらの操作方針に追加の質問はない。以下の数値・時間幅は訓練シナリオの固定値であり、公式の発表基準や運用周期を意味しない。

## 型・API契約

```ts
type TrainingItemId = `warning-${string}` | `bulletin-${string}`;
type TrainingTelegramType = 'VPWW55' | 'VPWW56' | 'VPWW57' | 'VPWW58' | 'VPWW59'
  | 'VPWW60' | 'VPWW61' | 'VPBS50' | 'VPHW50' | 'VPHW51';
interface TrainingItem {
  readonly id: TrainingItemId;
  readonly label: string;
  readonly group: string;
  readonly selectable: boolean;
  readonly unavailableReason: string | null;
}
interface TrainingGenerateRequest {
  readonly terminalId: string;
  readonly itemIds: readonly TrainingItemId[];
}
interface TrainingTelegramPreview {
  readonly id: string;
  readonly itemIds: readonly TrainingItemId[];
  readonly telegramType: TrainingTelegramType;
  readonly title: string;
  readonly xml: string;
  readonly reportDateTime: string;
  readonly targetDateTime: string;
  readonly validDateTime: string | null;
  readonly areaNames: readonly string[];
  readonly provenance: 'synthetic';
  readonly isTraining: true;
}
interface TrainingGenerateResponse {
  readonly generationId: string;
  readonly generatedAt: string;
  readonly telegrams: readonly TrainingTelegramPreview[];
}
```

- `GET /api/training/items?terminalId=...` → 200 `{ items: TrainingItem[], targetLabel: '東京ビッグサイト周辺' }`。queryはterminalIdだけを許可し、配列・重複・未知キーを拒否。
- `POST /api/training/preview` → 200 `TrainingGenerateResponse`。bodyはplain objectで、上記2キー以外を拒否。terminalIdは空でない文字列、itemIdsは1～16件、各IDは64文字以下、既知・選択可能・重複なし・group内1個を要求。日時・地域・生XML・modeを入力として受け付けない。query付きPOSTは未知パラメータとして拒否する。
- 不正入力／不明端末は400 `{status:'error',code:'invalid_request'}`、登録H端末は403 `forbidden_terminal`。registry/service未構成は503 `training_unavailable`。生成かparser照合の失敗は500 `training_generation_failed`。失敗時にXMLや部分成功を返さない。
- 成否すべて `Cache-Control: no-store`。既存の `express.json()` より前に `/api/training` 限定でheaderを設定するmiddlewareを置く。body上限は全体設定を変更せず、trainingルートでUTF-8の `JSON.stringify(req.body)` が16KiB以下か検証し、超過は413 `request_too_large`。既存HTTP parserが先に拒否した場合はその413を維持する。
- 生成時計は1回だけ読む。`generatedAt` はそのUTC ISO値、`T=floor(now/60000)*60000` を全電文共通の発表時刻とする。APIの日時はUTC ISO、XMLのHead/Body日時はJST `+09:00`、Control日時はUTC `Z`。
- `idFactory` は UUID v4文字列を返すものに固定し、テストも有効なUUIDを注入する。`generationId=idFactory()`、結果idは `generationId + ':' + zeroBasedIndex`。同じ分の再生成でもIDは異なるが、XML発表時刻が同じになることは正常。電文順は VPWW55、56、57、58、59、60、61、VPBS50（発生、直前、記録雨の定義順）、VPHW50、51 とする。
- `generateTrainingTelegrams(itemIds, {now, generationId})` はネットワーク・DB・環境時刻を参照しない。同じ引数に同じ出力を返す。

## XML共通規則

`Report` の名前空間は `http://xml.kishou.go.jp/jmaxml1/`、Headは `.../informationBasis1/`、Bodyは `.../body/meteorology1/`、量要素 `jmx_eb` は `.../elementBasis1/`。属性・本文はXML escapingし、DOCTYPE、外部実体、任意XMLの入力を許さない。生成結果は要素名・値から組み立て、サンプル全文の文字列置換や通常電文の再ラベルはしない。

Controlは `Status=訓練`、`DateTime=now`、`EditorialOffice=気象庁`、`PublishingOffice=気象庁`。この官署名は形式内の合成設定であり、画面には常に「訓練用合成」を表示する。Headは `InfoType=発表`、ReportDateTimeとTargetDateTimeはT。

訓練用に対象区域だけを表現する部分電文とする。公式配信の都内全区域スナップショットではない。無関係な地域に「発表なし」を生成せず、J2で欠落区域の削除として扱わない。参照元の原本はoriginal、出力はsynthetic。定義に参照資料URL・使用した原本ファイル名・生成内容を残す。

### 警報・注意報

- Control/Titleは `気象警報・注意報（Ｒ０６）（大雨／土砂／高潮／暴風／波浪／大雪／その他注意報）` の該当1つ。Head/Titleは `東京都大雨警報・注意報` 等、VPWW56は `東京都土砂災害警報・注意報`、VPWW58は `東京都暴風警報・注意報`、VPWW61は `東京都{選択した現象名を「・」で連結}注意報`（雷だけなら `東京都雷注意報`）。InfoKindは `気象警報・注意報`、Versionは `1.5_0`。EventID／Serialは空タグ。ValidDateTimeは生成しない。
- Headline/Textは `【訓練】江東区に{選択名を読点で連結}を発表する想定です。`。Informationは `気象警報・注意報（府県予報区等）`／`（一次細分区域等）`／`（市町村等をまとめた地域等）`／`（市町村等）` を生成し、対応区域は東京都130000／東京地方130010／２３区東部130012／江東区1310800。
- HeadlineのKindは選択したName/Code、Areas/codeTypeは上3層が `気象情報／府県予報区・細分区域等`、市町村が `気象・地震・火山情報／市町村等`。
- Body/Warningも同じ4種類のtype・同じ区域を持つ。各Itemは選択Kind群→Area→ChangeStatusの順。KindのStatusは発表、LastKind／NextKinds／Kind/DateTimeは省略（個別新規発表であり集約通報ではない）。ChangeStatusは `警報・注意報種別に変化有`。上3層にはFullStatus=一部、EditingMark=0を置き、市町村層には置かない。Propertyは市町村Kindにのみ生成する。

レベル5は危険度51、Kind/Condition=氾濫発生とする。**CriteriaPeriodを省略しない**。R06解説§3-2-4-1-1-5-3の［解説］1～4に従い、CriteriaClass=警戒レベル５相当/51、TimeはTの直前の正時（Tが正時ならT）、SentenceはそのJST時刻にレベル5相当へ到達した想定とし、継続期間が示せない想定なのでDurationだけを省略する。高潮基準超過は値4.0・Time=T、ピークは値4.2・Time=T+1h。この数値は公式江東区高潮基準（L4=3.4m、L5=4.0m）を踏まえた合成値。江東区の別紙4の予報区間・海岸・水位基準欄は空なので追加の高潮予報区間Warning／TidalAreaPartを生成しない。

**訓練画面の定義（J1）**

- `AppShell` の `toolbar` スロット（`view-content` の下）に、`view === 'training'` のとき `TrainingToolbar`（`OperationToolbar` を使う薄い部品）を渡す。外枠classは `view-toolbar view-toolbar-monitor`。
- 階層は1段（ルート `training-root`、`title: ''`）。ルートにいるので `<<`・`<` は監視画面と同じく `disabled`、階層名は表示しない。定義は配列で持ち、J2以降で `navigate` 項目と子階層を足せる形にする。
- 項目: ルートの1グループに選択型の「削除」「全削除」（この順、文字だけ、アイコンなし）。アイコン付きはクリア・送信だけ。両者は排他（選択は常に1つだけ。別の項目を押すと選択が移る、監視の規則と同じ）。
- 削除の規則（監視の Worker再起動＝`softDisabled` で選べない項目の規則に合わせる）:
  - 一覧のチェックが0件のとき「削除」は `softDisabled` で選べない。1件以上で選べ、押すと選択（`monitoring-toolbar-selected` の配色、`aria-label`「削除、選択中」）、再度押すと解除。
  - クリア: 選択中だけ押せ、選択を取消す。チェックは変えない。
  - 送信: 「削除」選択中かつチェック1件以上のときだけ押せ（送信準備の点滅あり）、`aria-label`「削除を送信」（未選択時は「操作を送信」）。押すとまず選択をクリアし、**送信を押した時点でチェックされている行**をすべて一覧から除き、直後に保存内容へ反映する。確認ダイアログは出さない。
  - 選択中にチェックが変わった場合: 選択は維持し、送信の対象は送信時点のチェックとする。【確定】選択中にチェックが0件になったら選択は維持したまま送信だけ押せなくする（監視の「照会中は選択を保持し送信不可」と同じ扱い）。チェックを付け直せば再び送れる。
- 全削除の規則:
  - 一覧が1件以上あれば、チェックの有無に関係なく選べる。0件のときは `softDisabled` で選べない。押すと選択（「全削除、選択中」）、再度押すと解除。
  - 送信: 「全削除」選択中かつ一覧1件以上のときだけ押せ（点滅あり）、`aria-label`「全削除を送信」。押すとまず選択をクリアし、一覧を全件消し、`localStorage` に空配列で保存する。チェックも全て消える。確認ダイアログは出さない。
  - 選択中に一覧が0件になった場合（削除の送信はできないため、20件上限による自動削除では起きず、端末切替等の破棄契機以外では実質起きないが、規則として）: 削除と同じく選択は維持し送信だけ押せなくする。
  - 選択の破棄契機は削除と同じ。
  - 生成中も削除の選択・送信はできる（生成結果は削除後の一覧の先頭に入る）。
  - 選択を破棄する契機: 送信、クリア、【確定】XML表示ダイアログを開く（監視のダイアログ表示と同じ）、画面離脱・端末切替（`resetToolbarToRoot`）。
- メッセージ: 監視と同じく共通通知領域の操作行に出す（`view === 'training'` のとき訓練の操作行を渡す）。
  - 選択中: `削除を選択中／送信で実行`／`全削除を選択中／送信で実行`（共通の `selectOperationLine`）。
  - 送信後: どちらも `{n}件を削除しました`（nは実際に消した件数）。【確定】次の選択・送信または画面離脱まで表示し、そこで消す。保存失敗は従来どおり右ペインの状態行に出す。
  - 生成中・生成失敗は右ペインの状態行のまま（ツールバーの操作ではないため操作行に出さない）。
- J2で「投入」「取消」を同じルートのグループ（またはnavigateで入る子階層）に選択型項目として追加し、送信の実行先を項目ごとに分ける。チェック選択はそのまま投入・取消の対象選択に使う。

#### 左ペイン（電文を作るゾーン）

- 上部（内部スクロール）: 区分見出し（警報・注意報／気象防災速報）の下に、**1行1カテゴリ**の `div.training-category[role="group"]`（`aria-labelledby` でカテゴリ名を参照）を並べる。fieldsetは使わない。
  - 複数段階のカテゴリ（大雨・高潮・風・波浪・大雪・線状降水帯・竜巻）: 「なし」＋各段階のradio。
  - 1項目だけのカテゴリ（土砂災害＝レベル２土砂災害注意報、記録的短時間大雨）: checkbox 1つ。
  - **「その他」行**: VPWW61系の雷・濃霧・乾燥・低温・霜・着氷・着雪の7注意報を、1行の中にcheckbox 7つで並べる（行名「その他」）。各checkboxはAPI上の各group（thunder、fog、dry、cold、frost、icing、snow-accretion）に対応し、独立にオン・オフできる。現状の実装で別行になっている7行はこの1行に統合する。行内で折り返してよい。
  - 表示上の行のまとめ方は画面側の対応表（VPWW61系のgroupを「その他」行へ寄せる）で行い、APIの項目・groupは変えない。
- 下端（固定、スクロールしない）: 操作行に「生成」「リセット」（`GbButton`、`size="sm"`、生成=filled、リセット=text。幅は状態で変えない）。
  - 押下即実行。生成は1項目以上選択・項目読込済み・非送信中のときだけ、リセットは1項目以上選択・非送信中のときだけ押せる（`softDisabled`）。失敗後も「生成」のまま、再押下で再試行。
  - リセットは項目選択の全解除で、一覧（ストック）とそのチェックは変えない。
  - 生成成功時は項目選択を全解除する（リセットと同じ結果。UI監修による追加）。失敗時は再試行のため選択を維持する。
- 送信中は左ペインの全入力をdisabled。選択変更で一覧は変えない。
- 項目読込中・読込失敗（CircularProgress／「項目を取得できませんでした。」＋再読込）は左ペイン上部内に出す。

#### 右ペイン（生成した電文の一覧＝ストック）

上から「状態行」「一覧」の2段。

- **状態行**（高さ48px固定）: 左に件数 `n／20件`、右に状態表示。生成中は `CircularProgress`（小）＋「生成中」(`role="status"`)。生成失敗時は日本語エラー文(`role="alert"`、`--md-sys-color-error`、1行・省略記号)。保存失敗時は「一覧を保存できませんでした」（同じ位置・同じ表示。生成失敗が同時にあれば生成失敗を優先）。自動再送しない。次の生成開始・リセットで生成失敗表示を消し、次に保存が成功したら保存失敗表示を消す。
- **一覧の行**: 1行＝生成した電文1通。行高48px固定。左から「チェック欄」「生成時刻（JST `HH:mm:ss`、`generatedAt`）」「項目名（その電文に含まれる選択項目ラベルを「、」区切り、1行省略記号）」「電文種別（`telegramType` のコードのみ）」。
  - チェック欄は `<input type="checkbox">`（行ごとの `aria-label` は「{時刻} {電文種別} を選択」）。複数チェック可。チェックの操作ではダイアログを開かない。
  - 行のチェック欄以外の部分は1つのボタン要素（チェック欄とは入れ子にしない）。クリック・Enter・SpaceでXML表示ダイアログを開く。
  - 生成成功時、新しい先頭行にもチェックは付けず、ダイアログも開かない（自動の強調もしない）。
  - チェック状態は保存しない（再読込・画面切替でチェックは外れる）。
- **並びと上限**: 新しい順。1回の生成で複数通返った場合はその回の電文群を先頭にAPI順で挿入。最大20件、超過は最古から自動削除（チェック中の行が押し出されたらその状態も消える）。1回の生成は最大10通。
- **空一覧**: 状態行の「0／20件」のみ。一覧領域に説明文は出さない（領域は確保）。

#### ストックの保存（localStorage）

- 保存先はブラウザの `localStorage`。端末（ブラウザ）ごとに保存し、K端末どうしでもサーバーでも共有しない。
- **キー**: `wx-viewer:training-stock:v1:{terminalId}`（既存の `wx-viewer:notification-preferences:v1` と同じ命名）。**端末コードごとにキーを分けることを推奨・採用する。** 同じブラウザで端末を切り替えたとき、別端末のストックを混ぜない・誤って削除しないため。端末切替時は旧端末の保存はそのまま残し、新端末のキーから読み直す。チェック・ダイアログは破棄する。
- **スキーマ（version 1）**: `{ "version": 1, "entries": TrainingStockEntry[] }`。`TrainingStockEntry` は既存の `TrainingHistoryEntry`（`id`、`generatedAt`、`itemLabels`、`telegram: TrainingTelegramPreview`）と同じ形。配列は新しい順、最大20件。
- **読込**: 訓練画面の表示時（項目取得と独立に、同期で）と端末切替時に読む。
  - `getItem`／`JSON.parse` を try/catch で囲む。キーが無ければ空。
  - 検証: `version === 1`、`entries` が配列、各要素の `id`・`generatedAt`・`telegram.xml`・`telegram.title` が文字列、`itemLabels` が文字列配列、`telegram.telegramType` が既知の10種、`telegram.provenance === 'synthetic'`、`telegram.isTraining === true`。
  - 1件でも不一致、またはversion違い・パース失敗なら**全体を捨てて空から始め**、そのキーを `removeItem` で消す（これもtry/catch）。部分的な救済はしない。21件以上入っていた場合は新しい20件だけ採用して書き戻す。
  - 読込失敗は画面に表示しない（空から始めるだけ）。
- **書込み**: 生成成功による追加、削除、20件超過による自動削除の直後に、その時点の一覧全体を `setItem` する（try/catch）。
  - 失敗時（容量超過・ストレージ無効等）は画面の一覧（メモリ上の状態）を正としてそのまま使い、状態行に保存失敗を表示する。リトライは次の書込み契機に任せる。
  - 一覧が空になったら空配列で保存する（キーを消さない）。
- 別タブでの変更（`storage` イベント）には追従しない。同じ端末で2タブ開いた場合は、最後に書いたタブの内容が残る。
- サーバーには保存しない。APIは項目取得と生成だけを呼ぶ。

#### XML表示ダイアログ

- 監視画面の `MonitoringDialogHost`（`apps/web/src/monitoring/MonitoringDialogHost.tsx`）と同じ方式とする。
  - ネイティブ `<dialog>` を `showModal()`。`aria-labelledby` で見出しを参照。
  - 開いた時点の `document.activeElement`（押した行のボタン）を記録し、初期フォーカスは「閉じる」。
  - 閉じ方は「閉じる」とEsc（`cancel` を `preventDefault` して同じ閉じ処理）。背景クリックでは閉じない。
  - 閉じたら記録した要素へフォーカスを戻す。要素が消えている場合は `#view-content` へ戻す。
  - Tabは `nextDialogFocusTarget`（`monitoringDialogFocus.ts`）でダイアログ内を循環。
- 表示内容: 見出し（電文名＝`title`）、訓練用合成バッジ、区域、発表時刻（JST）、竜巻のみ失効時刻、項目名。その下にXML全文を `<pre>`（等幅、折返しなし、ダイアログ本文内で縦横スクロール）。`dangerouslySetInnerHTML` は使わない。コピー・ダウンロードは追加しない。
- 表示中に生成が完了し、表示中の電文が一覧から押し出されても、閉じるまで表示を保つ。

#### 寸法・スクロール（状態による揺れを出さない）

- 通常幅（760px以上）: 表示領域を `grid-template-columns: minmax(320px, 2fr) minmax(0, 3fr)` の2ペイン。各ペインは表示領域の高さいっぱいで独立スクロールし、ページ全体はスクロールしない。左ペインは `grid-template-rows: minmax(0, 1fr) auto`（項目／操作行）、右ペインは `48px minmax(0, 1fr)`（状態行／一覧）。
- 狭い幅（760px未満、監視画面と同じ境界）: 1列に積み、左ペイン（操作行を含む）→右ペインの順でページ縦スクロール。一覧は `max-height: 336px`（7行）で内部スクロール。ツールバーは監視と同じく折返しなし・中央域横スクロール。ダイアログは画面幅−32px以下。
- 揺れてはいけない寸法（受け入れ条件で実測）: ツールバー外枠高さ（削除の選択中・送信準備の点滅中を含む）、ツールバー各ボタン幅、生成・リセットのボタン幅、左ペイン操作行の高さ、状態行高さ、一覧行高、通常幅での左右ペイン幅。状態は、空・生成中・生成失敗・保存失敗・1件・20件・チェック0件/複数件・削除選択中・削除直後・ダイアログ開閉・再読込直後。
- 左ペインの行内の折返し（とくに「その他」行）による左ペイン内部の高さ変化は許容（独立スクロールのため右ペインに波及しない）。

### 通信と状態管理

リクエストごとに連番とAbortControllerを持ち、端末切替・画面離脱でabortと連番更新する。古い成功・失敗レスポンスは描画せず、一覧にも保存にも追加しない。サーバー内部処理の取消は不要（副作用なし）。一覧への追加と保存は最新連番の成功応答時だけ行う。保存処理は `storage` を引数で差し替えられる関数（既存 `notificationPreferences.ts` と同じ形）に切り出し、web単体試験で正常・壊れたJSON・version違い・不正要素・21件・`setItem` 例外・`getItem` 例外を確認できるようにする。

## 生成後検証

各XMLを `parseWarningTelegram(rawXml, expected, {municipalCode:'1310800',displayName:'江東区'})`、`parseVpbs50(rawXml, expected, {includedAreaCodes:['1310800','130012','130010']})`、`parseVphw(...)` に通す。expectedはtelegramType、controlStatus=training、reportDateTime=TのUTC、controlDateTime=nowのUTC。okだけでなく、訓練区分・種別・区域・選択コード群・発表時刻が一致することを確認する。原文DOM検証でVersion、Namespace、Property、EventID規則、時間関係も確認する。既存parserは変えない。検証不一致は内部エラーとして全体失敗し、通常パイプラインを呼ばない。

## 受け入れ条件

- [ ] 項目表の全選択可能項目を固定時計 `2026-10-11T14:59:45.000Z` で個別生成し、種別・公式名称・コード・区域・Propertyを本書と比較して一致する。`GET /api/training/items` が33項目・16groupで、削除した09/49/39/17/22を含まない。削除IDを送るとAPIは未知IDとして400。
- [ ] 危険度コードと警報種別コードを独立に比較する。例: warning-43のKind/Code=43、Significancy/Code=41、warning-35はKind/Code=35、Significancy/Code=50。

## 後続への引き継ぎ

J2は生成セットの再検証、注入時の時刻再生成、訓練ID、セットの投入順と原子性を決める。今回の部分電文で、省略区域を「解除」「なし」「削除」へ変換してはいけない。一方、既存 `jmaWarningCurrentReducer.ts` は江東区の個別ストリームを完全状態として採用するため、VPWW58は風・風雪全体、VPWW61はその他注意報全体を置き換える。今回の選択セットは「その生成回における当該ストリームの訓練状態全体」であり、既存訓練への追加差分ではない。例：VPWW61で雷だけを選ぶと、このセットの同ストリームには乾燥を含まない。独立した生成セット間の状態を保持する保証はしない。J1のparser検証は形式・抽出の確認であり、注入後の状態維持を保証しない。J4はisTrainingを通知・履歴・各表示へ伝播する。

取消は次回PRのJ3へ引き継ぐ。**取消と解除は別**で、解除電文による代替はしない。とくにR06・竜巻の公式解説に記載されたInfoTypeは発表／訂正であり、全種へ機械的にInfoType=取消を付ける設計を保証しない。後続では各parser・公式の取消対応・訓練専用取消の必要性を確認し、対象範囲を決める。今回取消方式を先取りしない。J5の受入検証除外も対象外。

UI: J1のツールバーは取得監視画面と共通のモジュール（固定の `<<`・`<`・クリア・送信、階層定義、選択→送信の2段階、操作行メッセージ）で作り、ルート1段に選択型の「削除」「全削除」を置いた。J2では一覧のチェック選択をそのまま投入対象の選択にも使い、「投入」「取消」を同じ仕組みの選択型項目として追加し（ルートのグループまたは `navigate` の子階層）、送信の実行先を項目ごとに分ける。アイコン付きはクリア・送信だけとし、追加する操作ボタンは文字だけにする。外枠寸法は操作追加で変わらない前提とする。生成・リセットは左ペイン下端の押下即実行で、ツールバーには移さない。

時刻: 一覧は `localStorage` に保存され再読込後も残るため、保存した電文のXMLには生成した時刻（発表時刻・Control日時・竜巻の失効時刻等）がそのまま入っている。日をまたいで（あるいは時間を置いて）投入すると古い発表時刻の電文になる。投入時に時刻を付け直すか（再生成するか）、古い電文の投入を制限するかはJ2で決める。保存スキーマ（version 1）を変える場合はキーのversionを上げ、旧データは捨てる方針とする。
