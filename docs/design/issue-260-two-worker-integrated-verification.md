# Issue #260 2 Worker 構成の統合検証と運用手順

## 1. 位置づけと根拠

**実挙動未確認:** 本設計では実 Worker、実 HTTP、DB 競合、ブラウザ、性能負荷、終了/reset/rollback を実行していない。§3 の計測条件・目標はユーザーが設計条件として了承した値であり、性能達成を意味しない。

## 2. 検証構成と成果物

本番と同じ Worker 入口・HTTP API を用い、外部気象通信は固定 HTTP fixture サーバーへ向ける。気象 DB と保持 DB は一時ファイル、タイルは専用 cache、ポートは隔離し、利用者の稼働 DB に触れない。障害注入はテスト専用の依存注入/子プロセス制御に限定し、本番 HTTP に注入口を公開しない。同期 XML 解析、実 SQLite 書込み、実ファイル書込みを負荷源とする。未解決 Promise だけの試験は待機経路の確認に限る。

成果物は (1) 再現コマンドと機械可読な生計測値、(2) 条件・分布・失敗数・原因を示す統合検収記録、(3) 実行確認済みの運用手順とする。保存先は `docs/design/issue-260-verification-results.md` と `docs/operations/weather-workers.md`。製造段階のコード/試験ファイルは検証に必要な最小範囲とし、先行設計書と基本設計の確度表示を無断で変更しない。結果ファイルには比較元/対象コミット、dirty 状態、OS、Node、SQLite/driver、CPU、メモリ、DB/WAL 設定、会場・端末設定、fixture の生成手順/ハッシュ、DB/原文/タイルの件数と bytes、コマンド、開始/終了時刻を記す。

## 3. 比較と計測条件【承認済み設計条件】

比較元は #256 直前の `3e95635`、対象は #266 の修正を含む `8ad36a6` とする。両者の完全な SHA と dirty 状態を計測記録に残し、同じホスト・Node/driver・設定・fixture/DB 複製・HTTP 要求列を使う。両構成で実現不能な API は「比較不可」と明示し、最終構成の絶対基準で判定する。初回取得所要時間の短縮は目標としない。rollback の対象は #259 マージ `2619133` とし、DB 互換性を検証条件とする。

| 条件 | 固定値と理由 | 記録・判定上の注意 |
| --- | --- | --- |
| DB 規模 | 固定 seed で生成する5万電文、原文 1件1 KiB（合計約49 MiB）、保存済みタイル1,024枚・1枚64 KiB（合計64 MiB）を基準 fixture とする。#193 と同じ電文件数を保ちつつ、提供側のファイル負荷を追加する。 | DB ファイルの実 bytes と索引込みの増分、原文/タイルのハッシュを記録する。生成値を実運用の代表分布と断定しない。 |
| 会場/種別 | 主計測は1会場、境界試験は2会場も含め、H/K、normal/training/test、availability を決定的に配分する。TRC の存在を必須にしない。 | 配分の具体件数と seed を結果へ記録し、旧版と新構成で同じ論理内容を確認する。 |
| 負荷 | 取得の実解析・大量保存・復旧をそれぞれ少なくとも60秒継続し、ピーク/通常を区別する。 | 各負荷の処理件数と実 CPU 時間を記録し、待機だけで60秒を満たさない。 |
| 要求 | 各 API を同時 1 と 8、毎秒 1 と 10 要求で測る。保存済みタイルは hit/miss と清掃競合を別系列にする。 | 指定した投入率に達しない場合は達成率を記録し、そのセルを未検証とする。 |
| cold/warm | DB/プロセス起動直後の cold と、事前読取後の warm を分け、各条件3回以上。時刻/順序を記録する。 | OS ファイルキャッシュを強制消去しないため、cold はプロセス・接続・アプリ cache の初回として定義し、OS キャッシュ状態を推測しない。 |
| 判定統計 | 各セル 100 要求以上、p50/p95/p99 と最大値、タイムアウト・非2xx・切断件数を記録。失敗は除外せず不合格とする。 | 最大値と分位点の両方を提示し、平均値だけで判定しない。 |

時間目標は health 最大500 ms、監視最大1,000 ms、system 差分最大2,000 ms、保存済み気象 API 最大2,000 ms、保存済みタイル hit 最大2,000 ms とする。tile miss は別系列とし、既存の30秒絶対期限内に成功、または想定された停止/失敗条件なら期限内に明示失敗を返す。想定条件と HTTP status/body を実行前に列挙し、遅い成功や不明な失敗を合格にしない。これらは達成済みの値ではない。測定の時計はクライアント送信直前から本文受信完了までの単調時計とし、接続確立・キュー待ちを含める。監視の標本鮮度や system 差分の更新内容も別に検証し、速い空応答だけを合格にしない。

各要求の latency/status/bytes に加え、秒単位で main/両 Worker の CPU・RSS・heap、イベントループ遅延、要求キュー長、DB busy 回数/待機、WAL/checkpoint サイズと時間、状態報告の発生/受領差、cache 使用量を記録する。計測器自身の負荷と空運転を併記する。合否は各系列の全有効試行が時間上限内かつ予期しない失敗0件とする。外乱による無効化は、計測前60秒または計測中に、対象サーバー/fixture/計測器以外のプロセスの CPU 合計が論理1コアの25%を連続5秒超える、あるいは OS の swap 使用量が増える場合に限る。対象処理自身による CPU/メモリ圧迫は無効化理由にしない。無効セルは生値を保存し、同条件を再実行する。外乱計測が取得できない場合は無効化せず結果を残す。

## 4. 境界試験の実施方法

各試験は固定時計・一時 DB の初期状態、障害を入れる境界、期待 HTTP/状態/履歴、復旧条件、終了後のプロセス・接続・lease 残数を記録する。終了、応答途絶、単なる遅延は別 fixture とし、stale だけで自動停止・代替 spawn しない。メイン HTTP は `/api/health`、`/api/monitoring/status?terminalId=...`、system 差分、保存済み情報 API とタイルの実要求で観測する。再開は `POST /api/control/weather-workers/:role/restart` に `{requestId, expectedWorkerGeneration}` を送り、`GET /api/control/weather-workers/operations/:requestId` と監視/履歴で照合する。

| 境界 | 注入と観測する不変条件 |
| --- | --- |
| 気象 DB open/migration | 権限・破損 schema・migration 例外を別々に注入。メインの health/監視/system と保持履歴は継続し、気象だけ明示失敗。保持 DB 障害/共通安全条件違反は既存の起動拒否を確認。 |
| 取得負荷/通常停止/異常終了 | 保存済み情報・タイルの継続、最終更新と Worker 報告鮮度の区別、異常通知1回、自動再起動0回を確認。通常取得停止と Worker 停止を混同しない。 |
| 提供異常終了 | 保存済み閲覧は利用不能を明示し、メイン/取得は継続。専用再開後も受付と reader ready を区別。 |
| 応答途絶/期限切れ | stale 通知と監視応答を確認し、exit 未確認中は代替 spawn 0回。旧 Worker の exit を確認してから明示再開する。 |
| 作成/migration/DB 世代 | reader 開始前の schema 検証、reader close ACK、再接続と旧世代応答棄却を確認。未検証 schema・旧 DB 結果の正常公開0件。 |
| 更新/端末起動/通知 | 現況と cursor の同一スナップショット、claim と監査の同一 transaction、H/K の表示・鳴動・確認状態、初回 tracker と fetch_health 前回状態の維持を独立に照合。通知保存失敗は欠落と監視を確認し、再開で補完/再送0件。新たな変化の通常通知は発行する。 |
| 操作競合 | 同一 requestId 再送、別 ID 二重再開、応答喪失、再開と通常取得操作を注入。unknown を成功/失敗へ推測変換せず、二重 writer・二重実行・古い応答適用0件。 |
| DB/タイル競合 | busy/checkpoint、cache hit/miss、清掃/差替え、64件境界と超過要求を試す。破損を正常配信せず、待機・バッファ・メモリが既存上限内。 |
| 全体停止/reset/rollback | 正常・処理中・失敗後に main/両 Worker/タイマー/lease/read-only 接続を終了。DB 本体と付随ファイルの停止確認後のみ reset。保持履歴の不変と、対象旧版で読める DB/schema・保存データの保全を確認。 |

## 5. 実ブラウザと運用手順

隔離ブラウザで、取得/提供それぞれの正常、停止理由、報告 fresh/stale、再起動可否、受付後 ready 前、再開失敗、結果不明、操作履歴を実操作で確認する。通常取得操作との違い、H/K 表示・鳴動・確認状態も確認する。画面の時間表示は画面更新時刻と元データ/報告時刻を別々に観察する。

運用手順には、通常停止、異常停止、stale、DB 読取不能の見分け方、role 別の再開条件、旧 Worker exit 未確認時の待機と再確認、結果不明時の requestId 照会/再読込、再開失敗後の次の行動を記す。reset は両 Worker と read-only 接続を含む全接続停止、DB 本体・`-wal`・`-shm`・`-journal` の開放確認、既存の計画/digest/journal 手順を明示する。付随ファイルを手動削除しない。rollback は `2619133` のコードが `8ad36a6` で生成・更新した DB を読み取れるか、schema version・migration・代表データの照合で事前検証する。互換性が証明できない場合はバックアップから復元する分岐とし、保持 DB・気象 DB・タイル・操作/通知履歴の保全確認を記す。実行できなかった分岐は手順検証済みと書かない。

## 7. 残る確認事項と後続

比較元に存在しない API は最終構成の絶対基準で判定する。生成 fixture は再現可能な検証入力であり、実運用分布の代表性までは主張しない。tile miss の「想定された停止/失敗条件」は既存 API 契約の status/body に沿って製造前に列挙し、その契約を変更しない。rollback 互換性が確認できない場合、直接起動を合格にせずバックアップ復元経路を検証する。

#260 で判明した機能未達は対応する先行 Issue へ戻し、基準変更や制約記載だけで完了にしない。
