# テスト検証業務標準

対象: 主に製造担当・検収担当。手法の詳細・限界・過去の失敗事例は[G-03-verification-discipline.md](advisory/G-03-verification-discipline.md)を参照。

## redを先に確認する(必須)

新しく追加したテストは、対応する実装を意図的に壊して**実際に落ちることを確認してから完成とする。** 確認手順と結果を最終報告に書く。この確認をしていないテストは追加完了とみなさない。

## ミューテーション判定の必須手順

1. **対照実験を先に行う。** 意味を変えないダミー改変(コメント挿入等)を注入し、SURVIVEDになることを確認する。
2. 対照実験の後に本番の判定(実装を壊してテストが落ちるか)を行う。
3. SURVIVEDを短絡的に「テストの不備」と断じない。等価ミュータントの可能性を呼び出し関係を追って確認してから報告する。
4. 判定の範囲は、設計書が定めた受け入れ条件の項目に限定する。網羅的なバッテリを自発的に組まない。

対照実験を省略した判定結果は無効とする。

## アサーションの原則(必須)

- 期待値の検証は**完全一致を基本とする。** 部分一致(`includes`/`toContain`)を使う場合は、意図的である理由を明記する。
- 期待値を実装の式からコピーしない。独立に計算するかリテラルで書く。

## この手法で保証されないもの

ミューテーションテストが保証するのは「既存のテストが実装の変更を検知できること」であって「テストすべき次元が揃っていること」ではない。次の観点は別途、検証計画([04-inspect-protocol.md](04-inspect-protocol.md)の「2. 検証計画」)で扱う。

- アサーションが部分一致・緩い比較になっていないか
- 境界値・並行実行など、実装を壊しても落ちない次元がないか
- 公開面の契約(不変性・単位・null許容)で、テストが1方向しか見ていないものがないか
