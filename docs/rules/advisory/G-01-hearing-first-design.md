# ヒアリング前提の設計になっている理由

対象: 統括担当・設計担当。権限境界・設計書に必ず含める項目(必須事項)は[02-design-protocol.md](../02-design-protocol.md)を参照。

`docs/issues-draft.md`のIssue項目は「実装タスク単位の見出し+参照する基本設計の章番号」程度のあっさりした内容であり、実装方針を左右する論点の多くが未確定のまま残っている。このプロジェクトが他プロジェクトの3体構成と異なり、設計着手前に統括担当によるヒアリングフェーズを挟んでいるのはこのため。統括担当がユーザーへヒアリングし、確定した判断(【確定】事項)をプロンプトに含めて渡し、設計担当はこれをそのまま前提として使う。

`docs/design/issue-1-project-initialization.md`の構成(目的/参照資料/設計方針/変更対象/対象外/実装手順/検証計画/受け入れ条件/Issue本文へ反映する事項/実装上の注意)が設計書の書式・粒度の手本。Issueの性質に応じて節を増減してよい。設計書は「製造担当が迷わず実装できる粒度」で止め、実装の細部を擬似コードで埋め尽くさない。
