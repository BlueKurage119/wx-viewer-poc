# 外部レビューへの向き合い方

- 対象: 統括担当
- 関連する業務標準:
  - 外部レビュー対応の権限は[01-dev-workflow-protocol.md](../01-dev-workflow-protocol.md)の「外部レビュー対応の権限」
  - 独立レビューのゲート・レビュー担当の権限境界・指摘の真偽判定は[08-independent-review-protocol.md](../08-independent-review-protocol.md)
- 参照すべき関連指導文書:
  - 委託先の成果物の検証は[G-04-verification-basics.md](G-04-verification-basics.md)

## トリアージと再レビュー

- 外部ツールによるコードレビューは、統括担当がトリアージ(要対応・先送り・無視)を行ってから、本当に必要なものだけを提示する。年に1回あるかどうかのバグに何時間と何万トークン費やして直しても費用対効果が薄い。
- 修正が局所的で、指摘を再現する回帰テストを追加しすべての必須検証が通った場合、再レビュー不要と統括担当が提案してよい。
- **出典: `mj-stats-viewer`での起動条件の実績。** 外部レビュー(Codexの自動PRレビュー等)は、PRを開いたとき・Draftを Readyにしたとき・`@codex review`とコメントしたときに走る。**既存PRへの単なるpushだけでは自動起動しない。** ユーザーが再レビューを依頼する際の操作例は、明示的なコメントによる起動である。
- 外部レビューは、設計・製造・検収の当事者が同じ設計書・同じテストの枠組みを共有しているために見えなくなる「枠組み自体の穴」を検出できることがある。ミューテーションテストで全件KILLEDを達成した直後でも、部分一致アサーション・並行実行・共有可変インスタンスのエイリアシングなど、原理的にミューテーションでは検出できない欠陥が外部レビューで見つかった実績がある(`mj-stats-viewer`)。指摘は必ず実際のコードで裏取りしてからユーザー・統括担当へ説明する(鵜呑みにも却下にもしない)。

## 独立レビューの試行(2026-10-13〜、試行中)

オーナーの方針は「独立レビューは、なるべく製造に関与していない視点からのチェックが望ましい」である。そのため、製造に関与しないAGY(Antigravity CLI、Gemini系)を主とし、`/code-review`で補う運用を試している。以下は3PRの実績であり、**確定した優劣ではない**(サンプルが少なく、モデルも更新される)。

| PR | レビュー方式 | 結果 |
| --- | --- | --- |
| #278 | AGY(gemini-3.8-flash-high) | web側の局所的な競合・状態の不整合を、Claudeより多く拾った。誤った指摘は0件。処理をまたいで時刻を比べる不具合は、名指ししても見落とした。 |
| #281 | AGY(gemini-4-argon-medium) | 実際の不具合2件を確実に指摘し、誤検知は0件。不具合は、テストの設定注入漏れ(`startServer`呼び出し10箇所以上)と、本番エントリの直接起動の残存。 |
| #281 | `/code-review low` | 指摘なし。 |
| #281 | `/code-review medium` | 注入漏れは見落とした。一方、テストの検証力の低下(cwd非依存テストが文字列比較に弱まった)は、medium だけが拾った。 |
| #283 | AGY(argon medium)と`/code-review medium`を並行 | 現行テストを落とす不具合は、どちらも0件。表に出ていない弱点は、両者が共通して指摘した。argonは呼び出し元と行番号つきで裏付けが深いが、設計書の古い記録をそのまま「AC-2未達」と指摘した(実際は検収で実施済み)。mediumは採用できる改善案を3つ出した(遅延0の無限発火、本番側の改修案、事前のassert)。 |

試行中の運用上の見立て(いずれも権限・合否を変えない):

- AGYを主にする。
- 時刻や状態をまたぐ処理、またはテストの検証力が論点のPRでは、`/code-review medium`以上で補う。lowは浅すぎた。
- AGYは、設計書などの記録を鵜呑みにすることがある。記録と実際の状態が食い違うときは、`git log`や検収報告を正とする。

## 依頼文の雛形(AGYへの独立レビュー)

依頼文には次を入れる。

1. 対象: 作業ディレクトリ、ブランチ、基点(`origin/main`との差分)、設計書のパス。
2. 制約: 読むだけとする。ファイルを編集・コミットしない。`npm`コマンドを実行しない。PRにコメントしない。
3. 観点:
   - A: 差分を1行ずつ読む。
   - B: 削除した行の監査(削除で失われた挙動・検証がないか)。
   - C: 呼び出し元の追跡と、時系列のシナリオ(処理をまたぐ時刻・状態の比較)。
   - D: 設計書の受け入れ条件ごとに、それを試験するテストがあるか。
   - E: 整理系(不要になったコード、命名、重複)。
4. 優先順位: 記録(設計書・コメント)と実際の状態が食い違うときは、`git log`や検収報告を正とする。
5. 報告に含める: 読んだファイルと確認した呼び出し元の一覧、指摘ごとのファイル・行番号・根拠・影響。

## `/code-review`で補う条件

`/code-review`は、Claude Codeのハーネス独自のスキルである(Codex・Antigravityでは使えない)。Claude Code以外が統括担当のときの補い方は、未検証である。

- 時刻や状態をまたぐ処理が差分に含まれる。
- テストの検証力の低下(アサーションの弱まり、実読込から文字列比較への置換など)が論点である。

レベルは`medium`以上とする(#281で`low`は指摘なし)。`/code-review`は統括担当と同じ環境で動くため、AGYと比べて製造・設計の文脈から独立していない点に注意する。

## AGY運用の癖

- タイムアウトの指定には単位が必須である(裸の数値は即座に静かに失敗する)。委託用スクリプトは正規化とfail-fastを備える。
- 報告を返す前に終了することがある。結果の有無を、ファイルとgitの状態から確かめる。
- 結果ファイルの置き場所を取り違えることがある。依頼文で出力先のパスを明示し、実際にそこにあるか確かめる。
- 作業ディレクトリ以外を読ませるには`--add-dir`が必須である。
- 委託の一般的な作法は、スキル`agy-delegate`と[G-04-verification-basics.md](G-04-verification-basics.md)の「委託先の成果物の検証」を参照。
