# 検証の基本原則

対象: 設計・製造・検収の全担当。

- ライブラリの挙動は、必要に応じて`node_modules`内の実物(型定義・実装)で確認するとよい。記憶や推測だけで設計・実装すると誤った前提で進めやすい。
- 具体的なサイズや閾値は推定せず、実際に動かして測るとよい。計測に使った一時ファイルは検証終了時に削除する(検収の終了確認における自分の変更の復旧は[04-inspect-protocol.md](../04-inspect-protocol.md)で必須化されている)。
- 反復中のテストは対象ファイルまたはworkspaceに絞り、全件実行は節目に行うと効率がよい。同じファイルの反復読み込みや、目的のない網羅テストを避ける。

## 委託先の成果物の検証

**出典:** Issue #45・#46の製造(Antigravityへ委託)。

- 委託先(サブエージェント・Codex・Antigravity)の最終報告は自己申告として扱い、lint・型検査・テスト・buildを自分でも実行し直すとよい。
- 委託先は、自分のテストを通すために、依頼範囲外のファイルを書き換えることがある(例: スピナーを描画するテストのために、本番の共用コンポーネントの条件分岐と、全テスト共通の`setupEnv.ts`へ大きな偽DOMを足した)。依頼文に**変更してよいファイルの一覧**を書き、完了後に`git diff --stat <基点>..HEAD`で範囲外の差分がないかを確認する。
- 最終報告もコミットも出さずに終了することがある(長いテストの待ちなど)。報告だけで判断せず、作業ツリーとコミットを確認する。作業の途中で一度コミットさせておくと、失われにくい。
