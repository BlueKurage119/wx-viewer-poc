# Codexのサブエージェントへの委任と共有作業

対象: 統括担当と委任を受ける担当。委任の順序・引き継ぎ情報の制限は[開発フロー業務標準](../01-dev-workflow-protocol.md)、役割の権限は[AGENTS.md](../../../AGENTS.md)を参照。本書は実行支援の知識であり、新たな委任権限や並列実行の許可を与えない。

## 起動方法から隔離を推測しない

2026-09-14の本セッションでは、サブエージェントが親と同じディレクトリを共有することが実行環境の説明に明記されている。これはすべてのCodex製品・設定に共通する保証ではない。サブエージェント、別タスク、別ワークツリーを同じものとして扱わず、その環境のツール説明と実際の作業場所を照合するとよい。

同じ作業場所では、ある担当の編集を別の担当が直ちに読み取れる。一方、編集中のファイルを途中状態で読んだり、別担当の変更を含めてコミットしたりする可能性もある。とくにブランチ切替・ステージング・一時改変による検証は、担当ファイルが別でも影響し合う。

現行業務標準は設計・製造・検収を順に進めるため、製造が終わる前に同じ作業場所で検収用のミューテーションを始める、といった進め方はその順序に合わない。

## 委任時に役立つ確認

会話履歴の継承範囲は起動方法によって異なるため、継承だけを根拠に必要な情報が揃ったと判断しない方がよい。現行の引き継ぎ情報は、業務標準が指定する対象Issue・ブランチ名・設計書パス・ヒアリング済みの確定事項を使う。共通の規程本文は複製せず、その正本を読む構成にすると更新のずれを減らせる。

作業場所や承認済み設計の版が不明な場合は、担当が推測して補うより、統括が環境・履歴と照合して不明点を解消する方が安全である。引き継ぎ情報に作業場所・設計コミットなどを恒常的に追加したい場合は、本書で制限を上書きせず、開発フロー業務標準の改訂として扱う。

モデルを指定できる条件も実行環境によって異なる。役割の推奨モデルと利用可能な起動設定を区別し、推奨モデル名を書いただけで、そのモデルが起動したとはみなさない。

## 成果を受け取る際の見方

担当の報告と、対象ブランチの実際の差分・コミットを照合すると、別作業の混入や未完了を発見しやすい。「完了」という返答だけでは、コミット済みか、検証済みか、設計上の不明点が解消したかは区別できない。

検証証拠を利用する場合は、報告対象の版と現在の実装が一致するかを見るとよい。受け入れ条件の判定・証拠の再利用は[検収業務標準](../04-inspect-protocol.md)に従う。共有作業場所だから再検証が不要になるわけではない。
