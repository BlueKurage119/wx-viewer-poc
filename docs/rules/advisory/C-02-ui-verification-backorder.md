# UI検証の逆発注

対象: 主に`wxviewer-inspector`(検収)。**「実測できなかった項目を未検証のまま申告する」は[04-inspect-protocol.md](../04-inspect-protocol.md)の必須事項。** ここには逆発注の実務(手順書の書き方)を置く。

エージェントが原理的に確認できないUI検証は、手順書を書いてユーザーへ逆発注する。

**逆発注する対象**: OS設定の実切替、実機・高DPIでの描画品質、アニメーション完了イベント、配色やフォントの主観評価、デザインの最終承認。

**逆発注しない対象**(機械で測れるので人手を使わない): `getComputedStyle`/`getBoundingClientRect`で取れる実測値、コントラスト比計算、ビルド・lint・grep、回帰確認。

**手順書の設計で効いた点(`mj-stats-viewer`実績):**

- 手順書と結果欄を同一ファイルにする(往復が減る)
- 全項目に「判断保留」を用意する。合否二択だと迷ったとき無理にどちらかへ寄せて情報が失われる
- 期待結果は具体的に書く(「正しく表示される」ではなく「1回目のクリックで開く。空振りしたら不合格」)
- 主観項目は誘導しないopen questionにし、回答はユーザーの決定として扱い、エージェントは反論しない

検収担当は、実測できなかった項目を正直に申告し(隠して合格扱いにしない)、申告されたものを逆発注シートに集約する。1回の逆発注に複数Issueの積み残しをまとめてよい。

wx-viewer-pocでこの運用を導入する場合、資産の置き場所(例: `docs/ui-verification/`)と雛形は、実際にこの種の検証が必要になった時点で`wxviewer-inspector`が提案し、統括担当の承認を得てから整備する。
