# 設計書の内部矛盾・未実測の値・共用部品の強制挙動

対象: 設計担当・統括担当(ヒアリング)。検収担当が設計起因の不合格を切り分けるときにも読む。ここに書くのは確認の例であり、必須事項ではない(必須事項は業務標準を参照)。

**出典:** Issue #45(F2 雨雲ナウキャスト)・#46(F3 キキクル)。検収を5回繰り返し、うち後半の不合格はすべて設計起因だった。実機で使ったオーナーの所感(「シークバーが固着している」「コマ送りが重たい」)で、設計の抜けが初めて見つかった。

## 1. 数値(遅延・デバウンス・閾値・目標時間)は、実測した操作間隔や応答時間から導く

デバウンスを200msと置いたが、受け入れ条件は0.4秒間隔の連打と300ms/stepのドラッグだった。束ねられず、途中コマのタイルが要求されて不合格になった。値を置く前に、想定する操作間隔・応答時間を実測しておけば、設計の時点で気づけた。暫定値と書く場合も、どの実測を根拠に置いたかを併記する。

## 2. 受け入れ条件どうしと、変更禁止の制約が両立するかを設計時に確認する

「ドラッグ終了(`change`)で読込を始める」と設計したが、その実現にはF4所有の共用ファイル(`TimelineControlCard.tsx`)の変更が要る。一方で別の条件が「F4は変更しない」を求めており、両立しなかった。条件を書いたら、実現手段が触るファイルを、変更禁止の一覧と突き合わせる。

## 3. 共用部品を再利用する設計は、その部品が「必ずする」挙動を先に読む

共用の時間操作カードは、コマがあれば`kind`のバッジ(実況/予報/基準)を必ず表示し、再生ボタンもコマ0件のとき以外は活性になる。キキクルに使うと、「基準を出さない」「再生を不活性にする」というオーナーの指示を、ビューモデルだけでは満たせなかった。設計に「共用部品を流用する」と書く前に、部品側の分岐(型・ラベル・活性条件)を読む。満たせないなら、専用の部品を作る案も候補にする。

## 4. 操作部品には、応答時間と「操作意図/確定状態の分離」の条件を書く

「表示中の画像と表示日時は常に同じコマを指す」という原則を、スライダーのつまみ位置にまで適用してしまい、操作から3〜12秒つまみが動かなかった。連打も、確定前の状態を基準に計算されて握り潰された。原則が守るのは「表示されるコンテンツの整合」であり、操作部品(つまみ・前後ボタン)は、操作意図に即座に追従させて別に扱う。設計書には、操作から反応までの上限時間と、待ち中の入力の扱いを、受け入れ条件として書く。

## 5. 検証の入力は、受け入れ条件の代表シナリオに合わせる

単体テストは40ms間隔の連続操作だけを見ており、実操作の300〜400ms間隔をすり抜けた。ミューテーションテスト([G-05](G-05-test-effectiveness-verification.md))でも、入力の次元が欠けていれば捕まらない。受け入れ条件に書いた間隔・速度を、そのままテスト入力にする。

## 6. ユーザーに選択肢を出す前に、評価を左右する実測を先に取る

「`Cache-Control: no-store`の緩和」を有力な案として提示し、ユーザーが選んだ後で、単タイルの応答時間を測った(サーバー側キャッシュ未命中0.46〜5.5秒、命中約7ms)。効果が小さいと分かり、選択をやり直すことになった。判断を変えうる数値は、選択肢を提示する前に取る([G-04](G-04-verification-basics.md)、[G-01](G-01-hearing-first-design.md))。
