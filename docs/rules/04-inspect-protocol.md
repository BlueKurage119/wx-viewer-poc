# 検収フェーズ業務標準

対象: 検収担当。気象データの必須制約は[07-wx-data-protocol.md](07-wx-data-protocol.md)、ノウハウ・背景は[docs/rules/advisory/](advisory/README.md)(特に[G-05-test-effectiveness-verification.md](advisory/G-05-test-effectiveness-verification.md)・[C-01-browser-pane-visibility-limit.md](advisory/C-01-browser-pane-visibility-limit.md)・[C-02-ui-verification-backorder.md](advisory/C-02-ui-verification-backorder.md))を参照。上から順に進める構成にしてある。

## 1. 着手確認(必須)

- 対象の設計書(承認済み版)・対象コミット・作業ブランチを確認する。対象が不明・未承認なら統括担当へ返し、着手しない。
- 既存差分(未コミット・未検証の変更)がないか確認し、あれば内容を記録しておく(終了確認で自分の変更と区別するため)。

## 2. 検証計画(必須)

- 設計書の「受け入れ条件」全項目を、確認方法(自動テスト/コマンド/ブラウザ/目視)に対応づける。
- 製造担当の報告(スクリーンショット等)を再利用できる項目と、新たに実行する項目を決める。CI・既存自動テストで担保される項目は、実行結果の有無・成否のみ確認し重ねて詳細を読み込まない。

## 3. 検証実施(必須)

- 受け入れ条件は**1項目ずつ実際に実行して**検証する。**「コードを読んで多分大丈夫」は不合格。** 製造担当の報告を鵜呑みにせず、報告されたred/greenの確認や実測値は自分で再現して追認する。
- 各項目の期待結果・実測結果・使用した具体的なコマンド/操作を記録する。
- ミューテーションテストは対照実験(ダミー改変がSURVIVEDになることの確認)を先に行ってから本番の判定に入る。
- 環境上実行できない項目(実測不能なもの)は「未検証」として残し、隠して合格扱いにしない。
- 検証で加えた改変は必ず復旧する。

## 4. 発見の整理(必須)

- 受け入れ条件の**未達**と、**契約範囲外の発見**を分けて扱う。範囲外の発見で合否を覆さない。
- 発見は必ず次の3分類のいずれかに仕分けて報告する(判断に迷ったら「Issue化して後回し」):
  - 今すぐ直す(通常運用で踏む/次の予定作業で確実に踏む/実在する欠陥かつ修正が数行)
  - Issue化して後回し(将来のコードが誤用したときだけ踏む)
  - 報告不要(到達経路が無い)
- 未達がある場合、自分で修正しない。再現手順と原因の見立て(製造起因か設計起因か)を報告する。

## 5. 判定(必須)

- 合格・不合格・**未検証**を区別する。**未検証を合格に数えない。**
- 全項目が合格(未検証ゼロ)の場合のみ「全項目通過」とする。

## 6. 引き渡し(必須)

- **未達がある場合、PRを作らない。** 未達項目・再現手順・期待値と実測値・原因の見立てを統括担当へ報告する。
- **全項目通過の場合のみ**、`git push -u origin <branch>` の上、`main`をbaseとする通常PR(Draftではない)を作成する。
  - 本文に対応するIssue番号があれば `Closes #<N>` を含める。
  - 本文の構成: 実装したもの/主要な設計判断とその根拠/受け入れ条件の検証結果/後続Issueへの申し送り。
  - 署名フォーマットは[01-dev-workflow-protocol.md](01-dev-workflow-protocol.md)を参照。
  - **マージはしない**(統括担当が判断する)。
- 既にPRが存在する場合(差し戻し後の再検収等)は、`git push`で更新しPRにコメントで追加分を投稿する。新規PRは作らない。

## 7. 終了確認(必須)

- 自分が加えた一時的な変更(検証用の改変・一時ファイル・起動したプロセス)を復旧する。
- 開始時から存在した他者の変更(未コミットの作業等)は保持し、勝手に破棄しない。
- 最後に`git status`を確認し、**自分が加えた変更が残っていない**(着手確認時に記録した状態と一致する)ことを確かめる。開始時から存在した他者の変更はそのまま残っていてよい。

## 収束の判断

統括担当から「完了と見なしてよいか」を問われたら、次を根拠に判断する。

- 受け入れ条件の契約が満たされているか(未検証がないか)
- 発見が収束しているか(直近ラウンドで新規の作り込みミスがゼロなら打ち切りどき)
- 残るリスクがIssue化などで正しく管理されているか
