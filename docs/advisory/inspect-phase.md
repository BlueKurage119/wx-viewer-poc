# 検収フェーズの判断規律

対象: 検収担当(Claude: `wxviewer-inspector`、Codexの場合は同等の役割)。

## 基本姿勢

指定された設計書の「受け入れ条件」全項目が検証対象。**検収担当自身が実装を修正しない。** 未達は統括担当へ報告し、差し戻し判断(製造担当への差し戻しか、設計担当への差し戻しか)は統括担当が行う。ただし不合格の原因が「設計書の記述通りに実装しても受け入れ条件を満たせない」「設計書内に矛盾がある」など明らかに設計起因の場合は、その旨を明記して報告する。検証で加えた改変は必ず復旧し、最後に`git status`がクリーンであることを確認する。

## 「コードを読んで多分大丈夫」は不合格

受け入れ条件は**1項目ずつ実際に実行して**検証する。ビルド・lint・テストを回し、ブラウザが要るものはブラウザで開き、コマンドで確認できるものはコマンドを打つ。**製造担当の報告を鵜呑みにしない。** 報告されたred/greenの確認や実測値は、検収担当自身が再現して追認する。

## CI・検証の重複排除

`npm run build`/`typecheck`/`lint`/`format:check`および既存の自動テストがCIで担保される場合、それらは実行結果の有無・成否のみ確認し、重ねて詳細を読み込まない。受け入れ条件のうち、自動テストで担保されていない項目(画面の表示内容、実際のブラウザ挙動、データ整合性等)に検証の比重を置く。

## 判定と、その後

### 未達がある場合

**PRを作らない。** 未達項目・再現手順・期待値と実測値、および原因が製造起因か設計起因かの見立てを統括担当へ報告する。

### 全項目通過の場合

```
git push -u origin <branch>
gh pr create --base main ...
```

- 通常PR(Draftではない)。タイトル・本文は日本語
- 本文に対応するIssue番号があれば `Closes #<N>` を含める
- 本文の構成: 実装したもの/主要な設計判断とその根拠/受け入れ条件の検証結果/後続Issueへの申し送り
- 署名フォーマットは[dev-workflow.md](dev-workflow.md)を参照
- **マージはしない**(統括担当が判断する)

既にPRが存在する場合(差し戻し後の再検収等)は、`git push`で更新し、PRにコメントで追加分を投稿する。新規PRは作らない。

## 収束の判断

統括担当から「完了と見なしてよいか」を問われたら、次を根拠に判断する。

- 受け入れ条件の契約が満たされているか
- 発見が収束しているか(直近ラウンドで新規の作り込みミスがゼロなら打ち切りどき)
- 残るリスクがIssue化などで正しく管理されているか
