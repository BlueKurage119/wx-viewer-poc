# 開発フロー・ブランチ運用の指導文書

対象: 統括担当(メインセッション)、および各フェーズのサブエージェント。

## Issue単位の4フェーズ運用

Issueごとに、ヒアリング→設計→製造→検収の順で進める。統括担当(ユーザーと直接対話するメインセッション)はフェーズ間の判断・レビュー・マージを担い、自分では実装しない(軽微な修正を除く)。

- **ヒアリング**(統括担当): ユーザーとの対話で確定させた判断事項(設計担当起動時に渡す)
- **設計**(`wxviewer-designer`): `docs/design/issue-N-<slug>.md`(受け入れ条件を含む)。コードは書かない
- **製造**(`wxviewer-builder`): 設計書だけを唯一の仕様として実装。コミット・プッシュまで(PRはしない)
- **検収**(`wxviewer-inspector`): 受け入れ条件を実行して検証し、通過したらpushしてPRを作成する。マージはしない

- サブエージェントはバックグラウンドで動作しユーザーと直接対話できないため、**ヒアリングは統括担当の責務**とする。`docs/issues-draft.md`のIssue項目は実装タスク単位の見出しと参照章番号のみのあっさりした内容であるため、統括担当が`AskUserQuestion`等でユーザーに本質的な論点を確認し、確定した判断をIssue番号とあわせて設計担当へ渡す。
- 設計担当自身は設計中に新たな要ヒアリング事項を見つけても自分で決めず、最終返答で統括担当に投げ返す(→統括担当が追加ヒアリングするか判断)。
- **設計から製造に移行する場合は、一旦ターンを終了し、ユーザーの承認を受けること。**
- 設計書は使い捨てではなく、後続Issueの参照資産として、設計承認後に統括担当(設計担当がClaude以外の場合は、設計担当のモデル名・署名用メールアドレスを添えて)がコミットする。`docs/design/issue-1-project-initialization.md`が書式・粒度の手本。
- AGY等の外部エージェントの起動はユーザーまたは統括担当とし、製造担当が起動可能な場面は、並列しての製造を行う必要がある場合に限る。

## AGY(Antigravity)への製造委託

依頼文には次を含める。CLAUDE.md/AGENTS.mdに既に書かれている内容を重ねて記載する必要はない。

1. 対象の作業ディレクトリ・ブランチ・設計コミット
2. やること・やらないことの境界
3. 自己検証の手順
4. 最終報告のフォーマット

AGYの最終報告には、少なくとも次を含める。

1. 変更ファイル一覧
2. 検証結果(実行したテストと設計書の受け入れ条件への合否は必ず含める)
3. 設計との差異
4. 迷って止めた点
5. 未解決事項

ユーザーがGUIでAGYを起動した場合は、Walkthroughファイルに最終報告を記載する。

## devサーバーの起動・停止作法

**出典:** `mj-stats-viewer`での差し戻し事例(オーナーが検証用に自分でdevサーバーを立てていた回に、エージェントが無関係なサーバーごと一括終了させた)。

- オーナー(ユーザー)は検証やUI確認のために自分でdevサーバーを立てていることがある。ポート番号は固定で覚えず、その都度の状況を確認する。
- エージェントが計測のためにdev/previewサーバーを起動・停止する場合、自分が起動したサーバーだけを、ポート指定で停止する(例: `pkill -f "vite --port <自分のポート>"`)。
- **`pkill -f vite`・`pkill node`のような一括終了は禁止。** ユーザーが作業中のサーバーを黙って落とす事故につながる。
- wx-viewer-pocは`npm run dev`でweb(5174)+api(3001)を固定ポートで起動する(README参照)。この2ポート以外で検証用サーバーを立てる場合も、既存の5174/3001と衝突させない。

## ブランチ・コミット・PR

- ブランチ名: `feature/issue-<番号>-<短い説明>`(例: `feature/issue-2-common-shell`)。Codexが新規ブランチを作る場合もこの規約を優先する
- コミットメッセージ: 種別プレフィックス(`feat`/`fix`/`docs`/`chore`等)+ 日本語要約
- コミットの粒度は、設計完了時に1回、製造時に2〜3回を目安とする(変更の規模に応じて増減)
- PR本文に「Closes #<Issue番号>」を含める
- PR作成時、baseが`main`であることを確認する
- **製造担当の作業はコミット・プッシュまでとし、PRの作成・本文の記述は検収担当が行う**
- 既にPRが存在する場合(差し戻し後の再検収等)は、`git push`で更新しPRにコメントで追加分を投稿する。新規PRは作らない
- マージ後は`git merge-base --is-ancestor <マージコミット> origin/main`が真であることを確かめる

### 署名

エージェントが書いた文章(コミットメッセージ・PR本文・コメント等)には、それを生成したアプリケーション・モデル名を本文中に明記する。`gh`コマンドでの投稿は人間のアカウント名義になるため、本文中の明記で代える。

- **Claude** — コミット末尾: `Co-Authored-By: Claude <model> <noreply@anthropic.com>` / PR本文・コメント末尾: `🤖 Generated with [Claude Code](https://claude.com/claude-code)`
- **Codex** — コミット末尾: `Co-Authored-By: Codex (GPT <model> <推奨モデル名>) <noreply@openai.com>` / PR本文・コメント末尾: `🤖 Generated with Codex`
- **Antigravity(委託先として製造した場合)** — コミット末尾: `Co-Authored-By: Antigravity <gemini-code-assist@users.noreply.github.com>` / PR本文・コメント末尾: 委託元(Claude/Codex)の形式に従う

- Antigravityへ製造を委託した場合のコミット署名は、委託元(Claude/Codex)自身の名義ではなく上表のAntigravity専用名義を使う(作業主体を統計的に追跡するため)。
- 他のエージェントに投稿を代行させる場合は、そのエージェント向けの規約(AGENTS.md等)による。

## コードレビューへの向き合い方

- 外部ツールによるコードレビューは、統括担当がトリアージ(要対応・先送り・無視)を行ってから、本当に必要なものだけを提示すること。年に1回あるかどうかのバグに何時間と何万トークン費やして直しても費用対効果が薄い。
- レビューへの回答・解決済みマークは統括担当が行う。
- 再レビューの要求はユーザーが行う。統括担当は必要により再レビューの提案を行うこと。修正が局所的で、指摘を再現する回帰テストを追加しすべての必須検証が通った場合、再レビュー不要と判断できる。
- **出典: `mj-stats-viewer`での起動条件の実績。** 外部レビュー(Codexの自動PRレビュー等)は、PRを開いたとき・Draftを Readyにしたとき・`@codex review`とコメントしたときに走る。**既存PRへの単なるpushだけでは自動起動しない。** 修正後の再レビューを依頼する場合は、明示的なコメントで起動すること。
