# 防災気象情報機能 基本設計（協議用たたき台）

更新日: 2026-09-13（Issue #139 棚卸し反映）

本書は基本設計の協議記録であり、実装仕様の確定版ではない。「確定」は本セッションのユーザー発言・承認による事項、「設計案」は今後具体化する提案を示す。既存資料中の提案・作業指示を、そのまま今回の承認済み要件とはしない。

## 1. 目的と利用者【確定】

- 地区本部の担当者がPCで適宜確認する。
- 開場中の雨・雪の接近、天候の急変、各種気象警報等を把握し、参加者・スタッフの安全管理に役立てる。
- 将来の統合時には、基本画面から通常の操作で参照するほか、必要に応じて通知を契機として、この画面への遷移と内容確認を促す。
- 今回の実装範囲に基本画面（中央アプリサーバー・他機能と共有する本番の通知UI）への統合は含めない。バックエンドでは、何をどの通知区分で流すかを判定する機能を実装対象とする（詳細は7章）。
- フロント側の通知表現は練習として本番相当で実装する【確定】: 単体のwx-viewer-poc画面内で、ヘッダー点滅ブザー・下部通知領域・確認操作・非常ブザーのスヌーズ等、既存モックアップ（`cmk-gsx-mockup`）と同等の挙動をこの画面専用に実装する。ただし確認／回答操作はフロント側の挙動（ブザー停止等）のみとし、「誰が・いつ確認したか」をサーバー側で追跡・保持する仕組み（受領監視）は今回実装しない【確定】。7.3で設計した通知用データに確認状態フィールドを持たせる場合も、フロントの一時的な状態管理に留め、永続化・監視画面への反映は行わない。本番統合時には、この画面専用実装を中央アプリの共有通知機構に置き換える。
- 実装時の優先順位について【確定】: [本番PoC要件定義書](../../docs/260830_poc-v2-requirements/260830_00_poc-requirements-v2.md)（2026-08-31版）は気象情報機能を【推奨】（【必須】の設備状態変更ワークフロー・情報伝達機能より優先度が低い）と位置づけ、C109が12月開催（冬季）であることから「夏季の降雨を主眼に作り込んだ内容の優先度は下がる」としている。本書の§4（ナウキャスト・キキクル切替）はこの夏季降雨系の機能に該当する。本セッションでは基本設計として§4を維持するが、実装順序ではC109向けの優先度を下げて扱う。§5（警報・注意報系パネル）は警報コード表（大雪・着雪・なだれ・低温・霜等の冬季注意報を含む）に基づくため季節に依存せず、優先度を下げる対象ではない。冬季固有の追加要件（積雪・凍結等の表示要否）は本書の対象外とし、別途検討する。

- 既存モックアップの画面・操作を参考にしつつ、提示画像のレイアウトを基本とする。
- この行までの開発前提は当初の基本設計時点の記録である。Epic A〜D の実装済み契約は本書の追記と [棚卸し台帳](audit-epic-a-d.md) を参照する。
- 成果物は `wx-viewer-poc` に保存する。
- `data-acquisition-report.md` および本書は `wx-viewer-poc/docs` に格納する。

## 3. 画面構成

**H端末・K端末の合成【確定】**

工数削減のため、今回は本番のH端末（防災気象情報の閲覧）とK端末（気象通報取得監視）相当の機能を単一のアプリケーションに合成する。ヘッダー・左ナビレール・最下部の通知領域は全ビュー（3.1〜3.3）で共有する単一の固定シェルとする。端末種別を表すパラメーター（例: `terminalMode: 'H' | 'K'`、名称は実装時に定める）を用意し、H端末相当のモードではナビレールから3.3（気象通報取得監視）を非表示にできるようにする。通知の生成・保持自体は端末種別によらず共通で行い、表示のみモードに応じて絞り込む（8.4参照）。

**端末・会場の実装済み契約（#2・#109・#114・#29）【確定】**

登録済み端末 `hkeagh01` / `kkeagh01` / `htrcph01` / `ktrcph01` の URL から端末台帳を参照し、`terminalMode` と `venueId` を分離して解決する。未知の端末を既定会場へ落とさない。H/K は表示の差であり、気象対象は同じ会場内で共有する。会場選択 UI は追加しない。これらは認証・認可の代替ではない。本番PoCへの移植時の AuthGate 連携は別途設計する。

### 3.1 防災気象情報【確定】

- 上部ヘッダー、左ナビレール、主領域の地図、右側情報パネル、下部操作メニュー、最下部の通知領域を基本とする。
- 右側は詳細への入口だけでなく、その場で内容を読めるパネル群とする。
- 必要な情報が入電した際に表示し、必要な情報を判断しやすい順に配置する。
- 表示領域を超える場合はスクロールで閲覧できる。
- 長文や詳細情報は、詳細ボタンからダイアログで表示できる。
- 対象情報は警報・注意報、警報等時系列、警報級の可能性、アメダス、地域時系列予報、気象防災速報、ナウキャスト、キキクルとする。個別の速報種別・観測要素・キキクル種別の実装範囲は別途確定する。
- 左ナビレールの防災気象情報アイコンには、発表中の最高危険度レベルのバッジを常時表示する【確定】。速報パネル（5.6）は新着時にパネル自体を強調表示しない代わりに、このバッジで気付けるようにする。バッジの色・段階は5.7で確定した警戒レベル配色（黒/紫/赤/黄）に準じる。このバッジは常時表示の状態表示であり、7章の通知区分（警報／問いかけ／非常ブザー）や3.1で確定したヘッダー・下部通知領域の鳴動とは別のものとする。アイコン・バッジの具体的な見た目は画面実装時に定める。

**下部通知領域【確定】**

画面最下部（3.3のようにツールバーを持つビューではツールバーのさらに下）に、全幅の通知領域を固定配置する。ヘッダー・左ナビレールと同格の固定シェル要素とし、地図領域内の時間操作カード（4.3）やカードを除いた表示領域の中心点算出（4.3で確定）には影響しない。上記「H端末・K端末の合成」のとおり、3.1〜3.3の全ビューで共有する単一の領域とする。既存モックアップ（`cmk-gsx-mockup`）の他ビュー（設備一覧・警報一覧等）が個別に持つ「下部通知領域」パターン、および既存モックのナウキャスト（`view-radar`）ビューだけに専用の通知領域がない構成のいずれとも異なり、全ビュー共通の単一領域に一本化する。

表示内容は1章・7.1で確定したとおり、既存モックアップと同等のヘッダー点滅ブザー・確認操作を伴う表現とする。7章の通知判定（警報／問いかけ／非常ブザー）に加え、8.4の装置異常系の警報・問いかけも同じ通知領域・同じ表現の仕組みに流し込む【確定】。両者はデータ上区別しつつ（7.3・8.4参照）、表示先は分けない。具体的な表示項目・レイアウトは実装時に定める。

### 3.2 警報一覧【確定】

ナビレールに、3.1・3.3（気象通報取得監視）と並ぶビューとして「警報一覧」を追加する。既存モックアップの警報一覧ビュー（`view-alert`相当）を踏襲するが、次の点で簡略化する。

- 一覧表示とフィルターのみとし、既存モックにある承認／差戻ボタン・行ごとの確認操作は設けない。気象警報・注意報は地区本部の承認を要する情報ではないため。
- ブザーの停止（確認）は3.1で確定したヘッダークリック／F8キー等の全体操作で行い、この一覧内には個別の確認ボタンを置かない。
- 一覧の行は7.3で設計した通知用データ（notificationId、category、sourceType、occurredAt、summary等）を基にする。列構成・フィルター項目（通知区分、対象情報種別、期間等）の詳細は実装時に定める。
- 履歴の集約先は監視画面（3.3・8章）としており、この一覧は現行・直近の通知の確認を主目的とする。両者の役割分担（保持期間・件数上限等）は実装時に具体化する。

### 3.3 気象通報取得監視（仮称）

取得処理の監視用画面を基本設計の対象として扱う。ユーザーから必要性の検討が提示されており、詳細な機能範囲は未確定。

- 想定利用者【確定】: 地区本部の一般運用担当者ではなく、デバッグ用途および開発サイドの監視・トラブルシューティング用とする。この位置づけを踏まえ、8章の情報粒度・専門用語（電文種別コード等）は運用担当者向けの平易さより開発者向けの詳細さを優先してよい。
- 今回はナビレールで切り替える構成とする。H端末相当モードではナビレールからこのビューを非表示にできる（上記「H端末・K端末の合成」参照）。
- 本番環境ではK端末（システム監視端末・仮称）の機能の一部として提供する想定。今回はH端末相当の機能と合成した単一アプリとして実装する。
- 設計案: 情報種別ごとの取得処理の稼働状態、最終成功時刻、遅延、エラー、処理待ちを表示する。
- 監視画面と負荷対策は別に設計する。画面を設けること自体は取得負荷の軽減にはならない。
- 再取得などの操作権限・操作機能は未確定。

### 3.4 訓練通知【確定】

ナビレールに、3.3（気象通報取得監視）配下の機能として「訓練通知」を追加する。目的は、本物の気象警報の発生を待たずに通知パイプライン（7章の判定〜3.1のヘッダーブザー・下部通知領域〜3.2の警報一覧〜8章の通知出力履歴）を通しで検証・訓練できるようにすることとする。本番PoC要件定義書4.3.2の「保守・訓練モード」に対応する機能候補として位置づける。

- 想定利用者は3.3と同じくデバッグ・開発サイド用とする。H端末相当モードではナビレールから非表示にする（3の「H端末・K端末の合成」参照）。
- **注入要求**: あらかじめ用意したサンプル電文（取得方法レポートで確認済みの提供サンプル。5.6・7.4で参照した`jmaxml_20260723_Samples`等）を選択し、実際に受信したものとして通常の取得・検証・正規化・通知判定パイプラインへ投入する。パイプラインを経由させることで、7章の状態変化判定（新規・強化・緩和・解除等）や通知区分の判定を実データと同じ経路で検証できる。
- **抹消要求**: 注入した訓練データを取り消す。電文の取消（InfoType=取消）を模した合成電文を同じパイプラインへ投入する方式を基本とし、パイプラインを経由しない直接削除は状態不整合の原因になるため用いない。
- **本番データとの分離【確定】**: 注入した電文・生成された通知・履歴には、訓練由来であることを示すフラグ（例: `isTraining`）を付与する。このフラグは6.2の共通メタ情報・7.3の通知用データ・8.1の履歴に一貫して伝播させる。
  - 3.1の下部通知領域・3.2の警報一覧・5章の各パネルには、訓練データであることが分かる表示（例: 「訓練」バッジ）を付けたうえで表示する。実発表と誤認させない。
  - 8.1で確定した「履歴は明示削除まで保持」の例外として、訓練データは通常操作（抹消要求）で削除できることとする。
  - 9章の受入条件検証は、訓練データを対象に含めない（`isTraining`で除外して判定する）。
- サンプル電文のカタログ化（一覧・選択UI）、注入操作の権限、同時に複数の訓練データを扱う場合の管理方法は実装時に具体化する。

## 4. 地図の切り替え

### 4.1 基本動作【確定】

同じ地図領域で「ナウキャスト」と「キキクル」を切り替えて表示する。

- 初期表示は雨雲ナウキャストとする。
- 操作メニューから、必要に応じて表示レイヤーを切り替えられるようにする。

### 4.2 操作・時間管理【設計案】

- 操作メニューに主表示の選択を配置する。ナウキャストは雨雲表示を前提とし、雷・竜巻等の追加は未確定。
- キキクル選択時は種別選択を表示する。今回採用する種別は大雨・浸水・土砂の3種とする【確定】。洪水キキクルは複合ベクトル描画が取得方法レポートで未検証（0バイトタイル）のため今回は対象外とする。
- 切り替え時は地図中心・ズームを保持する。
- 地図の凡例、単位、表示対象時刻、操作可能な時刻一覧は、選択した情報に合わせて切り替える。
- ナウキャストとキキクルの時刻一覧は個別に管理する。切り替え先に存在しない時刻や固定のコマ数を仮定しない。
- 切り替え時は再生を停止し、切り替え先の最新の利用可能時刻を表示する案とする。時刻の引き継ぎや選択状態の保存は要協議。
- 地図の切り替え・移動では右側パネルの対象地域を変更しない（5.1の確定事項）。
- 一方の情報取得に失敗しても、もう一方の閲覧を妨げない。失敗時は表示対象を明記し、別の情報へ黙って切り替えない。

### 4.3 地図・操作メニューの具体案【設計案・未確定】

#### 初期表示・背景

- 端末台帳の会場を中心に、東京23区・東京湾北部・周辺の千葉／神奈川方面の雨雲を見渡せる画角とする。
- 中心点の算出方法【確定】: 地図領域のうち、右側情報パネルの幅と下部の時間操作カードの高さを差し引いた矩形（＝カードに隠れず見える範囲）を求め、その矩形の中心に端末の会場が来るように地図中心をずらす。ヘッダー・左ナビレールは地図の外側にある固定要素のため除外の対象にしない。レイヤー選択ボタン・ズームボタン等、地図領域内に浮かぶ他のボタン・カードの面積は今回考慮しない。数値のズームはこの矩形の寸法で調整する。
- 「会場へ戻る」もこの中心点・ズームに戻す。画面幅・右パネル幅・下部カード高さが変化しうる場合、中心点の再計算方法は画面実装時に定める。
- 背景は地名と行政界が読める淡色地図を第一案とする。配信元・利用条件は採用時に確認する。
- 端末の会場に常設マーカーを置き、その市町村境界を細線で表示する。広域表示では境界による視認性低下を避ける。
- PCではドラッグ移動、ホイールおよび＋／－ボタンで拡大縮小。「会場へ戻る」で初期中心・画角に戻す。時刻とレイヤーは変更しない。

#### レイヤー

- 気象レイヤーは単一選択式とし、初期は雨雲ナウキャスト。
- キキクルは大雨・浸水・土砂の3種を操作メニューにまとめる【確定】。大雨キキクルは公式仕様上、浸水・洪水の危険度を統合したPNGであり、単一レイヤーで取得・描画済みの検証がある。キキクルへの初回切り替え時は大雨（統合表示）を初期選択とし、以降は選択した種別を画面内で保持する【確定】。
- 洪水キキクルは、PBF流路・指定河川GeoJSON等の複合描画が取得方法レポートで未検証（会場周辺タイルが0バイト）のため、今回の採用種別に含めない【確定】。大雨キキクルの統合表示が浸水・洪水双方の概況を代替する。将来、洪水の複合描画が検証できた場合に候補として再検討する。
- 雷・竜巻ナウキャスト、気象レイヤーの同時重ね合わせは初期版に含めない案とする。
- レイヤー切り替え時は中心・ズームを維持し、再生停止、切り替え先の最新時刻を選択する。

#### 操作メニュー・常時表示

- 操作領域は横長のツールバーではなく、動画プレーヤーのようなコンパクトなカード形式とする【確定】。レイヤー切り替え・ズーム・初期位置ボタンはカード外に独立配置できる方針とする。
- 配置案: 右側情報パネルを除いた地図領域の下部中央に、時間操作カードを常設する。上段に選択レイヤー名と表示日時・状態、中段に時刻スライダー、下段に前コマ／再生・停止／次コマと「最新へ」を配置する。具体的な幅は画面設計時に調整し、地図幅いっぱいには広げない。
- 配置案: 地図領域の左上にレイヤー選択ボタンを置き、選択メニューを開く。レイヤーの濃さと凡例の開閉もこのメニューにまとめ、時間操作カードには入れない。
- 配置案: 地図領域の左下に＋／－と「会場へ戻る」（初期位置・画角）ボタンを縦配置する。ナビレールとは別の操作群として余白を設ける。
- 先の横長時間操作バーと汎用の「操作メニュー」開閉ボタンの案は、このカードと独立ボタンの構成に置き換える。
- 選択レイヤー名、表示対象日時、実況／予測の区別（データに応じた表現）、最新追従中か過去等を選択中かを常時表示する。
- キキクルの時刻は危険度判定の基準時刻として示し、予測を含む危険度を単なる実況と表現しない。
- 凡例は初期表示し、閉じた場合も再表示ボタンを残す。出典は常時表示する。
- 各操作・マーカー・出典は右側情報パネルや凡例の下に隠れない配置とする。

#### 時間範囲・更新

- 雨雲は過去60分〜未来60分を表示窓の上限とし、実際に取得できるコマのみを使用する。
- キキクルは最新を基本とし、取得可能な過去3時間を表示窓とする案。選択種別の提供時刻を使い、未来時刻の選択は設けない。
- スライダーは利用可能なコマ単位とし、欠けたコマを生成・補間しない。表示対象日時で時間の欠けが分かるようにする。
- 再生は選択レイヤーの利用可能コマを古い順に約1秒間隔で繰り返す。再生中のコマ一覧は固定し、新規コマは再生停止後に反映する。
- 最新追従中のみ、新しいデータの取得に合わせて表示時刻を進める。手動で時刻を選択したら追従を止め、最新へ戻すまで選択時刻を保持する。
- 最新追従中でも地図中心・ズームは変更しない。「最新へ」は時刻のみ、「会場へ戻る」は画角のみを変更する。
- 選択中の時刻が提供範囲外になった場合、状態を明示して「最新へ」を案内する。別時刻へ無表示で置き換えない。
- タイル未取得部分は状態を明示し、降水・危険度なしと誤認させない。取得失敗で以前の画像を残す場合は、その画像の時刻と前回値表示を明示する。

これらの時間範囲はアプリの表示窓の案であり、提供元の全期間や可用性の保証ではない。具体的な取得可否・表示位置は実装時の検証対象とする。

警報・注意報の解除は通知区分「警報」で知らせ、解除された情報は現況パネルから外す。「解除」を一定時間残す表示は設けない。履歴は監視画面で閲覧する。保存期間は8.1の履歴保持方針（明示的に削除するまで保持）に従う。

### 5.5 有効期限が明確でない速報

対象は気象防災速報（線状降水帯発生）、同（線状降水帯直前予測）、同（記録的短時間大雨）。

**表示期間【確定】:** 3種類とも発表後3時間の固定表示とする。利用者が表示期間を変更する設定は設けない。これは閲覧上の整理期間であり、気象上の有効期限・危険の終了時刻ではない。

以下は表示・履歴処理の設計案とする。

- パネルを「最近の速報」として扱う。
- 発表時刻と経過時間を明示する。期間経過では解除通知を生成しない。履歴は監視画面で参照し、保持期間は8.1の履歴保持方針（明示的に削除するまで保持）に従う。
- 再取得・訂正の受信時刻だけで表示期間を延長しない。新しい発表と同じ情報の訂正を区別する。
- この3種類のパネル表示終了は発表後3時間で判定し、公式地図の表示終了状態には連動させない。補助JSONを別用途で使用する場合も、地図の表示期限とXML速報の有効期限は同一視しない。
- 2026-09-07に気象庁の線状降水帯解説を検索確認。直前予測の2〜3時間前という説明は、速報の表示期限を定めたものではない。公式地図の説明テキストは今回Webツールで取得できず、固定表示時間の公式根拠は確認していない。

参照: [気象庁・線状降水帯に関する情報](https://www.jma.go.jp/jma/kishou/know/bosai/kishojoho_senjoukousuitai.html)

### 5.6 速報パネルの内容【確定】

長い本文や補足情報が別に存在することを前提にしない。短い速報文はパネルで全文を読めるようにし、要約と本文に機械的に分割しない。

- 線状降水帯の速報も含め、標題、対象区域、発表時刻・経過時間、速報文全文を表示する。発表官署は補助表示とする。
- XMLは電文種別に応じて表示文の所在を定義する。Bodyに自由文がなくても情報欠落と判断しない。
- 構造化された観測値が速報文と重複する場合、同じ値を別欄に繰り返すことを必須にしない。
- 詳細ボタンは追加で見せる情報がある場合に限り、短い速報文を再表示するためだけには設けない。履歴は監視画面に集約する。
- 対象電文【確定】: VPBS50（線状降水帯発生・直前予測、記録的短時間大雨情報）に加え、竜巻関連（VPHW50／51、気象防災速報（竜巻注意情報・竜巻目撃情報）として5.12の方針で扱う）も今回の実装対象に含める。竜巻はVPBS50と異なる電文形式のため、別途の取得・正規化処理を要する。VPBS51（潮位速報）はJMA側が当面提供見送りとしているため対象外とする。短時間大雪（VPBS50の一種）は5.12ですでに対象外。
- 複数件同時発表時の並び順【確定】: 発表時刻の新しい順とする。種別固定順は採用しない。
- 新着の強調表示【確定】: パネル自体の新着強調は行わない。通知区分（7章）による問いかけ・非常ブザー等で気付ける設計とし、加えて3.1で確定したナビレールの危険度バッジで発表中の状態を常時示す。

確認したユーザー提示サンプル:

- `19_01_01_091210_VPHW50_kana.txt`: 旧竜巻注意情報。対象地域、注意を促す文章、明示された有効期限がある。このサンプルを根拠に竜巻情報へ5.5の3時間ルールを適用しない。

### 5.7 警報・注意報パネルの内容【設計案・未確定】

目的は江東区に現在発表されている警報・注意報の把握とする。ユーザー提示のNERV防災スクリーンショットを参考に、見出し「気象警報・注意報」の下に発表時刻と危険度カラーのバッジを配置する。従前の1情報1行の案を置き換える。以下の細部は設計案とする。

| 場所 | 表示項目 |
|---|---|
| パネル見出し | 気象警報・注意報。対象「江東区」は補助ラベルで明示 |
| 見出し直下 | 対象地域の現況に反映した発表の時刻。「○月○日○時○分 発表」と表示 |
| バッジ群 | 危険度カラーと文字でレベル・現象を表示。警戒レベルを冠さない情報に独自のレベルを付与しない |
| 更新の補助表示 | 新規・強化・緩和の変化があった行の表示。強調の保持時間は未確定 |
| パネル下部 | 取得状態の扱いは5.12に従う |
| 詳細（情報がある場合） | 当該情報の付加事項・補足、発表官署。将来の量的予想は原則として時系列パネルで扱う |

- バッジは横に並べ、パネル幅を超えたら次の行へ折り返す。横スクロールは設けない。バッジの短縮表記は「レベル3大雨警報」「洪水警報」「雷注意報」のように、警戒レベルを持つ種別は正式名称に準じた「レベルN＋正式名称」、レベルを冠さない種別は正式名称のみとする【確定】。
- 表示は、個々の警報・注意報の初回発表時刻を並べるのではなく、新しい発表に含まれる「発表・継続・解除」等を反映した対象地域の現況を一組のバッジ群として示す。見出し下の時刻は、その現況に反映した発表の時刻であり、各バッジの新規発表時刻を意味しない。
- ユーザー提示例: 大雨警報の発表後、新しい情報で「大雨警報継続・土砂災害注意報発表」となった場合、新しい発表時刻の下に両方のバッジを表示する。大雨警報を新規発表として扱わず、新着の扱いは土砂災害注意報に適用する。
- 個々の初回発表時刻を詳細に必須表示する従前の案は取り下げる。取得時刻は発表時刻と区別する。
- この表示方針と、取得電文が含む現象・地域の範囲は分けて設計する。受信した一電文に全現象が含まれると仮定して未掲載の警報を削除せず、取得方法レポートに従って各電文の適用範囲と継続・解除を処理し、現況を構成する。
- 特別警報、危険警報、警報、注意報の順にまとめ、同じ段階内は現象ごとの固定順とする【確定】。通知区分の名称を気象情報の名称の代わりに表示しない。
- 色は気象庁公式の警戒レベル配色（レベル5・特別警報=黒、レベル4・危険警報=紫、レベル3・警報=赤、レベル2・注意報=黄。レベルを冠さない警報・注意報も同じ段階の色を使う）を基調とする【確定・出典: [防災気象情報と警戒レベルとの対応について｜気象庁](https://www.jma.go.jp/jma/kishou/know/bosai/alertlevel.html)】。具体的な配色値（コントラスト調整、ダークモード対応等）は画面実装時に別途調整する【設計案・未確定】。色は補助とし、文字でも種別・段階が分かるようにする。
- **レベル5・特別警報のダークモード表現【確定】**: 共通シェルがダーク固定（8.4参照）のため、純粋な黒（背景と同化する）ではなく、黒と紫の中間色を背景、紫を縁取り、黄を文字色とする組み合わせで表現する。「黒」という配色系統自体は変更せず、視認性確保のための画面実装値の確定として扱う。具体的なHEX値・トークン化はIssue単位の設計書（`docs/design/`）に委ねる。

### 5.8 警報等時系列パネル【確定】

- 対象地域は江東区とする。
- 発表時刻の下に、縦軸を現象、横軸を時間帯とする危険度の色分け表を表示する。
- 雨量・風などの量的予想は詳細ボタンからダイアログで確認する。

以下は設計案・未確定事項とする。

- 色に加えて文字や凡例で危険度を判別できるようにする。欠測・未取得を危険度の低い状態として表示しない。
- 時間帯は提供データの時間定義に従う。現在発表中の警報と予測上の危険度を混同しない。
- 詳細では量的予想の単位、対象時間、陸上／海上等の区分を保持する。
- 対象の現象【確定】: 固定リストを仮定せず、電文（VPWP50）に含まれる現象だけを表示する。行の順序は5.7で確定した段階内の固定順（暴風雪→大雨→洪水→暴風→大雪→波浪→高潮→土砂災害）を流用する。
- 表示時間範囲・横幅を超える場合の扱いは5.13の一般方針（初期位置は現在を含む時間帯、全期間を横スクロールで閲覧可能、固定コマ数で切り捨てない）に従う。

### 5.9 警報級の可能性パネル【確定】

- 対象地域は東京地方とする。
- 発表時刻の下に、縦軸を現象、横軸を時間帯・日付とする表を表示する。
- 「高」「中」など提供された値を文字と色で表示する。
- 同じパネル内で「明後日まで」と「明々後日以降」を分け、提供データの時間区切りに合わせて表示する。

以下は設計案・未確定事項とする。

- 2つの情報の発表時刻が異なる場合は、それぞれの表に対応する発表時刻を明示する。
- 「なし」「値なし」、未取得・取得不能を区別する【確定】。独自に「低確率」や数値確率へ置き換えない。表示は次のとおりとする。
  - 「なし」（JMA提供の実際の予測値。警報級でない見込み）: セルに「－」を表示する。
  - 「値なし」（`condition="値なし"`。その区間・現象が構造上提供されない）: セルに何も表示しない（空白）。「なし」の「－」とは区別する。
  - 自システムの取得不能・未取得: 5.12の取得状態表示ルールに従い、表自体を非表示にする（セル単位の記号にしない）。
- パネル内は前半（明後日まで）・後半（明々後日以降）を別表のまま表示する【確定】。現象分類が異なる場合に無理に同一行へ統合しない。詳細ダイアログでは、共通する現象を1つの表に結合して表示する【確定】。日付境界と重複期間の処理は取得方法レポートに従う。
- 幅を超える場合の扱いは5.13の一般方針（横スクロール、全期間閲覧可能）に従う。凡例の具体的表現（「高」「中」「－」の色・文言）は実装時に定める。

### 5.10 アメダスパネル【確定】

- 観測所名「江戸川臨海」と観測時刻を明示する。会場地点の観測値として表示しない。
- パネルには気温、湿度、風向、風速、直近1時間の降水量を表示する。
- 推移グラフやその他の観測項目は詳細ダイアログにまとめる。詳細に採用する項目・期間は別途決める。

以下は設計案・未確定事項とする。

- 気温は℃、湿度は%、風速はm/s、直近1時間の降水量はmmで表示し、風向は方位名で示す。
- 降水量には集計期間が1時間であることを明記する。表示する各値は対応する観測時刻にそろえ、欠測項目だけ過去値を無表示で混ぜない。
- 欠測、観測非対応、通信異常を区別し、欠測等を0として表示しない【確定】。
- 品質注記（JMAのAQCフラグが1／4等）の扱い【確定】: 正式な名称・業務上の判定基準が未確認のため、初期版ではフラグによる区別をせず通常の観測値として表示する。欠測（値なし）・観測非対応（要素自体を提供しない）・通信異常（取得失敗）の3区分とは別軸であり、これらの区別は今回も維持する。品質フラグの意味が確認でき次第、表示要否を再検討する。
- **AQCフラグ5（休止中）・6（×）の例外扱い【確定・Issue #19協議で追加】**: 公式画面の表示規約（取得方法レポート§5のAQC表）でAQC=5は「休止中」、AQC=6は「×」を示す記号表示に対応する。この2値は上記「AQCで区別しない」の対象から除外し、値が数値であっても欠測相当として扱う（通常の観測値として表示しない）。AQC=1／4等その他の値は引き続き区別せず通常の観測値として表示する。実観測でAQC=5／6かつ数値が入る電文は未確認であり、本追記は挙動を先回りして定めたものである。

### 5.11 地域時系列予報パネル

### 5.12 対象範囲・表示状態・履歴（追加協議）

**取得状態の表示案【未確定】**

| パネル | パネル内の表 | 詳細ダイアログ |

| 警報等時系列 | 現象名を左列固定、提供された今後の時間帯を横並び。初期位置は現在を含む時間帯。危険度を色・文字で表示 | 同じ現象・時間帯に対応する雨量・風等の量的予想を表形式で表示。単位と対象区分を明記 |

### 6.1 保存方式【確定】

ローカル検証では組み込みDB（SQLite等）をファイル1つで保存先とする。既存モックアップ（`cmk-gsx-mockup/server.js`）はインメモリ実装でDB非依存だが、8.1で確定した「履歴は明示削除まで保持」「クラッシュ・再起動で履歴・前回正常値を失わない」を満たすため、今回はディスク永続化を採用する。外部DBサービス（Cloud SQL等）は導入しない。将来的にFirebase等へ置き換える構想があるが、今回の基本設計では確定事項としない。実装は `node:sqlite` と forward-only の migration `0001`〜`0020` を使用する。実行DDLを正とし、Issue #6 のテーブル定義書は当時の記録として扱う。情報別snapshot/明細、取得試行、受信原文、会場別採用、検知通知履歴、操作履歴、端末session、起動出力権と起動応答監査を分離する。表示窓は保存期限ではなく、自動削除はない。タイル本体は専用キャッシュに保存し、DBにはメタ情報を持つ。ファイル保存とDBは単一transactionではなく、原子的rename・参照外清掃・再取得で整合を補う。

### 6.2 API境界【確定】

内部APIは取得方法レポートの提案どおり、情報種別単位（現況警報／警報等時系列／早期注意／地域時系列／レーダー／キキクル／アメダス／気象防災速報）でRESTエンドポイントを分ける。各エンドポイントは共通メタ情報として source、issuedAt、validAt／validFrom／validTo、fetchedAt、lastSuccessAt、availability（available／stale／unavailable）、sourceVersion を持つ。レーダー・キキクルのタイル配信は画像エンドポイントとして別に設ける。7章の通知用データ（notificationId等、7.3参照）と監視画面向けAPI（8章の稼働状態・履歴）は、この情報種別単位のAPIとは別系統として設ける。情報別APIは E1〜E8 の設計時に契約を承認する。DB行型・内部ファイルpathをそのままHTTP公開せず、会場・`controlStatus` の明示検証、null、正常空、各時刻の意味、区域/時間参照を維持する。起動通知 `POST /api/notifications/startup` のみD5で公開済みであり、情報別REST・通常通知差分・監視・取得制御のAPIは後続である。

### 6.3 異常時の状態遷移（availability）【確定】

各情報種別のavailabilityは次のとおり定義する。

| 状態 | 意味 |
|---|---|
| available | 利用可能な正常値があり、その情報源の鮮度・取得結果から利用可能と評価される |
| stale | 前回正常値を保持するが、取得失敗・鮮度低下がある。保持値と鮮度低下をAPIで表現し、画面の具体策は5.12で判断する |
| unavailable | 有効な値を一度も取得できていない（初期取得中・初期取得失敗を含む）、または保持データ自体が存在しない |

取得元の健全性（8.1）と情報の `availability` は別軸である。D7の状態をそのまま各snapshotの状態に変換しない。XML通常フィード・画像索引の鮮度初期値は独立した固定300秒で、夜間も時間経過を評価する。画像結果と索引 `availability` も別に返し、索引がstaleでも保存索引の有効frameに対する画像GETを鮮度だけで抑止しない。夜間等の画像上流取得許可は別判定とし、検証済みキャッシュは停止中も読める（#24）。

### 6.4 サーバー構成【確定】

- 防災気象情報サーバーは、既存の中央アプリサーバー（`cmk-gsx-mockup`。H/M端末の設備管理APIを持つ既存Expressプロセス）とは別プロセスとして、`wx-viewer-poc`単独の実験として構築する。既存`weather-api.js`への統合は行わない。
- 将来の本番PoCで中央アプリサーバーと接続できるよう、6.2のAPI境界（情報種別単位のREST、共通メタ情報）は疎結合を保つ。同一プロセスへ統合するか、別サービスとして連携させるかは本工程では判断せず、次工程以降の検討事項とする。

### 6.5 将来のデータ配信方式との関係【確定】

気象情報の配信方式は、少なくとも3段階の変化を見込む。

1. **今回（wx-viewer-poc、基本設計フェーズ）**: 6.1で確定したとおり、SQLite等の組み込みDB＋サーバー経由のREST APIを前提とする。7.7（起動時出力のpull方式）・8.3（気象画面15秒・監視画面5秒周期のポーリング）はこの前提に基づく。
2. **本番PoC（Cloud Run＋Firestore）**: 警備システムのメイン部分はクライアントがFirestoreを直接購読する構成を想定している。気象情報についても、公開パネル・地図（クライアントの表示更新）はFirestoreの直接購読に合わせ、監視画面・通知出力履歴（管理系操作を伴う情報）はREST経由を継続する【確定・本セッションでの方針決定】。取得・正規化・通知判定・監視機能は引き続きサーバー（Cloud Run上のNode.js）が担い、その結果をFirestoreへ書き込む。
3. **将来（有志運用サーバーへの移行時）**: 本番PoC要件定義書7.5（将来の移行性）が示すとおり、Cloud Run・Firestoreという管理サービス依存を解消し、自前のSQLデータベース＋WebSocketによるpush配信へ移行する可能性がある。

この見通しを踏まえ、6.1・6.2の設計は情報種別単位を「ドキュメント／レコード単位」として見立てやすい形にしておく【確定】。共通メタ情報（source、issuedAt、availability等）をどの段階でも共通のスキーマとして扱えるようにし、配信方式（REST polling／Firestoreリスナー／自前WebSocket）の差し替えがデータモデルの再設計を伴わずに行えることを目指す。段階2・3への移行時期・詳細設計は次工程以降の検討事項とする。

| 通知区分 | 意味 | フロント側の表現案（今回wx-viewer-poc画面専用として実装） |
|---|---|---|
| 警報（新設） | 通知するが、利用者に操作を求めない | ピンポーン、またはピロン・ピロン… |

### 7.3 バックエンド設計の論点【設計案】

- 対象の気象情報・状態変化と、通知不要／警報／問いかけ／非常ブザーの対応表を作る。情報種別の割り当て案は7.4に記載し、状態変化による通知条件は別に定義する。
- 新規発表、継続、強化、解除、訂正、取消、初期取得・復旧での取り込みを区別し、同一情報の再取得で通知を重複生成しない。
- 通知用情報には識別子、原因となる気象情報とその版、対象地域、発生時刻、通知区分、確認／回答の要否、要約、関連情報への参照を保持する案とする。
- 通知の保存・配信方法、再配信、確認状態を管理する責務は別途定義する。バックエンドの通知判定を実装対象とすることだけで、確認管理まで今回の対象と確定したことにはしない。
- 通知音・ヘッダーはH系で今回の画面専用として接続する。A2のfixture試作は実通知との接続完了を意味しない。

**通知用データの実装済み契約（#25・#103・#28・#31・#32）【確定】**

| 層 | 内容 |
|---|---|
| 通知事実 `Notification` | `notificationId`、`category`、`sourceType`、`sourceVersion`、非空配列 `targets`、`occurredAt`、`detectedAt`、`changeType`、`relatedRefs`、`isTraining`、`origin`、`detectionContext` |
| 原因・検知文脈 | `origin: weather / system` と `detectionContext: normal / initial` は独立。`initial` は端末起動ではなくサーバー検知の文脈 |
| 表示定義 | shared の型付き静的レジストリから、定義ID・版・区分・対象・詳細を検証し、タイトル/対象/詳細を解決。未知IDや不整合は低い区分にfallbackしない |
| 出力snapshot | 解決済み文面、確認要否・操作等。`ackRequired` は確認済みではない。B4には確定した出力内容を保存し、後日定義を変えても過去履歴を書き換えない |

同じ情報種別・状態変化・区分・操作条件の対象群だけをまとめる。D4の警報処理は市町村・現象キーごとの通知で、採用履歴の `venue_id` を通知IDへ流用しない。D7は取得元ごとに生成する。注意報発表定義は `warning / question`、警報発表定義は `question / emergency` を受け、区分から操作を解決する。定義文面の意味を変更する場合は版を上げる。通常通知APIで過去の表示3要素をどう配信するかはE9の未決事項であり、保存summaryを機械的に再解析しない。

### 7.4 情報種別と通知区分の対応【ユーザー検討案】

以下はユーザー提示の業務上の割り当て案であり、気象庁の情報体系を本書で新たに検証した結果ではない。通知対象の地域は5.1に従う。

### 7.5 強化・緩和・解除時の通知【確定】

- 強化・緩和: 変更後の気象情報に対応する通知区分で通知する。緩和を一律に通知区分「警報」とはしない。
- 解除: 通知区分「警報」で知らせる。
- 通知区分が変更前後で同じでも、強化・緩和の状態変化があれば通知対象とする。

例: レベル4危険警報からレベル3警報への緩和は「問いかけ」、レベル3警報からレベル2注意報への緩和も「問いかけ」、解除は「警報」となる（7.4の対応案に基づく）。

### 7.6 その他の状態変化【確定・#28の実装範囲】

- 新規発表: 7.4の対応表に従って通知する。
- 同一内容の再取得・単なる継続: 新たな通知を生成しない。
- 訂正・取消は通常の発表と同じ受信・処理・通知経路で扱う【確定】。重要変更の判定を再通知の必須条件とする案は取り下げる。同じ版の再取得は重複処理しない。
- 訂正・取消の原文の区分は保持する。通常経路で処理することは取消済み内容を現行の警報として有効化する意味ではない。警報取消は解除相当の `warning`・確認不要とする。取消本文Kindは実構造未確認のため解釈せず、取消ストリームと基準時刻を使い集約側の古い値へのfallbackを防ぐ。訂正は変化した現象を通常ルール、継続した現象は寄与元 `sourceTelegram` が訂正電文と一致する場合に通知する。判定不能は当該1件だけskipし他の現況処理を止めない。
- 初期取得・復旧【確定】: 初期取得・復旧時に検知した「すでに発表中」の情報も、新規発見として通常の状態変化ルール（7.4の対応表）どおりに通知を生成する。履歴の一括通知防止のための特別な抑制は設けない。サーバー再起動のたびに現況が再通知されうることを許容する。
- 「初期取得済み」の判定はプロセス起動単位でリセットする【確定】。永続化せず、プロセスを再起動するたびに初期取得として扱う。

### 7.7 起動時の通知出力【確定・#29】

- 端末起動時: 問いかけ・非常ブザーに該当する現行情報を必ず出力する。
- 通知区分「警報」の起動時出力: サーバー起動後の初回のみとし、端末の追加起動では再出力しない。
- 上記は起動時の再提示ルールであり、通常運用中の新規発表・強化・緩和・解除・訂正・取消による通知を抑止するものではない。

**方式【確定】**

起動時出力はサーバーから端末へのpushではなく、端末がサーバーへ問い合わせるpull方式とする。サーバーは常に最新の現況（発表中の警報等・表示期間内の速報・通知出力履歴）を保持するだけでよく、端末が未接続の間の受け渡し・保持期間という論点は生じない。端末は起動時に現況取得APIを呼び出し、以後は通常の更新確認（8.3の気象画面15秒周期等）に合流する。

`POST /api/notifications/startup` は実装済みである。要求は端末 ID とセッション ID を受け、サーバー側の端末台帳から会場を解決する。初期取得・会場別初期評価が完了していない間は `202` を返し、完了後は起動時通知を返す。通常ポーリングの差分取得、cursor、通信失敗時の再試行、共通通知 store への合流は後続タスクで扱う。

実装済みの出力単位は次のとおりである。

- 要求は登録端末IDとUUID v4のsession IDだけを受け、会場/モードをサーバーの台帳で解決する。ブラウザはsessionStorageとメモリ縮退でIDを保持する。同一タブreloadは継続、独立新規タブは別ID。複製タブ・復元時に同じIDとなる挙動は許容している。
- 初期4フィード取得完了と会場のD4初期評価が揃うまで202。正常な現況なしは200の空結果である。個別電文取得の全成功を保証するreadinessではない。初期評価失敗は後続周期で再試行する。
- `warning` 出力権は **サーバー起動世代×会場** ごとに一度だけ、SQLiteのimmediate transactionで消費する。応答喪失時も再送しない at-most-once を採る。同一sessionの継続問い合わせは新規起動扱いしない。
- `question / emergency` は有効な問い合わせごとに現在情報から再構成する。解除・取消・期限終了を過去履歴から再生しない。
- 現在の対象は本番・訓練の警報・注意報現況（試験報testは除外）と表示期間内のVPBS50の3種で、`origin` は weather のみ。system・竜巻の起動統合と速報の通常通知生成は D10 #145 で対象の採否から設計する。VPHW収集そのものはC8で完了している。
- 起動応答は専用監査表と `outputId` で記録し、B4の検知通知 `notificationId` と区別する。実鳴動や受領完了の記録ではない。
- 通常差分/cursor、202・通信失敗再試行、共通通知storeへの合流は E9 #41。確認・スヌーズ等のUIはH系で、受領監視や指令伝達は追加しない。

D4の初期通知は保存済み現況の再構築・再評価で生成され、端末出力権とは別である。試験報 `test` は通知を生成せず、訓練 `training` は `isTraining` を伝播する。C3適用と通知保存は別transaction、D7は保存失敗後も状態を進めるため、障害時の通知再送保証はない。この運用上の採否はL3に残す。

### 8.1 監視画面の役割

**履歴の入口・表示構成【確定・Issue #75/#76会話】**

**履歴の保持方針【確定】**

受信履歴・通知出力履歴・操作記録・解除済み警報等の履歴は、自動削除・自動ローテーションを行わず、明示的に削除するまで保持する。サーバーはコミケット開催期間に合わせて稼働させる運用のため、期間ベースの自動失効は設けない。手動削除の操作・権限は本工程では定義しない。

**ツールバーと操作手順【確定】**

```text
[取得開始][取得停止]　　[強制更新]　　[受信履歴]　[出力履歴]　　　　[ 送信 ]
```

- 取得開始・取得停止・強制更新は、ボタン選択だけでは実行しない。「送信」を押して初めてサーバーへ実行要求を送る。
- 「受信履歴」は受信履歴ダイアログ、「出力履歴」は警報出力履歴ダイアログを直接開く。履歴の閲覧に「送信」は不要。
- 警報出力履歴は通知区分「警報」だけに限定せず、問いかけ・非常ブザーを含む通知出力を扱う。

**操作状態の具体案【未確定】**

- 取得操作の選択は単一とし、別の操作を選ぶと切り替える。選択中のボタンを強調し、「取得停止を選択中／送信で実行」などの説明を表示する。

**遅延・異常判定基準【確定・#31】**

- 新着の有無ではなく取得試行の成否を基準とする【確定】。「新着なし」を障害と扱わない8.2の既定方針に従う。取得元は XML定時・XML随時・雨雲時刻一覧・キキクル時刻一覧・アメダス最新時刻・アメダス地点データの6系列で、最終試行時刻・最終成功時刻・連続失敗回数を独立に保持して判定する。全体状態カードの「取得健全性」は取得元ごとの判定の最悪値に従って集約する。地点データは条件付き取得のため、経過時間条件を適用せず連続失敗回数で判定する【確定】。
- 意図的な停止・スケジュール停止（夜間の定期取得停止等）はこの判定から除外し「停止中」として区別する（8.2で確定済みの方針）。
- 承認済みの運用初期値（異常を遅延より優先）:

  | 状態 | 判定条件 |
  |---|---|
  | 正常 | 直近の取得試行が成功、または再試行待ちだが連続失敗1回以内 |

  | 異常 | 連続失敗5回以上、または同基準から固定10分を超過 |

- タイル（雨雲・キキクル画像）はオンデマンド取得のため周期ベースの判定になじまない。直近数分間の失敗率など別基準を設ける案とする。
- 上記の具体的な数値（連続失敗回数、周期倍率、固定時間）は設定ファイルで変更可能にする【確定】。画面上の設定UIは設けない【確定】。判定方式（新着ではなく試行の成否を見る）と停止中の除外は確定方針とし、数値は承認済みの初期設定であり実測最適値ではない。`fetchHealth` で評価周期30秒、最大走査50件を設定する。地点データは経過時間条件を適用せず、10分間隔で5失敗に至る場合は最悪50分となる。この運用上の扱い・タイル画像の別基準は未決のままE10/K6/L2へ残す。

- 開始: 自動取得を開始／再開する。再開直後に最新状態を確認し、その後は時間帯別周期に従う。初期化・復旧が必要なら長期フィード等による復元を行う。
- 停止: 新しい取得の投入を止め、実行中の処理は完了させる。「停止処理中」と「停止中」を区別する。保存データ・履歴は消さない。手動停止は時間帯が変わっても維持する案。
- 強制更新: 次回予定を待たずに一度だけ取得する。停止中でも実行できるが、自動取得は再開しない。同時実行は集約し、連打・複数端末による多重取得を防ぐ。取得済みの全XMLを再ダウンロードする機能にはしない。画面上の名称は「強制更新」に統一する。
- 今回は取得元単位の操作を設けず、開始・停止・強制更新は全体一括操作のみとする【確定】。取得元単位の操作は、ダッシュボードのレイアウト・情報設計が固まった後に別途検討する。複数情報が同じXMLフィードを共有するため、仮に取得元単位の操作を設ける場合も情報パネルごとに独立した上流取得は起動しない。
- 操作対象はサーバー共通であり全端末に影響することを表示する。将来K端末へ移せるよう操作APIの権限を分離する。
- 監視画面の操作者識別・認証は、本番PoC要件定義書で全体方針が定められているAuthGate（内製SSO、端末単位のログイン可否判定）と連携する前提とし、認証の実装自体は別途（AuthGate連携作業側で）行う【確定】。本書では認証方式の詳細を規定しない。

### 8.3 時間帯別の取得周期【確定・#24】

`config/polling.yaml` を起動時に厳密検証し、不正設定はDB初期化・HTTP待受前に拒否する。設定変更はAPI再起動で反映し、再ビルドは不要。設定UI/API・ホットリロードは追加しない。境界はJST。

| 取得対象 | 4:00〜5:00 | 5:00〜18:00 | 18:00〜20:00 | 20:00〜翌4:00 |
|---|---|---|---|---|
| XML定時・随時フィード | 120秒 | 60秒 | 120秒 | 停止 |
| 雨雲・キキクル索引 | 120秒 | 60秒 | 120秒 | 停止 |
| アメダス最新時刻 | 300秒 | 60秒 | 300秒 | 停止 |
| 画像本体 | 必要な閲覧要求時 | 必要な閲覧要求時 | 必要な閲覧要求時 | 上流取得禁止・検証済みキャッシュ読取可 |

- XML/索引は初期値が同じでも独立設定。`imageCatalogSeconds` は索引の定期周期、`nowcastEnabled / kikikuruEnabled` は画像取得許可である。途中案の「索引定期取得廃止」は取り消されている。
- アメダスは最新時刻変化時、または地点取得の実開始から600秒で現行ブロックを再確認する。地点未試行回で再確認時刻を更新しない。両地点の定期接続はC17 #144。
- 初期XMLは高頻度・長期の4フィード。未成功フィードだけ60/120/240/300秒上限のbackoffで復旧し、成功時reset。通常は高頻度2フィードを用いる。非XMLへ同じbackoffを適用したとはしない。
- 停止境界前に始めた定期ジョブは後続HTTPを含め完了させ、新規ジョブを停止する。画像HTTPは要求ごとに許可を確認する。設定した境界・対象の次回許可時刻を使い、04:00固定や旧mode名に依存しない。
- `readCatalog` は保存索引を読むだけでHTTPを起こさない。同じサービスを定期取得と画像配信で共用する。上流索引の周期と、画面側の読込周期を区別する。
- 気象画面15秒・監視画面5秒は画面更新の初期案であり未実装。保存索引の再読込頻度と通常通知差分の周期はE/Fで承認する。周期は表示遅延保証ではない。

### 8.4 装置異常系警報・問いかけ【確定】

取得系のシステム健全性問題（取得失敗・遅延等）を、気象内容の通知（7章）と**同じ通知パイプライン・同じ下部通知領域**（3.1で確定）に流し込む【確定】。3章の「H端末・K端末の合成」方針のとおり、通知の生成・保持は端末種別によらず共通で行う。H端末相当モードでの表示要否は表示段階のフィルタリングで扱い（後述）、生成経路や通知領域そのものを分けない。

**トリガーの対応【確定】**

8.1で確定した遅延・異常判定を基準に、次のとおり対応させる。

| 区分 | 発生条件 |
|---|---|
| 警報（操作不要） | いずれかの取得元が8.1の「遅延」判定に該当したとき |
| 問いかけ（確認を要する） | いずれかの取得元が8.1の「異常」判定に該当したとき |

非常ブザー相当の区分は今回設けない。装置異常は生命・安全に直結する気象内容の通知（7章）ほどの即時性を要さないと判断する。将来必要になった場合は別途追加を検討する。

- 同一の取得元が遅延から異常へ悪化した場合、7.5と同様の考え方で状態変化として扱い、問いかけを新たに発生させる。異常から遅延へ回復した場合も状態変化として扱い、警報で知らせる。
- 複数の取得元が同時に問題を抱える場合、取得元ごとに個別に通知する（1件に集約しない）。例えば5取得元すべてが異常化すれば問いかけが5件発生する。どの取得元が原因かは通知本文および監視画面本体（8.1・8.2の表）で確認する。（Issue #31実装時に確定変更。旧方針は「最も高い区分で1件だけ通知」だったが、取得元ごとの個別把握を優先する運用判断により変更した）
- 確認操作（ブザー停止）は3.1と同様にフロント側の挙動のみとし、サーバー側での受領監視は行わない（1章・7.1の方針に準じる）。
- 通知用データ（7.3）・通知出力履歴（8.1）には、気象内容の通知（7章）と装置異常系の通知を区別できるフィールド（origin等）を持たせる【確定】。実装は `origin: system`、`sourceType: fetch_health` と取得元別のchangeTypeを持ち、`detectionContext` を別に保持する（#31・#32）。

遅延/異常から正常への回復も `warning` で通知する。停止への移行は問題の解消ではなく、回復通知を出さない。現在の最大6件は取得元別の検知通知であり、D5起動応答にsystemを追加した意味ではない。

**表示段階でのフィルタリング【確定】**

3章の端末種別パラメーターがH端末相当モードのとき、装置異常系の通知（本節でoriginが装置異常系と区別されるもの）は下部通知領域・ナビレールバッジ等の表示から除外する（生成・保持はそのまま行う）。端末台帳でK端末相当と定義されたモードではすべての通知区分を表示する。フィルタリングの実装位置（フロント側／配信APIのクエリ側）は実装時に定める。

### 8.5 監視画面レイアウト概要【設計案】

8.1・8.2で確定した領域構成・ツールバーを踏まえ、画面全体の配置を次のとおりとする。ヘッダー・左ナビレール・下部通知領域は3.1と共通の固定シェルである（3章「H端末・K端末の合成」参照）。

```text
┌─────────────────────────────────────────────┐
│ ヘッダー：気象通報取得監視　20XX/XX/XX XX:XX:XX　端末名：… │← 3.1と共通のヘッダー
├───────┬───────────────────────────────────┤
│        │ 全体状態（4カード：取得運転／取得健全性／スケジュール／処理待ち）│
│ ナビ   ├───────────────────────────────────┤
│ レール │ 取得元別の稼働状況（主テーブル）                     │
│        ├───────────────────────────────────┤   本体は縦スクロール
│        │ 情報別の反映状況（処理結果テーブル）                  │
│        ├───────────────────────────────────┤
│        │ 現在の異常（解消していない問題だけ）                  │
├───────┴───────────────────────────────────┤
│ [取得開始][取得停止]　[強制更新]　[受信履歴][出力履歴]　[送信] │← 8.1で確定したツールバー
├─────────────────────────────────────────────┤
│ 通知領域：3.1と共通。装置異常系の警報・問いかけ／操作送信結果を表示 │← 画面最下部（確定）
└─────────────────────────────────────────────┘
```

- 本体は4段（全体状態・取得元別・情報別・現在の異常）を上から順に並べ、縦スクロールで閲覧する。個々の受信・出力履歴はダイアログで別途開く（8.1で確定済み）。
- ツールバーは8.1で確定したボタン構成のまま、本体の下・通知領域の上に固定する。
- 通知領域は3.1と共通の単一領域を画面最下部に配置する【確定】。8.2で確定した「操作の選択中・結果表示」もこの領域に統合し、平常時は空欄、操作送信中は選択内容・結果、通知発生時は7章・8.4のメッセージを表示する。同時発生時の優先表示順は実装時に定める。
- 具体的な余白・カードの縦横比・レスポンシブ対応は画面実装時に定める。

## 9. 受入条件【設計案】

本書に基づく製造・試験工程の完了判定は、次の観点で行う。個々の数値・実装詳細（ズーム段階、具体的な色コード等）は本書で「実装時に定める」とした設計案の範囲であり、ここでは検証可能な条件のみを挙げる。

### 9.1 表示（地図・パネル）

- 初期表示が雨雲ナウキャストであり、対象会場が4.3で確定した中心点算出方法（カード類を除いた表示領域の中心）に一致すること。
- キキクル（大雨・浸水・土砂）とナウキャストを切り替えても地図中心・ズームが保持され、切り替え直後は再生停止・最新時刻表示になること。
- 右側情報パネルが5.2の順序（気象防災速報／警報・注意報／警報等時系列／警報級の可能性／アメダス／地域時系列予報）で表示されること。
- 5.1の会場別定義に対応する地域・観測地点が固定され、地図の移動・レイヤー切り替えで変化しないこと。
- 取得不能・初期取得中・正常な発表なしが、5.12の取得状態表示ルールに従って区別して表示されること（内容を無表示にする／前回値を残す等の混同がないこと）。
- 警報・注意報バッジが5.7で確定した配色・段階順・短縮表記のルールに従うこと。

### 9.2 取得・保存

- Node.js側の取得処理が、取得監視画面を開閉しても増減しないこと（3.3・8.1で確定した方針）。
- 各情報種別のavailabilityが6.3の定義（available／stale／unavailable）どおりに遷移し、正常な発表なし（空一覧）とunavailableが区別されること。
- サーバー再起動後もディスク永続化（6.1）により履歴・前回正常値が失われないこと。
- 取得失敗時に指数バックオフで再試行し、8.1で確定した遅延・異常判定の閾値（設定ファイルで変更可能）が機能すること。

### 9.3 通知判定（バックエンド）

- 7.4のコード対応表どおりに、警報等コードから通知区分（警報／問いかけ／非常ブザー）が判定されること。
- 強化・緩和・解除（7.5）、新規・継続・訂正・取消・初期取得（7.6）で、確定した通知生成ルールどおりに通知が生成される／されないこと。
- 初期取得・復旧時も通常の状態変化と同様に通知が生成され、プロセス再起動のたびに現況が再評価されること（7.6で確定）。
- 起動時出力APIがpull方式で提供され、端末問い合わせ種別とサーバー起動世代×会場の警報出力権を分離して7.7のルールどおりに応答すること。

### 9.4 監視画面

- ツールバーの開始・停止・強制更新が「送信」操作なしには実行されないこと（8.1で確定）。
- 取得操作が全体一括のみで、取得元単位の個別操作を持たないこと（8.2で確定）。
- 履歴（受信履歴・通知出力履歴・操作記録）が自動削除されず、明示削除まで保持されること（8.1で確定）。
- 8.1の遅延・異常判定が装置異常系の警報・問いかけとして、3.1と共通の下部通知領域に表示されること（8.4で確定）。
- 端末種別パラメーターがH端末相当モードのとき、装置異常系の通知が下部通知領域・ナビレールバッジ等の表示から除外されること（生成・保持は継続すること）（8.4で確定）。
- 訓練通知（3.4）の注入・抹消要求が、通常の取得・検証・正規化・通知判定パイプラインを経由して処理されること。生成された通知・履歴に`isTraining`等の訓練フラグが伝播し、画面上で訓練データと分かる表示になること（3.4で確定）。
- 訓練データが、8.1の「明示削除まで保持」の例外として、抹消要求により削除できること（3.4で確定）。

### 9.5 通知UI（フロント側）

- ヘッダー点滅ブザー・下部通知領域・確認操作・非常ブザーのスヌーズが、既存モックアップ相当の挙動でwx-viewer-poc画面専用に動作すること（1章・7.1で確定）。
- 確認操作の結果がサーバー側に永続化されず、フロントの一時的な状態にとどまること（受領監視を実装しないこと）（1章で確定）。
- 警報一覧ビュー（3.2）に承認／差戻ボタン・行ごとの確認操作が存在しないこと（3.2で確定）。

### 9.6 対象外・除外の確認

- 洪水キキクル、潮位速報（VPBS51）、短時間大雪の速報が実装対象に含まれていないこと。
- 通知の確認状態のサーバー側追跡（受領監視）、基本画面（中央アプリ）への統合が実装対象に含まれていないこと（1章・7.1で確定）。
- 9.1〜9.4の検証において、`isTraining`が付与された訓練データが判定対象から除外されていること（3.4で確定）。
