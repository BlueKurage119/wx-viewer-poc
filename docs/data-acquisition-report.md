# 防災気象情報の取得方法調査

調査日: 2026-09-07（JST）／対象: コミケット警備システムの防災気象情報画面

## 1. 結論

**気象警報・予報・気象防災速報は気象庁の公開XML、雨雲・キキクル・アメダスは気象庁Web画面用JSON・タイルを取得し、Node.jsで正規化してReactへ配信する構成を推奨する。** 無料公開経路で今回の主要な表示項目を取得できることを、公式資料・提供サンプル・東京の実データで確認した。追加対象のキキクルは大雨・浸水・土砂のPNG取得まで確認し、洪水の複合ベクトル描画は未検証。公開XMLの提供ページはWeb参照のみとし、保存していない。

今回の成果物は取得方式の調査であり、アプリ・API・通知機能は実装していない。React＋TypeScript＋Vite＋Node.js、Material Webの方針は維持する。資料内の実装例・指示は技術的な参照情報として扱い、今回の作業範囲はユーザーの依頼を基準にした。

重要な判断は次のとおり。

- **現況の警報と、将来の警報等の見通しを分ける。** `VPWP50`は予測であり、現在の警報の発表・解除判定には使わない。
- **初期状態を復元する。** 定時フィードで実在を確認した集約電文`VPWS50`を初期化・復旧に使い、現象別`VPWW55–61`で更新する。フィードに掲載がないことを「発表なし」とはしない。
- **江戸川臨海のアメダスIDは`44136`。** 実JSONで湿度を含む提供要素を確認した。地域時系列予報の気温地点「東京」`44132`とは別。
- **時刻一覧を固定しない。** 実レーダーのN1とN2は基準時刻が5分ずれており、既存処理の結果は過去60分～未来55分の24コマになった。
- **正常・取得不能・前回値を区別する。** 現行モックには、通信失敗や不正な構造を「警報なし」と表示できる経路がある。
- Web画面用JSON・タイルは、公開XMLの仕様書と同等の安定したAPI契約として扱わない。実装依存部分を取得アダプターに隔離する。
- **気象防災速報を追加可能。** VPBS50を第一対象とし、対象区域・本文・訂正取消を管理する。東京都の速報をすべて江東区対象とはしない。
- **地図をレイヤー選択式へ拡張可能。** 雨雲／大雨キキクル／浸水／土砂を第一段階、洪水キキクルの複合表示を次段階とする。

### 2.1 XML取得URL

基点: `https://www.data.jma.go.jp/developer/xml/feed/`

| 用途 | URL末尾 | 方針 |
|---|---|---|
| 定時・高頻度 | `regular.xml` | 60秒間隔で確認する提案 |
| 随時・高頻度 | `extra.xml` | 同上 |
| 定時・長期 | `regular_l.xml` | 初期化・復旧時に参照 |
| 随時・長期 | `extra_l.xml` | 同上 |

高頻度フィードは毎分更新・直近少なくとも10分、長期フィードは毎時更新・数日分を掲載する。これは取得間隔の上限保証や可用性保証ではない。[W1]

**今回の差異:** 公開電文一覧は警報等時系列を随時に分類しているが、取得した`regular_l.xml`に東京の`VPWP50`が実在した。`VPWS50`も定時に存在した。前の検討で「VPWP50は随時のみ」とした前提を修正する。収集対象は両フィードの和集合とし、電文種別のフィード所属を固定して取りこぼさない。高頻度フィード本体の実GETは今回未実施で、URLは公式ページのリンクによる確認。

フィード内のリンクをたどってXMLを取得する。日時・官署コードから電文URLを自作しない。Atomのタイトル・概要は絞り込み補助とし、本文の名前空間、Control、Head、地域要素を検証してから採用する。全国集約のURL末尾`010000`を北海道限定と解釈しない。

## 3. XMLの読み取り方

### 3.1 共通処理

- XML名前空間を考慮する。Report/Control、Head、Body、気象要素の名前空間は同一ではない。ローカル名だけの一致は調査用抽出に限定する。
- `Control/Status`の通常・訓練・試験を区別する。PoCの通常画面へ訓練・試験を混入させず、検証モードで明示する。
- `Control/DateTime`（発信）、`Head/ReportDateTime`（発表）、`TargetDateTime`（基点）、有効期間、実際の受信時刻を別々に保持する。原文のUTC/JSTを尊重し、画面はJST。
- `InfoType`は個別仕様に従い処理する。警報・時系列は発表／訂正、予報類は発表／訂正／遅延等。一般の取消処理と、本文中の警報の解除は別。
- 共通運用指針は独立情報単位をControlのTitle＋EditorialOffice＋Status、EventIDがある場合はそれも含めて定義し、単位内の最新をDateTimeで決める。**実東京電文ではEventID・Serialが空であるため、これだけを全地域共通の保存キーにしない。** 本調査では電文種別・対象府県も保存キーへ追加する設計を推奨する。多地域間衝突を避けるためのアプリ側の補強であり、公式共通キーの引用とは区別する。
- URL／Atom IDで二重取得を避け、本文ハッシュで同一内容を識別する。Serialの大小や到着順だけでは現行を決めない。逆順到着でも過去版へ巻き戻さない。
- XSD適合だけでなく、必要地域・単位・時間参照・既知バージョンを検証する。未知コードや構造変更を「なし」に変換せず、原文を保持して未対応として扱う。

根拠: 運用指針の冊子pp.4–7（PDF物理pp.7–10）、管理部・ヘッダ部整理表、対象電文の解説。[L1][L2]

### 3.2 警報・注意報の現況

| 電文 | 現象 |
|---|---|
| VPWW55 | 大雨 |
| VPWW56 | 土砂災害 |
| VPWW57 | 高潮 |
| VPWW58 | 暴風・暴風雪 |
| VPWW59 | 波浪 |
| VPWW60 | 大雪 |
| VPWW61 | 雷・融雪・濃霧・乾燥・なだれ・低温・霜・着氷・着雪等 |
| VPWS50 | 上記の警戒・注意事項の全国集約 |

`Body/Warning`のtypeを選び、市町村等の`Item/Area/Code=1310800`を読む。東京都・東京地方のHeadlineを江東区の現況として代用しない。`Kind`のName、Code、Status、LastKind、Property、Additionを保持する。種別コードと危険度のSignificancy/Codeは別の辞書である。[L3]

発表・継続・段階切替を扱い、解除と明示的な発表なしを区別する。市町村単位の解除Code=00と、上位集約の解除対象種別コードの保持を同じ規則で処理しない。VPWW61には複数Kindがある。

**復元案:** 最新VPWS50を検証して全要素の基準状態を作り、以後のVPWW55–61を現象別に反映する。集約電文の外側の発信時刻だけで更新優先度を決めず、Kind/DateTimeにある対象要素の発表時刻と個別電文の発表時刻を比較する。新しい個別警報を遅れて届いた集約で上書きしない。集約にない種別を削除する場合も、正常な完全スナップショットであることと基準時点を確認する。初期集約が取れなければ未初期化表示を続ける。

2026体系の「レベル4危険警報」を明示的に扱う。旧H27や旧JSONのコード番号大小から危険度を推測しない。新旧電文は二重表示せずR06を優先する。

なお、VPWW55–61／VPWS50だけでは指定河川氾濫等を網羅しない。河川別`VXKOii`等は別電文と地域対応が必要であり、今回の画面の警報一覧を「すべての防災情報」と表示しない。河川情報の詳細取得設計は追加調査事項とする。[L3 PDF p.2]

### 3.3 警報等時系列（VPWP50）

`MeteorologicalInfos type=量的予想時系列（市町村等）`を読み、江東区ItemのKind/Propertyを抽出する。`TimeDefines/TimeDefine@timeId`と各値の`refID`を**同じTimeSeriesInfo内**で結合する。異なるブロックの同じIDを混ぜない。

雨・風・雪などの量的予想と危険度を別項目にする。陸上／海上、地域内の細分類、単位、期間を保持し、最大値・範囲等を単なる現在値にしない。定時発表時刻によって区間数が変わる。

修正は気象要素単位で、Kind/Status（発表／継続）とKind/DateTimeで修正状況を知る。修正発表はInfoType=発表であり、誤りを直す「訂正」と異なる。継続要素も含めて提供される構造を読み、値を省略した差分パッチと決めつけない。現在の警報が予測に即時反映されるとは限らない。[L6]

### 3.4 早期注意情報

- `VPFD61`: 明後日まで。6時間区間と明後日の12時間区間をTimeDefinesから取得する。大雨と土砂災害は別項目。
- `VPFW60`: 明々後日以降。電文中に残る明後日部分はVPFD61との併用時には使わない。発表日のJST日付と時間定義で切り分ける。
- `PossibilityRankOfWarning`の高・中・なし、空要素の`condition="値なし"`を保持する。「値なし」は通信障害や数値0ではない。画面の凡例で意味を伝え、独自に「低確率」に変換しない。
- Control/TitleやInfoKindに旧名称が残る。名称の文字列だけで旧電文と決めない。VPFD61はInfoKindVersion=1.5_0、VPFW60は1.2_0を実データで確認した。
- 後半の「雨」は大雨と土砂災害を併せた表現であり、前半のどちらかへ同じ値を機械的にコピーしない。[L7][L8]

### 3.5 地域時系列予報（VPFD51）

Bodyには府県天気予報、降水確率、地点の最高・最低気温、地域時系列が共存する。今回の右下パネルは`３時間内卓越天気`、`３時間内代表風`、`３時間毎気温`を選ぶ。天気・風はArea=東京地方130010、気温はStation=東京44132。

気温は時点、天気・風は3時間区間なので、異なるTimeDefinesを配列番号だけで横並びにしない。風速階級1–6をm/sの実数と解釈せず、対応する範囲として表示する。今回は実東京XMLで東京地点の気温26、27、26、26度等と単位・refIDを確認した。[L9]

### 3.6 気象防災速報（追加検討）

**VPBS50を追加することを推奨する。** 現況警報とは別の速報一覧として、Head/Title、Headline/Text、対象区域、発表・観測時刻、情報タグ、EventID、更新状態を保持する。地図の補助パネルから詳細を確認する案とし、通知音や自動判断は今回追加しない。

| 電文 | 内容と採用範囲 |
|---|---|
| VPBS50 | 府県気象防災速報。線状降水帯発生／直前予測、記録的短時間大雨、短時間大雪等。第一対象 |
| VPHW50／51 | 竜巻関連。標題が気象防災速報（竜巻注意／竜巻目撃）へ変更されるが別電文形式。速報全般を網羅する場合の追加候補 |
| VPBS51 | 潮位の速報。最新保存資料p.2では当面提供見送り。実提供開始は未確認で、今回の取得対象には固定しない |

根拠は[L10]と技術情報634号。旧VPOA50／VPFJ50等の経過措置電文と新VPBS50を二重表示しない。名前が「速報」でも同じ本文スキーマとは限らない。

地域はHeadline/Information[@type="情報タグ"]/Item/AreasとBodyのAreaをcodeType付きで読む。江東区1310800は直接対象、東京地方130010・23区東部130012等は「江東区を含む広域情報」として区域名をそのまま示す。地域不明は不明のままとし、タイトルの「東京都」だけで採用しない。

実取得した`20260905220832_0_VPBS50_130000.xml`は東京都の線状降水帯直前予測だが、対象タグは**伊豆諸島南部130030**だった。江東区向け一覧に混入させない負例を確認できた。広域一覧では区域を明示して閲覧できる設計がよい。

InfoKindは「気象解説情報」、Version=1.5_0。InfoTypeは発表／訂正／取消。EventIDの親番は一連の現象を関連付ける。枝番を伴う情報には、親番の内容を更新する場合と、別の補足・追加情報を発表する場合がある。完全なEventIDを更新単位として保持し、親番は関連付けに使う。親番だけの上書きで別の速報を消さない。訂正でReportDateTimeが変わらない場合を考慮し、Control/DateTimeで更新を判別する。[L10 pp.3–6,35]

専用の有効期限を確認できていないため、アプリの表示期間を気象上の解除期限に見立てない。発表時刻・対象時間・取消状態を表示し、最近の速報と履歴を分ける。受信不能を「速報なし」としない。江東区対象の実速報、訂正・取消の実電文、竜巻系の全仕様対応は追加検証事項。

#### 公式速報地図を使った対象判定（ユーザー提示URLの検証）

[ユーザー提示の速報地図](https://www.jma.go.jp/bosai/map.html#11/35.637/139.784/&element=sokuhou&contents=information)のHTML・公開スクリプトと取得JSONを確認した。`11/35.637/139.784`は表示ズームと地図中心であり、「この地点に対する速報を返すAPI」の検索条件ではない。

地図は以下を読み、`mapKey=class10s`（一次細分区域）を塗り分ける。

```text
https://www.jma.go.jp/bosai/information/data/r8/information.json
https://www.jma.go.jp/bosai/information/data/r8/tornado.json
```

information.jsonは実GET、tornado.jsonは公開スクリプトで参照を確認したが実GETは今回行っていない。

- `header`でVPBS50等を選び、`areaTag[].code`を地図の区域に対応させる。タグがない場合にはareaCodesと地域階層を用いて広域へ展開する処理がある。
- 線状降水帯は`senjouHassei`／`senjouChokuzen`の`class10Code`、`validTime`、`validOut`を使う。関連配列`senjouYosoku12h`はclass15sCodesから上位区域へ対応させる処理がある。
- `mapValidOut`、`validMap`や線状降水帯ごとの期限を使い、地図上の表示対象から外す。JSONには履歴が残るので、配列に存在するだけでは「現在表示中」と判定できない。
- `sokuhou`レイヤーはVPBS50／51だけでなく竜巻JSONも合成する。VPBS50だけのPoCは公式地図の全情報と同等ではない。

今回のJSONにはVPBS50が18件あり、東京都には伊豆諸島南部・北部対象の速報が含まれた。2026-09-06 07:08の直前予測はXMLと同じEventID・130030で、`validOut=true`だった。2026-09-07 14:18の速報は伊豆諸島北部130020で、東京地方130010ではない。これらを「江東区近辺の速報」としないことを確認した。これは取得時の検証記録であり、現在の速報状況ではない。

**推奨する使い分け:** 本文・発表・訂正取消の正本はXMLとし、公式地図と同じ表示対象・表示期限を求める場合にWeb JSONを補助アダプターとして追加する。header＋完全なEventID＋editorialOffice＋発信時刻等で同じ版を照合し、片方が遅い場合は相違を残す。JSONのvalid／validMapをXMLの気象上の解除・取消と同一視しない。

江東区向けの一次判定は`1310800 → 130012 → 130010`の包含関係で行い、「東京地方対象（江東区を含む）」と表示する。**この地図だけでビッグサイト敷地への直接影響や半径数kmの危険を判定することはできない。** 「近辺」は現段階では東京地方を含む広域情報という意味に限定する。将来、任意の会場範囲との交差を判定する場合は会場範囲と区域ポリゴンを別途定義するが、元の速報の区域精度を超える判定にはしない。実地図のブラウザ描画比較は未実施。

## 4. 雨雲レーダー

取得URLは既存実装と実GETで確認した。

```text
https://www.jma.go.jp/bosai/jmatile/data/nowc/targetTimes_N1.json
https://www.jma.go.jp/bosai/jmatile/data/nowc/targetTimes_N2.json
https://www.jma.go.jp/bosai/jmatile/data/nowc/{basetime}/none/{validtime}/surf/hrpns/{z}/{x}/{y}.png
```

### 4.1 キキクル（追加検討）

**無料のWeb表示用タイルで追加できる見込み。** 正式配信の数値格子GRIB2等とは別経路であり、公開XMLに危険度分布画像が含まれるわけではない。画像の色から会場の危険度を自動判定する処理は今回含めない。[W6]

2026年の公式画面には大雨・土砂・浸水・洪水がある。大雨キキクルは浸水と洪水を重ね合わせた公式の統合表示。タイル生成時の詳細な算出規則は今回未検証。会場周辺の概観には大雨・浸水を第一候補にし、土砂も広域確認用に選択可能とする。[W6][W7]

| 表示 | element／画像識別子 | 形式と意味 |
|---|---|---|
| 大雨キキクル | heavyrain／rain_mesh | PNG格子。浸水と洪水の危険度を統合 |
| 浸水キキクル | inund／inund | PNG格子。実況・1時間先までの予測に基づく |
| 土砂キキクル | land／land | PNG格子。現在の公式解説では最大6時間先までを利用し、黄は6時間、赤は3時間、紫は2時間等で判定 |
| 洪水キキクル | flood／複数レイヤー | PBF流路、指定河川GeoJSON、水害リスクライン、内水氾濫等を重ねる。単一PNGでは公式画面を再現できない |

危険度は予測を含む判定結果であり、未来の同時刻の実況ではない。土砂を一律「2時間予測」とする旧資料の説明を現行へ適用しない。浸水・洪水の現行解説には過去30分間の最大危険度表示も記載されている。[W8–W10]

## 6. 取得・配信構成の提案

```text
公開XMLフィード ─→ XML取得・地域抽出 ─┐
雨雲・キキクル  ─→ JSON/タイル取得     ─┼→ 検証・正規化 → 保存/キャッシュ → React
アメダスJSON   ─→ 観測取得         ─┘
```

Node.js側で取得を一元化する。Reactが全端末からXMLを取りに行く構成にしない。主目的は取得負荷・状態管理・仕様変更の集約であり、「常にCORSで取得不能だから」とは説明しない。今回latest_timeのHTTPヘッダにはAccess-Control-Allow-Origin: *があった。

### 推奨する動作（アプリ側の設計提案）

- **初回:** 長期フィードから最新集約・予報・時系列を取得し、対象地域を検証。高頻度フィードも取り込んで初期取得中の更新を補う。処理済みID・原文・現行状態を永続化する。
- **通常:** 両高頻度フィードを60秒周期、レーダー・キキクル時刻・アメダス最新時刻も60秒周期で確認。同一取得の同時実行をまとめる。端末からの更新操作で上流TTLを無制限に回避させない。
- **アメダス更新:** 最新時刻が変われば対象ブロックを再取得。最新時刻が不変でも現行ブロックを10分ごとに再確認する提案とし、遡及訂正を完全検出する保証はしない。
- **タイル:** 必要な画角・時刻だけを読む。Node.js側に許可済み時刻・ズーム限定のタイルキャッシュを設ける案を推奨。任意URLを受け取る汎用プロキシは作らない。
- **復旧:** 永続化済み状態と長期フィード・集約で復元。停止期間が掲載期間を超えた場合、過去の全履歴は回復できない。復元した現況と失われた履歴を区別する。
- **失敗:** タイムアウト10秒、指数バックオフ60秒から最大5分を初期案とする。正常な前回値を残し、失敗時に空配列で上書きしない。不正構造・未対応コードも取得失敗と区別して記録する。
- **鮮度:** 取得成功時刻・情報発表時刻・観測時刻・有効期間を別に管理。長期間変化しない警報の発表日時だけで古いと判定しない。通信障害や最新観測の遅延を表示し、データ欠如を「安全」に変換しない。

速報地図の表示対象情報を取り込む場合、Web JSON補助アダプターも60秒周期で確認する案とする。取得不能時はXML速報を消さず、「地図表示状態は未確認」として扱う。

将来の内部APIは現況警報／警報等時系列／早期注意／地域時系列／レーダー／キキクル／アメダス／気象防災速報の単位で提供する。共通メタ情報はsource、issuedAt、validAt/validFrom/validTo、fetchedAt、lastSuccessAt、availability（available/stale/unavailable）、sourceVersionを持たせる案とする。正常な発表なしはavailable＋空の警報一覧で表現し、取得不能とは明確に分ける。観測値ごとの品質と情報全体の通信状態も別にする。URLやTypeScript型の確定・実装は次工程。
